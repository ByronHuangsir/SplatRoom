## 0. 用户需求原文（逐字记录，2026-09-30）

> 1、我需要更好的交互性能和更均衡的显示呈现效果；
> 2、随着需要处理的模型越来越大，而大部分用户的电脑性能实际上没有大的提升，处理效率就非常重要；
> 3、可以参考 supersplat 3.3.0 以上版本，处理的速度很快，并且显示的效果没有大的影响；
> 4、splatroom 在旋转时会出现短暂的排序错误，虽然停止旋转模型后再微动模型影响就会消失，但是依然体验不好，我希望能解决这个问题；
> 5、请同时参考市面上的其他浏览器或编辑器，找到能够根本解决性能与显示的均衡的方案。

**这五条合成一句话**：以"普通用户硬件上流畅编辑越来越大的模型"为目标，
根治旋转错序，向 SuperSplat 3.3.0+ 的性能水平看齐，同时显示质量不能有明显妥协。

## 1. 结论先行

1. **旋转错序（需求 4）的根治方案已经建成**：unified 通路（引擎 GPU 同帧排序，
   `?unified=1`，3.23.44–3.23.53 六轮迁移完成）把"顺序与绘制"放进**同一帧**，
   结构上消灭了滞后——这正是 CPU worker 排序回传延迟（~0.5 s，与模型大小无关）这个根因的对症解。
   **剩下的工作不是"再找方案"，而是"转正"**：把拾取搬进 worker、定 WebGL2 策略、默认开启。
2. **交互性能与显示均衡（需求 1）的行业标准答案只有一个**：把投影/剔除/排序搬进 GPU compute。
   官方锚点：同一份 20M 模型，GPU compute 架构 **10.22 ms/帧**（97.8 fps @ M4 Max），
   架构等价于我们的 CPU 排序路径 **44.93 ms/帧**（22.3 fps）——**4.4× 的差距来自架构，不来自后端 API**
   （PlayCanvas 官方博客图表数据，已核对组件源码）。
3. **大模型效率（需求 2）是三条腿**：内存（SH 物化策略 + 流式加载）、
   帧时间（GPU 排序 + 运动期降级）、交互（选择/拾取 worker 化或 GPU 化）。
   SuperSplat 3.4.2（2026-09-23）刚落地"single sweep PLY 加载"，方向一致。
4. **市面调研（需求 5）的共识**：CPU 排序的查看器至今都有同样的运动伪影
   （mkkellogg / antimatter15 的 known issues 原文自认），**没有第二条根治路**——
   只有 WebGPU compute 排序。我们已经在正确的路上，且比多数开源实现走得更远。

## 3. 排序错序：为什么 unified 通路是根治（需求 4 专节）

**根因回顾**（`docs/排序错序-结构性解法…`，全部实测）：

```
现状（主线）：为位姿 A 算顺序 → worker 排序 → 回传主线程 → 上传 → 相机已转到 B 才消费
             ⇒ 顺序永远滞后一拍；小模型排序只要几毫秒，但回传+上传+等帧的延迟与模型大小无关
unified：    投影 + GPU 基数排序 + indirect draw 全在 GPU 上、同一帧内完成
             ⇒ testCameraMovedForSort 每帧转角 >1e-3 rad 即重排，顺序永远是这一帧的
```

**已完成的迁移**（全部在 `?unified=1` 之内，主线零改动）：

| 轮 | 版本 | 交付 | 验收 |
| --- | --- | --- | --- |
| 调色对齐 | 3.23.45 | 引擎 gsplatPS 材质上对齐我们定制的色调映射/伽马 | 双通路亮度/色彩对照 |
| 包围盒 | 3.23.48 | unified 通路恢复包围盒 | — |
| edit state | 3.23.49 | per-splat 编辑状态上 GPU 排序路径 | — |
| 拾取族 | 3.23.50–51 | CPU 拾取（单点/矩形/环模式/深度 pass），引擎 GPU 拾取路线已用证据关死 | 环模式 0→468（主线 208）；删除判据双向通过 |
| crop box | 3.23.52 | 片元级盒/柱/椭球裁剪，缩盒后与主线一致到小数点后两位（48.62% 双通路一致） | 探针 69/70/71 |
| 粒子效果 | 3.23.53 | scatter/ripple/burst/fade 四判据双通路全过，恢复后精确回到基线 | 探针 73 |

**转正前的三件收尾**（见 §6 路线 M1）：

1. **拾取进 worker**：`src/splat/cpu-pick.ts` 是纯计算（当初就为此写成无 playcanvas/DOM 依赖），
   20M 上约 1 s/手势，是 unified 转正前最后一块交互短板 → 搬进 selection worker。
2. **WebGL2 策略**：引擎 `GSPLAT_RENDERER_AUTO` 在 WebGL2 上自动回退 CPU 排序 ⇒ WebGL2 用户仍会看到错序。
   SuperSplat v3 的做法是**直接砍掉 WebGL2 路径**（v3.0 release notes："The CPU sort worker and WebGL2 path are gone"）。
   我们的选项：a) WebGL2 上沿用"排序闸门 + 停手干净帧"（P0-2 已落地，把错序从"连续滞后"压成"停手一帧"）；
   b) 提示用户 WebGPU 模式体验更好。**不建议**为 WebGL2 重写 GPU 排序（WebGL2 无 compute，不可能同帧）。
3. **默认开启与回归**：`?unified=1` 转为默认（保留 `?unified=0` 逃生门），跑全量双后端批量。

## 4. 市面方案调研

### 4.1 SuperSplat 3.3.0 → 3.4.2 的增量（本轮查证）

- **3.3.0（2026-09-14）**：运动剔除修正（贡献上限封到 1）+ 基于深度的遮挡剔除 —— 即"交互期降级"的打磨（我们 P0-3 的对标物）。
- **3.4.2（2026-09-23，当前 latest）**：**"Load PLY in a single sweep, show load progress"** ——
  PLY 单遍扫描加载 + 加载进度显示 + WebP 解码修复。与我们 20M 导入 57.4 s 的痛点正对。
- 官方持续方向没变：GPU compute 渲染器（引擎 2.19.0 起）+ Streamed LOD（SOG 分块流式，Viewer 运行时预算桌面 2M/4M）。

### 4.2 其他浏览器查看器 / 编辑器（2026-09-30 查证）

| 方案 | 排序位置 | 运动伪影 | 对我们的启示 |
| --- | --- | --- | --- |
| **SuperSplat / PlayCanvas** | WebGPU compute（GPU radix sort），**v3 起 WebGL2 路径已删除** | 无（同帧排序）；运动帧另有免排序的 stochastic 模式 | 正解样板；我们 unified 通路即引擎同款 |
| **Babylon.js 8**（2026-02） | WebGPU GS 内置 | 无（WebGPU 路径） | 引擎级集成的另一例证；iPhone 15 上 3M@60fps |
| **three.js 原生 GS**（2026） | 官方新增 GS 加载 + WebGPU 渲染器，支持 SPZ 3/4 | WebGPU 路径无 | GS 已成浏览器一等公民，WebGPU 是分水岭 |
| **Spark.js 2.0**（World Labs，2026-04） | WebGL2 | 有（CPU 路径） | 但它的 **LoD Splat Tree + .RAD 流式 + GPU 虚拟内存分页**值得借鉴（大场景流式） |
| **mkkellogg GaussianSplats3D** | CPU（WASM SIMD）+ octree 剔除 | **known issues 原文自认**："Artifacts are visible when you move or rotate too fast (due to CPU-based splat sort)" | CPU 排序的运动伪影是行业通病，不是我们独有的 bug；但它 octree 预剔除 + 渐进加载可借鉴 |
| **antimatter15/splat** | CPU worker | 同样有 | 同上 |
| **WebSplatter**（arXiv 2602.03207） | WebGPU GPU radix sort | 无 | 学术侧同样结论：跨设备 WebGPU compute 是唯一根治路 |
| **NanoGS**（Unreal 插件，2026-03） | GPU 加速排序 + Nanite 风格 LOD | 无 | 屏幕空间误差选 LOD 的思路可映射到浏览态预算 |

**调研结论**：不存在"第三条路"。性能与显示的均衡 = **GPU compute 同帧排序（正确性）+ 交互期降级（帧时间）+ 分级/流式（规模）** 三件套。SuperSplat 快而不损画质的核心不是某一招，而是这三层的组合；我们 unified 通路已覆盖第一件，后两件在 P0-3 / P2-6 已有部分落地。

## 5. 根本方案总架构

```
                     ┌─ 正确性层（需求4）：unified 通路 = 引擎 GPU 同帧排序，默认开启
                     │   · WebGL2 回退：排序闸门 + 停手干净帧（P0-2 已落地）
目标：普通硬件流畅编辑大模型
                     ├─ 帧时间层（需求1）：交互期降级 + unified 通路每高斯 1 次投影
                     │   · 运动/静止双态：静止帧全量精确；运动帧按 GPU 帧时间预算自适应
                     │     （参考 SuperSplat motionBudgetMs=12 的贡献剔除，实测 −26% GPU）
                     └─ 规模层（需求2）：分级 + 流式 + 内存经济
                         · SH 降档导入（−3.4 GB，唯一大杠杆，用户决策点）
                         · PLY 单遍扫描加载（对标 SuperSplat 3.4.2）
                         · 浏览态 SOG/LOD 预算（桌面 4M 量级，编辑态放开）
                         · 拾取/选择 worker 化（cpu-pick.ts 进 worker）
```

**显示质量不妥协的保证**：所有降级都只在**运动帧**生效（静止帧回到全量精确渲染，
等同 SuperSplat 的 pendingResolve 干净帧机制）；所有开关可逆、保留逃生门（`?unified=0`、
波段手动提高、SH 降档默认关 + 设置面板可见）。
