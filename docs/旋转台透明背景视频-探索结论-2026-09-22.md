# 旋转台"透明背景视频（MOV）"探索结论（2026-09-22）

用户休息前给的第 4 件事：**探索旋转台视频导出透明背通道视频（mov 格式）**。
结论先行：**在当前技术栈里做不到"应用内直接导出透明 MOV"**，原因是**编码器**这一层，
不是封装格式那一层 —— 而且实测比预期更严格：**这台机器上连"透明 WebM"也编不出来**。
下面是实测数据与三条可行路线（含推荐）。

---

## 1. 实测：WebCodecs 的 alpha 支持（`docs/probes/video-alpha-support.cjs`）

在同一台机器、同一个 Chromium（Electron 43 / Chromium 150 内核，Edge 无头）里逐个问
`VideoEncoder.isConfigSupported({ codec, width, height, bitrate, alpha })`：

| codec | `alpha: 'discard'` | `alpha: 'keep'` |
|---|---|---|
| `vp8` | ✅ true | ❌ **false** |
| `vp09.00.10.08` | ✅ true | ❌ **false** |
| `av01.0.05M.08` | ✅ true | ❌ **false** |
| `avc1.42001f`（H.264） | ✅ true | ❌ false |
| `hev1.1.6.L93.B0`（H.265） | ❌ false | ❌ false |

`MediaRecorder.isTypeSupported`：

| type | 支持 |
|---|---|
| `video/webm;codecs=vp9` / `vp8` / `video/webm` | ✅ |
| `video/mp4;codecs=avc1.42001f` | ✅ |
| **`video/quicktime`** | ❌ **false**（连容器都不认） |

⇒ 往返验证（编一帧"左半边不透明、右半边透明"的 RGBA，再解码读 alpha）在三个候选 codec 上
**都在 `isConfigSupported` 就被拒**，根本没进编码。

**为什么预期里"透明 WebM 应该可以"**：Chromium 有 `AlphaEncoderWrapper`（双编码器分别编 Y 与 alpha，
见 [Chromium issue 40266640](https://issues.chromium.org/issues/40266640)），但它**只在特定平台/开关下启用**；
本机（Windows + 该内核版本）没有开。
上游 SuperSplat 之所以有"透明背景"选项，是因为它用 webm-muxer + VP9 alpha 的老路，
在**能编 alpha 的环境**里成立；本项目的封装库换成了 mediabunny 1.50.8：

- mediabunny 里**只有 Matroska/WebM 的 muxer 会写 alpha**（`EBMLId.AlphaMode` + BlockAdditions，
  见 `matroska-muxer.ts:381/758/923`），并且它的 alpha 是**自己再开一个 `VideoEncoder` 编 alpha 平面**
  （`media-source.ts:809-843`）⇒ **仍然依赖上面那条实测结论**；
- **ISOBMFF（mp4/mov）muxer 里连 `sideData` 都没有** ⇒ 就算编出 alpha，MOV 也装不下；
- MOV 容器本身"允许 prores"（`VIDEO_CODECS` 里有），但**没有 ProRes 编码器**：
  `@mediabunny/prores` 官方说明是 **decoder only**（"Browsers have no support for Apple ProRes
  in their WebCodecs implementations"）；Uncompressed 32-bit / QuickTime Animation 在 Windows
  Chromium 里同样没有编码器。

### 1.1 "也许只是被特性开关挡住"——这条假设也测了（不成立）

因为 Chromium 里有现成的 `AlphaEncoderWrapper` 实现，值得确认一下是不是只是开关没开。
`video-alpha-support.cjs` 支持追加 Chromium 开关（第 2 个参数），逐个试：

| 追加的开关 | vp8 | vp9 | av1 | h264 | h265 |
|---|---|---|---|---|---|
| （无，基线） | ❌ | ❌ | ❌ | ❌ | ❌ |
| `--enable-features=WebCodecsAlphaEncoder` | ❌ | ❌ | ❌ | ❌ | ❌ |
| `--enable-features=AlphaEncoderWrapper` | ❌ | ❌ | ❌ | ❌ | ❌ |
| `--enable-blink-features=WebCodecsAlphaEncoding` | ❌ | ❌ | ❌ | ❌ | ❌ |

⇒ 至少在我能猜到的这几个开关下都不放行。**结论不变：本机拿不到任何带 alpha 的编码器**
（要复现：`node docs/probes/video-alpha-support.cjs "<url>" "--enable-features=AlphaEncoderWrapper"`）。

### 1.2 两个"以后真能编 alpha 了也会踩"的坑（提前记下）

1. **预乘问题**：splat 片元输出的是**预乘 RGBA**（`splat-shader.ts:684`
   `pcFragColor0 = vec4(finalColor * alpha, alpha)`），而 WebM/Matroska 的 alpha 惯例是**非预乘**。
   直接喂给编码器会让半透明边缘**发暗**（不是变透明）。真要走路线 B，必须先 un-premultiply
   （8 位预乘反解有量化误差，最好在 16F 回读缓冲上做，或让着色器在导出时输出非预乘）；
2. **容器会静默吞掉 alpha**：ISOBMFF（mp4/mov）muxer 忽略 sideData，所以"透明勾选框 + MOV"
   会产出一个**看起来正常但其实没有 alpha** 的文件。真做 UI 时必须按容器禁用透明选项。

**当前状态**（代码层面）：`src/ui/video-settings-dialog.ts:269` 把"透明背景"整行 `hidden = true`
（注释还写着"till we add support for webm"，对当前架构已过时），
旋转台对话框（`turntable-video-dialog.ts`）连字段都没有，且 `render.ts:1476` **硬写**了背景色。
**好消息**：抓透明帧这件事本身是通的 —— splat 片元输出预乘 RGBA
（`splat-shader.ts:684`）、离屏 RT 是 RGBA、默认清屏色是 `(0,0,0,0)`，
图片导出（PNG RGBA）已经产出过带 alpha 的成品（`png-writer.ts:44` colorType 6）。

## 2. 三条可行路线

### 路线 A（推荐）：**透明 PNG 序列 + 外部编码器合成 MOV**

- 应用侧：旋转台新增"帧序列（PNG, RGBA）"输出 —— 复用现有的旋转/抓帧循环
  （`render.ts:1513-1572` 的逐帧 `colorBuffer.read`）+ 现有的 PNG 写入器
  （`png-writer.ts`，`colorType 6` 已经过验证）+ 现有的"写目录"通路
  （`render.ts:1221-1243`，`render.keyframes` 就是这么把逐帧 PNG 落盘的：Electron 下走
  `window.splatroomFS.writeFile`，浏览器下走 File System Access / 下载兜底）
  ⇒ 也就是**这套零件全是现成的**，只缺一个"旋转台 + 序列"的入口；
- 用户侧（一行命令，ProRes 4444 带 alpha）：

```bash
ffmpeg -framerate 30 -i frame_%04d.png -c:v prores_ks -profile:v 4444 -pix_fmt yuva444p10le -vendor apl0 out.mov
```

  （想要无损逐行、体积小一点也可以 `-c:v qtrle`（QuickTime Animation，支持 alpha））
- 优点：**完全在自己掌控内**、无新依赖、任何 NLE（Premiere / DaVinci / FCP）都能直接吃；
- 代价：1080p 720 帧的 PNG 序列大约几 GB 磁盘，且多一步外部命令。

### 路线 B：等/换运行环境 —— 用 **MediaRecorder 的 VP9 alpha**（WebM，不是 MOV）

如果哪天本机的 Chromium 支持了 `alpha: 'keep'`（换版本/换平台，或加启动开关），
就能走"WebCodecs 编 VP9 + alpha 平面 → WebM"这条路（mediabunny 原生支持）。
**但产出只能是 `.webm`**（透明 MOV 仍然要在外部转一次）。
⇒ 建议：**先做 A，等 B 的条件具备再补一层"直接出 WebM"**。

### 路线 C：应用内直接出透明 MOV（成本高，不建议）

- C1 引 `ffmpeg.wasm`（ProRes 4444）：+30 MB 依赖、无 COOP/COEP 时只能单线程、720 帧要几分钟；
- C2 自研未压缩 32-bit MOV writer：1080p ≈ 8.3 MB/帧 ⇒ 720 帧 ≈ 6 GB，实务不可接受；
- C3 走 `prores` 的 WebCodecs 编码：**实测本机没有该编码器**（`isConfigSupported` 直接判 false）。

---

## 3. 建议的落地顺序（下一轮可以直接做）

1. **旋转台加"帧序列（PNG, RGBA）"格式**（路线 A 的应用内那一半，约 2 个文件 + 3 个文案键）：
   - `src/ui/turntable-video-dialog.ts`：格式下拉加一项；透明背景勾选（默认勾上，因为序列格式天然透明）；
   - `src/app/render.ts`：在旋转台循环里分流 —— `format === 'png-sequence'` 时不建 muxer/encoder，
     每帧 `encodePng` + 写文件，进度条复用现成机制；
2. 对话框里给一句"输出透明 MOV 需外部一步"的说明 + 现成的 ffmpeg 命令（可复制）；
3. 若用户更想要"应用内一键出 MOV"，再评估 C1（ffmpeg.wasm）—— 需要他确认可接受 +30 MB 体积。

---

## 4. 一句话总结

**透明帧抓得到（已有 PNG 通路），但"透明 MOV"被编码器卡死**：
本机 Chromium 对所有 codec 都拒绝 `alpha: 'keep'`，MOV/MP4 的 muxer 又不写 alpha。
所以正确做法是"**应用导出透明 PNG 序列 + 一步 ffmpeg 合成 ProRes 4444 MOV**"，
而不是继续在应用内找透明 MOV 的编码器。
