## 1. SH 波段通路：可用，但切换有成本

**通路完整**：`src/core/preferences.ts:87`（`view.bands` → `view.setBands`，validate 0..3）→ `src/app/editor.ts:2295-2310` → `src/splat/splat.ts:202`：

```ts
material.setDefine('SH_BANDS', `${Math.min(bands, (instance.resource as GSplatResource).shBands)}`);
```

**切换代价**：`material.update()` → `clearVariants()` → 销毁 ShaderInstance（不销毁 Shader）→ 下一次 draw 从 `ProgramLibrary` 取（键含 defines hash、**无淘汰**）⇒ **两套变体可以预热**，但每次切换仍要重建该 material 下所有 meshInstance 的 bindGroup / UniformBuffer ⇒ **只能在手势边界切，不能每帧切**。

**会漏掉的地方**：合并组的实体与 **overlay 材质**各自用 `resource.shBands`（`src/splat/splat-overlay.ts:227-234`）⇒ 降级只影响主 splat 材质。

**安全的地方**：直方图 / 范围选择 / 导出都按 `resource.shBands` 走（`src/data-processor/calc-histogram.ts:65`、`src/data-processor/select-by-range.ts:49`、`src/splat/splat-serialize.ts:659`）⇒ 临时降波段**不会**污染统计与导出成品。

**必须做的护栏**：`src/app/editor.ts:2412` 会把这个值写进文档（→ `src/app/doc.ts:206`），`src/core/preferences.ts:180-195` 会持久化 ⇒ 临时降级必须包 `preferences.suspend`，否则会被写进 `.ssproj` 与用户偏好（**"改完关掉再打开发现波段变 0 了"**）。

## 2. `alphaClipForward`：本 fork no-op（对调研文档的更正）

- **引擎默认值**（唯一写入点）：`.../scene/gsplat/gsplat-instance.js:101-113` = `alphaClip 0.3`、`alphaClipForward 1/255`、`minPixelSize 2`。
- 引擎侧 `alphaClipForward` 只被 `clipCorner` 使用（`.../wgsl/chunks/gsplat/vert/gsplatCommon.js:17,19`；GLSL 同），而 `clipCorner` **只在引擎自带的顶点入口里被调用**（`.../vert/gsplat.js:75`）。
- 本 fork 用**自家顶点入口**替换了它（`src/splat/splat.ts:186-187`、`:195-196`），自家入口只调 `initCorner`（`src/shaders/splat-shader.ts:182`、`src/shaders/splat-shader-wgsl.ts:219`）⇒ 引擎那段 `clipCorner` 根本不会被调用；片元侧引擎的 `alpha < alphaClipForward → discard`（`.../frag/gsplat.js:59`）同样不在本 fork 路径里（本 fork 片元只有 PICK_PASS 硬编码 `1.0/255.0`，见 `splat-shader.ts:626`、`splat-shader-wgsl.ts:658`）。
- 复核（本机实测）：`grep -rn "alphaClipForward\|alphaClip" src/` → **零命中**（`src/` 里从来没有任何代码读它）。
- ⇒ **结论**：`docs/perf/supersplat-3.3.0-对比调研.md` 第 3 节 P0-3 "改法 1" 里"把 `alphaClipForward` 提到 1/32"这条**作废**；要这个效果就得**先把 `clipCorner`（或片元 alpha 下限）自己加回自家 shader**，那属于改着色器而不是拧旋钮。

## 2.1 参数怎么设才对（一个容易踩的坑）

本 fork 强制 **`unified: false`**（`src/splat/splat.ts:290-293`；同样写法见 `group-renderer.ts:511`、`merge-model.ts:51`、`compare-scene.ts:228`）⇒ 走的是经典 `GSplatInstance`。因此：

| 写法 | 是否有效 |
| --- | --- |
| `splat.entity.gsplat.instance.material.setParameter('minPixelSize', v)` | ✅ **正确**（`GSplatInstance.update()` 只写 `numSplats`，不会覆盖它：`gsplat-instance.js:130-141`） |
| `scene.app.scene.gsplat.minPixelSize = v`（= `GSplatParams`） | ❌ **无效**：`GSplatParams` 只被 **unified** 通路消费（`gsplat-manager.js:118-122` → 各 unified renderer 的 `frameUpdate`），找不到任何写进经典 `GSplatInstance.material` 的通路 |
| 给 `instance.material` 赋新材质 | ⚠️ 会把 `alphaClipForward` 强制写回 `1/255`（`gsplat-instance.js:87-97`） |
| 参数推送惯例 | `material.setParameter(...)` + `material.update()`（`src/splat/splat.ts:202-227`）；**合并组是第二份 material，要一起改**（`src/splat/group-renderer.ts:556-573`） |

> 引擎源码读哪一份：`rollup.config.mjs:23` 把 `playcanvas` alias 到 `node_modules/playcanvas/build/playcanvas/src/index.js` ⇒ **运行时真正执行的是 `build/playcanvas/src/**`**，查引擎行为时看这里，不要看 `playcanvas.mjs`。

## 3. `minPixelSize`：可用（两条后端都生效）

- 它是"屏幕尺寸下限剔除"：GLSL 走引擎 chunk `.../glsl/chunks/gsplat/vert/gsplatCorner.js:3`（声明）`:63`（`if (max(l1, l2) < minPixelSize)`）；WGSL 走 fork 自写 chunk `src/shaders/splat-shader-wgsl.ts:831`、`:896`（`if (max(l1, l2) < uniform.minPixelSize) return false;`）⇒ **提高它 = 直接在顶点阶段丢掉小高斯**，是**真正减少顶点/填充量**的旋钮，与 SH 波段互补（一个减顶点着色成本，一个减被着色的高斯数）。

## 5. `sorter.setMapping` 抽稀：可达，但很贵

- 可达且已在用：`src/splat/splat.ts:604-625`（`this.entity.gsplat.instance.sorter?.setMapping(mapping)`）；引擎实现 `.../scene/gsplat/gsplat-sorter.js:78-99`。
- **稀疏 mapping 的形态**：`Uint32Array`，长度 = 想保留/绘制的高斯数，值是**原始 splat 索引**；worker 端用 `order[i] = mapping[order[i]]` 还原原始 id（`.../gsplat/gsplat-sort-worker.js:138-142`）。生效链路：worker 返回 `count` → `material.setParameter('numSplats', count)`（`gsplat-instance.js:130-135`）→ 引擎 chunk 按 `source.order >= numSplats` 裁剪（`.../vert/gsplatSource.js:7,15-24`）。
- 代价：① `mapping.buffer` 被 **transfer** 掉 ⇒ 每次必须新建（现有调用点就是这么做的）；② 同时重建 worker 端 centers，**4 B + 12 B / 项** ⇒ 20M 全量 ≈ **320 MB**，4:1 抽稀仍需 ≈ **80 MB** 传输/次 ⇒ **只能"运动开始/结束各一次"，绝不能每帧**。
- **必须先合并**删除过滤用的 mapping（同一个方法里构建：`splat.ts:610-618`，条件 `this.numSplats !== state.length && !this._showDeleted`），否则恢复时 `setMapping(null)` 会让**已删除的点复现**（`splat.ts:1335-1342` 的 `set showDeleted` 就靠它刷新）。
- ⚠️ 抽稀还会**动 pick/depth 语义**：`splat.index` 来自 order 映射（`src/shaders/splat-shader-wgsl.ts:314`、`:305-316`），降级期间未绘制的高斯无法被拾取。

## 7. 本机基线实测：合成 20M（WebGPU，4 秒连续旋转）

> ⚠️ **本节的数字已作废（2026-09-21 更正）**，保留在此仅作记录。原因有两个，都已查清并修掉：
> 1. **探针把相机搞成了 NaN**：`cam.setAzimElev(cam.azim + 1.2, cam.elev, 0)` 里的 `cam.elev`
>    在本 fork 的 Camera 上**不存在**（只有 `elevation`）⇒ 俯仰角 NaN ⇒ 相机矩阵 NaN ⇒ 模型并没有被正常绘制
>    （实测：运动检测 0/60 帧、控制台 948 条 NaN/秒）。
> 2. **夹具是亚像素的**：核心高斯 0.006–0.02 世界单位，在取景距离下小于引擎的 2 px 尺寸剔除阈值 ⇒
>    20M 点几乎全被丢掉，`litPercent` 只有 **2.1%**（"快"是因为屏幕上没东西）。
>
> 更正后的实测、旋钮量化与 A/B 结果见 **`docs/perf/交互期降级-实现与实测.md`**。
> 下面这张表里的"旋转"一列都是在 NaN 相机上量的，**不要引用**。

| --- | --- | --- |
| 帧数 | 120 | 232 |
| p50 | 16.7 ms | **16.6 ms** |
| p95 | 18.1 ms | **21.3 ms** |

**"确实在画满 20M"的证据**（不然上面的帧时间没有意义）：`meshInstance.instancingCount = 156250`（= 20,000,000 / 128，与交接包记录的 156250 完全一致）、`numSplats = 20000000`、`vram.tex ≈ 1.997 GB`、`visible = true`。

**为什么这还不够**：交接包记录的真实 20M 在**原机器**上是 `median 16.7 / p95 29.6 / max 462.8 / >33ms 5 帧`；本机合成夹具是 `p95 21.3 / max 163.8 / >33ms 1 帧`。**夹具没有复现"不流畅"**，三个可能原因（未定论）：

1. 本机 GPU 比原机器强；
2. 合成夹具的高斯**偏小**（核心 scale 0.006–0.02 世界单位，屏幕上多为亚像素），填充/overdraw 远小于真实扫描件的表面级高斯；
3. 视角/取景不同（真实件密集区在 153 半径内、被噪声撑爆 AABB，取景后屏幕上更"满"）。

⇒ **P0-3 的收益（预期"旋转帧 GPU 时间降 30–60%"）在当前夹具上量不出来**。要能量出来，需要三选一：
**(a)** 把真实扫描件拷过来（最可信）；**(b)** 给合成夹具加"大高斯"档（把核心 scale 提到 0.5–2.0 世界单位，专门加大填充成本）；**(c)** 换口径，只量 GPU 侧（引擎 timestamp query：本机 `app.stats.gpu` 是空对象，`graphicsDevice.gpuProfiler` 存在但需要自己挂 `gpu:report` 消费）。

## 8. 顺带发现：20M 上量帧时间时会刷 6 条 `translate(NaN, NaN)`

- 现象：在合成 20M 上跑 `perf-probe.cjs`（导入 → 取景 → 旋转 4 秒）时，控制台**每次都是 6 条** `<g> attribute transform: Expected number, "translate(NaN, NaN)"`；换成 2000 点小夹具则 **0 条**。
- 6 条 = 视图立方体六个面各一条 ⇒ 指向 `src/ui/view-cube.ts:128-142` 的 `transform(shapes.px/nx/py/ny/pz/nz, vecx.x, …)`（内部就是 `translate(${x*40}, ${y*40})`）；也就是某一次 `update(cameraMatrix)` 拿到不可逆/含 NaN 的相机矩阵。
- **但触发条件还没定论（如实）**：同一个 20M 夹具上，只做"导入 + 取景 + 等 6 秒"那次跑（`_tmp/nan-diag.cjs`）**0 条错误**、SVG 里也没有 NaN 残留，`framingRadius = 1691.07`（有限）；只有**带旋转**的那两次跑出现 6 条。⇒ 更像是"旋转（或与取景 tween 叠加）期间某一帧的相机矩阵退化"，**不是导入本身**。
- 换机前修的是**另一条路径**（`src/ui/bound-dimensions-overlay.ts:181-190` 的标签，而且它写的是 `<text>` 不是 `<g>`），所以交接包记的"已修"没错，只是**同款症状还有第二处**。
- 归属：控制台噪音（+ 视图立方体某一帧乱掉，下一帧恢复），**不影响渲染结果**。修法很小（写 `transform` 前判 `Number.isFinite`，非有限就跳过这一次写），建议与下一轮一起做；要做"根治"就得先复现定位到具体那一帧。
