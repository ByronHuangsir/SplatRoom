## 逐条结论

### ①表示/隐藏 Splats 后，已删除的点全部又出现了 —— 已定位，已修
- 右侧工具栏那个按钮的事件是 `camera.toggleOverlay`（`src/ui/right-toolbar.ts:164`），它切的是
  **点覆盖层 `SplatOverlay`**（`enabled` 要求 `camera.mode === 'centers'`，而
  `src/core/preferences.ts:97` 的默认值就是 `centers`，所以这个按钮人人都会碰到）。
- `src/splat/splat-overlay.ts` 在 **WebGPU** 上是"恒等序纹理 + 画 `splat.numSplats` 个"，
  而 `splat.numSplats` = 行数 − 已删除数；着色器里只判了锁定位（bit 2），注释写着
  "deleted splats are already excluded from order texture" —— 那只在 WebGL2 成立
  （引擎的 order texture 是排序后的可见集合）。**于是 WebGPU 下前 N 行照画，删除位无人过问。**
- 修法：`src/shaders/splat-overlay-shader.ts` 自己判 bit 4（`overlayShowDeleted` 可放开），
  `src/splat/splat-overlay.ts` 在 WebGPU 下改成画**全部行**（`splat.splatData.numSplats`）并每帧
  下发 `overlayShowDeleted`。
- 验证：`window.__SPLATROOM_VIEWER_STREAM__` 无关；用 20M 模型 → 删一批点 → 切 overlay →
  数"屏幕内点数"应与"未删除点数"一致（原实现会多画）。

### ②底部"高斯点数据"展开没有任何数据 —— 已定位，已修（子代理在改）
- 控制台每次都有：`CommandQueue task failed TypeError: e.updateBegin is not a function`。
- 根因：`src/data-processor/calc-histogram.ts:241-257` 的 `clearRT()` 与
  `src/data-processor/draw-points.ts:32-70` 的 `drawPointsWithShader()` 用了 **WebGL 专用**
  `updateBegin()/updateEnd()`（`WebgpuGraphicsDevice` 没有这两个方法），
  且 `src/shaders/histogram-shaders.ts:101` 的 bin 顶点着色器赋值 `gl_PointSize`
  （WebGPU 转 WGSL 会丢入口点 → 非法 pipeline）。
- 直方图 pass1/pass2 用的是 `drawQuadWithShader`（后端无关）所以没事，只有 pass3（bin 累加）炸。
- 结果：直方图每次 `run()` 都抛异常 → 面板里"计数/选中数"与直方图**全空**（属性名列表还在，
  所以用户看到的是"展开了但没有任何数据"）。

### ③选择范围只能收缩、无法扩展 —— 已量化（根因=深度滑块的"有用行程是一根针"），修法待落
- **能扩展**：先 40–60% 矩形 → 选中 19,997,733；再用更大矩形 `add` → 19,999,986（`expanded: true`）。
- **两个轴都能改**：左右 40–60 把全屏选中从 19,282,378 收到 **14,347,710** ✔。
- **问题在深度轴的"行程分布"**（20M 夹具实测，全屏框选后用 `selection.setDepthRange` 逐档推）：

  | 深度范围 | 选中点数 |
  |---|---|
  | 0–100（默认整段） | 19,282,378 |
  | 10–90 | 17,956,371 |
  | 25–75 | 16,468,657 |
  | 40–60 | 13,930,757 |
  | 48–52 | 2,644,133 |
  | 49–51 | 1,332,551 |
  | 50–50.5 | **358,006** |

  拖 0→40 只掉 28%，而 **48→50 就从 264 万掉到 36 万**：密集区挤在深度 ≈50 的一根针上，
  滑块绝大部分行程"没反应"，靠近针尖时一步就是几百万点 —— 用户体感就是"拉几次没反应 / 只能收缩"。
  这是**范围按 AABB（被 18 km 噪声点撑爆）线性映射**的必然结果（`poseExtent`/`rangeDistances`）。
- 修法方向（等 P0-1 落地后再动 `editor.ts`/`selection-range.ts`，避免与其 Worker 改造冲突）：
  深度范围改用**裁剪分位数**（与 `framingRadius()` 同一套 1%~99% 思路）或对 `tailMap` 做非线性压缩，
  让密集区在滑块上占到有意义的行程；左右/上下不动。
- 顺带修掉（本轮已提交 `72a1085`）：`src/ui/bound-dimensions-overlay.ts` 在投影退化时会把
  `translate(NaN, NaN)` 写进 SVG（控制台每次刷
  `<g> attribute transform: Expected number, "translate(NaN, NaN)"`）——现在改成 `visibility: hidden`。
- 仍需用户确认：他说的"选择范围调整"用的是**深度浮条**（`#selection-range-bar`）还是别处、
  当时是 `centers` 还是 **`rings`（环）**模式 —— 环模式下 `rangeMask()` 直接把拾取掩码原样返回、
  **滑块完全不参与**，那是另一种明确的行为。

### ④"框显所选"只显示一小块 —— 已定位，已修
实测四种状态（20M）：

| 状态 | 相机到密集中心 | 密集半径 | 比值 | 屏内点数 |
|---|---|---|---|---|
| 导入后 | 16115 | 153.2 | ×105 | 100% |
| 框显所选（无选中） | 8297 | 153.2 | ×54 | 100% |
| 重置相机 | 13629 | 153.2 | ×89 | 100% |
| 框显所选（全选中） | 8297 | 153.2 | ×54 | 100% |

- 根因：`Splat.focalPoint()` 是对的（密集中心），但**半径用的是
  `worldBound.halfExtents.length()` = AABB 半对角线**（本夹具 8297~16115），被远处噪声点撑爆
  （`src/camera/camera.ts` 的 `getSplatInfo`、`src/app/editor.ts` 的 `camera.focus` 处理器）。
  相机因此落在 8~16 km 外，屏幕上只剩一个点。
- 修法：新增 `Splat.framingRadius()` = **裁剪包围盒**半对角线（按轴取 1%~99% 分位、抽样 ≤20 万点、
  ×1.1 余量），三处取景都用它。实测 20M：取景半径 **301.7**（AABB 8297.4），框显所选后
  相机到密集中心 301.67（修复前 8297）、比值 1.0。
  为什么不用 `denseRadius()`（不透明度×尺度的加权 3σ）：它会把薄墙/稀疏结构也裁掉，
  实测直接让 `verify-mask-vs-rect` / `verify-equirect-export` 两套回归的取景前提失效；
  裁剪分位数只丢极值、不加权，正常模型上与 AABB 同量级（这两套回归改用裁剪包围盒后恢复 failed=0）。

### ⑤"重置相机"要回到密集区斜上方 15° —— 已定位，已修
- 原实现：`setFocalPoint(0,0,0)` + `setAzimElev(0,0)` + `setDistance(initialZoom)`
  → 实测相机停在离模型 13629 处（模型密集区 153），什么也看不到。
- 修法（`src/app/editor.ts` 的 `camera.reset` 分支）：密集中心 + `framingRadius()` +
  `setAzimElev(0, -15)`（`calcForwardVec` 的 `y = sin(-elev) > 0` ⇒ 相机在上方 15°、俯视）。
  没有模型时保持原来的默认视角。

### ⑥2000 万点不如浏览器版 SuperSplat 3.3.0 流畅 —— 已量到热点，方案调研中
- 已量到的本机热点（20M）：
  - `select.rect` 一次 **1275ms**（用户框选时的主要卡顿来源）
  - `updateState(deleted)` 179ms（重建 20M 的排序映射）
  - `Splat.focalPoint()` 是**整点遍历 + 每点 2 次 `Math.exp`**（20M ⇒ 4000 万次 exp，秒级），
    每次"框显所选"都跑一遍；而同一个文件里的 `denseRadius()` 对 >50 万点**会抽样**
    —— `focalPoint()` 应该同样抽样（或缓存）。
  - 轨道旋转时 max 462.8ms / 5 帧 >33ms 的抖动来源待定（排序 worker / GC / 包围盒补算）。
- 浏览器版对比调研：见 `docs/perf/supersplat-3.3.0-对比调研.md`（含上游 v3.3.0 源码出处与 P0/P1/P2 差异清单、
  量测方案与判定阈值）。核心结论：上游 3.3.0（playcanvas 2.22.1）已自带 **GPU 投影 + 紧凑化 + GPU 基数排序
  + indirect draw**，官方博客 20M 一档 WebGL2 44.9ms(22fps) / WebGPU 10.2ms(98fps) ——
  本机 WebGPU 架构**等价于那一列 WebGL2**（worker CPU 排序 + 每高斯展开 quad），
  所以"换 WebGPU 后端"本身不加速，加速来自把投影/剔除/排序搬进 compute（P0-3）。
  最值得先做的三条：P0-1 框选改 GPU/Worker（1275ms → 目标 ≤300ms）、
  P0-2 停止每帧强制全量 worker 排序、P0-3 交互期降级。

## P0-2 实施结果（2026-09-20，20M / WebGPU 实测）

**第一版改错了地方**：只在"我们自己的排序派发"（`splat.ts` 的 1e-12 检测路径）上做限流 ——
实测**完全无效**（4 秒旋转期间仍 postMessage **181 次 = 45.1 次/秒**，最差帧 489.6 ms）。
原因查清了：真正把 worker 喂饱的是**引擎**那条路 ——
`GSplatInstance.update()` 每帧无条件调 `sorter.setCamera()`（`gsplat-instance.js:123-126`，引擎门限 1e-6
≈"动一点就发"），worker 收到后按自己的 1e-3 门限（`gsplat-sort-worker.js:43-46`）决定是否排序，
旋转时每帧变化远大于 1e-3 ⇒ **只要相机在动，worker 就一直在排**（20M 一次约 0.4 s ⇒ ~2.5 次/秒），
每次排序完成引擎还要做一次 ~80 MB 主线程上传 ⇒ 那就是 489 ms 卡帧的来源。
（另：本仓库 vendored 的 `gsplat-sorter.js` 里**没有** `_sortInFlight` 合并字段 ——
`splat.ts` 里读它/设它的那段"合并"注释与实际引擎不匹配，等于没有合并。）

**第二版（有效）**：在 `sorter.setCamera` 上装闸门（`Splat.ensureSorterGate`，幂等）——
最快每 `SORT_MIN_INTERVAL_MS = 800 ms` 放行一次（选 800 是因为 20M 一次排序约 0.4 s，
间隔要大于排序时长 worker 才有机会空闲），停手 `SORT_SETTLE_MS = 200 ms` 后补一帧；
我们自己的检测路径仍保留（间隔到点时主动派一次带 `forceUpdate` 的排序，绕开 worker 的 1e-3 门限）。

| 量（20M / WebGPU / 4 秒连续旋转，同一进程同一夹具） | 改前 | 改后 |
|---|---|---|
| 旋转期间排序消息数 | 181（45.1/秒） | **17（4.2/秒）** |
| 停手后的补帧消息数 | 40 | **3** |
| 最差帧 | 489.6 ms | **343.7 ms** |
| >33 ms 的帧数 | 6 | 5 |
| median / p95 帧 | 16.6 / 28.6 ms | 16.6 / 29.0 ms |

⇒ 消息速率降 10 倍、最差帧降 30%；但**>33 ms 的卡帧数几乎没变**：
剩下的抖动是"每次排序完成引擎要做的那次 80 MB 上传"的固有成本（20M 下约 1~2.5 次/秒），
想再降只能动架构（上游 SuperSplat 3.3.0 的做法：**运动帧完全不排序**，或把排序搬到 GPU）。
复现：`node _tmp/sortrate.cjs "http://localhost:3621/?gpu=webgpu" test-20m.ply 4`
（探针包一层 `worker.postMessage` 数派发、采样帧间隔、检查停手补帧）。

回归：**37 套 TOTAL FAILED: 0**、`npm run check` 退出码 0（排序影响画面顺序，所以整套都跑过）。
**双后端**：webgl2 侧再跑一遍全量 **36 套 TOTAL FAILED: 0** ✔；但用 `docs/probes/sortrate.cjs`
在 webgl2 上量闸门时观测到 **0 次 worker 消息**，进一步诊断（同一探针加了诊断字段）：
```json
{"hasSorter": true, "hasWorker": true, "hasCenters": true, "sorterHasGate": true,
 "azimBefore": 0, "azimAfter": 216.0, "azimMoved": true,
 "sortPostsDuringOrbit": 0, "sortPostsAfterSettle": 0, "manualCall": {"posted": 0, "threw": null}}
```
即：闸门**确实装上了**（说明 `onPreRender` 里那段至少执行过一次）、相机确实转了 216°、
手动调 `splat.onPreRender()` 也**不报错**，但 2~3 秒旋转期间**一条消息都没有** —— 而我们自己那条
派发路径本来应该每 800 ms 主动派一次。最可能的解释是 **WebGL2 下这份 splat 的排序不由这段代码负责**
（`hiddenByGroup` 提前 return —— 注释里提到 group-renderer 激活时由 `group-renderer.ts` 自己 `sort()`；
或 WebGL2 的资源走另一条实例化路径）。⇒ **闸门在 webgl2 上"无结论"**（不是失败），待用
`dist/test-model.ply` 之外的中等夹具 + 直接给 `dispatchSort` 打点来确认；语义侧不受影响（套件全绿）。

把"框选/套索/多边形/2D 笔刷"的 2000 万点投影从主线程搬进 Worker（新文件 `src/splat/selection-core.ts`

②`applySelectionMask` 分块让出宏任务。

**同进程对照实测（同一夹具、同一相机、状态哈希相同 `3395733176` / 选中 16,765,227 ⇒ 逐位等价）**：

| 模式 | e2e | **主线程最长阻塞** | longtaskMax |
|---|---|---|---|
| legacy/b（改前代码路径） | 1067.9 ms | **1068.1 ms** | 895 ms |
| worker/b（改后） | 987.5 ms | **188.4 ms** | 0 |

相位表（改后，worker）：`worker.begin 40.2` + `worker.select 766.3`（**在 worker 线程**）+ `applyMasks ~244`（主线程）
⇒ **主线程阻塞降 ~82%**（1068 → 188 ms），但**未达 ≤150 ms 的验收线**，端到端 ~1000 ms 也未达 ≤600 ms
（单 worker 的 20M 投影本身 766 ms 就是地板）。

**结论口径**：这是一次**实测有效但未达标**的优化 —— 要不要落地需要用户拍板：
（a）按现在这样收（阻塞降 82%，保留 `window.__SPLATROOM_SELECT_WORKER__ = false` 回退开关）；
（b）继续做 K 路并行 worker（按全局索引切片 + 直方图/掩码分段合并，采样集 `i % stride == 0` 在切片下逐点一致
⇒ 仍可逐位等价），目标端到端 ≤600 ms；
（c）不落地，保持现状（P0-1 只留补丁与数据）。
⚠️ 探针的 `blockStartAttrMs` 在部分 run 里仍为 0（legacy/a），所以**验收以"相位表之和 ≈ e2e"自洽的那几组为准**。
