# 交互期降级（P0-3 v1）—— 实现与实测

> 本轮把"运动期降质量、停手恢复"做出来了，并且是**先量后改**：先量化了每个候选旋钮，再挑真正有效的那个。
> 结论：**在 GPU 受限的 20M 上，旋转帧 p50 70.9 → 29.8 ms（−58%）**；而文档原来推荐的三个旋钮里，
> **SH 波段只值 −0.5%、`alphaClipForward` 是 no-op**，唯一有效的是**降渲染分辨率**。
> 同时查出并修掉了两个**测量层面的 bug**（见 §2、§3），它们此前让"旋转期"的结论建立在一个没有正常绘制的相机上。

## 1. 做了什么（代码）

| 文件 | 作用 |
| --- | --- |
| `src/core/camera-motion.ts`（新） | 相机运动检测：位姿对比 + 指针按下，`settleMs = 200`。位姿对比是主信号——`camera.userDragging` 漏掉自动旋转、时间轴 tween、`setPose` |
| `src/core/gpu-frame-timing.ts`（新） | GPU 每帧耗时：包装引擎 `gpuProfiler.report` 按 `renderVersion` 归属到帧，并按动/静分类统计；`settledSpanPeak` 是"最近若干静止帧的峰值" |
| `src/core/motion-quality.ts`（新） | 纯策略状态机（不引引擎、可纯 node 单测）：`autoEngageMs = 60`、预算 33 ms、步进限频 300 ms、阶梯 = 渲染缩放 0.7 / 0.5 |
| `src/scene/scene.ts` | 每帧接线：运动状态 → GPU 标签 → 策略 → 幂等施加 `camera.targetSizeOverride` + `rebuildRenderTargets()`；降级期间保持渲染直到恢复那一帧真正发生 |
| `docs/verify/verify-motion-quality.cjs`（新，进批量） | 浏览器回归 7 项：静止全分辨率 / 运动降分辨率且渲染目标真的变小 / **`view.bands` 全程不变** / 停手精确恢复 / 逃生开关 |
| `docs/verify/verify-motion-quality-policy.mts`（新，纯 node） | 策略单测 13 项：arming 阈值、预算方向、限频、恢复、无 timestamp 回退、master switch、forceEngaged、reset |
| `docs/probes/gpu-frame-probe.cjs`（新） | GPU 每帧耗时探针 + **`litPercent` 可见性检查**（没有它，"快"可能只是没画东西） |

**逃生开关**：`window.__SPLATROOM_MOTION_QUALITY__ = false` 整体关闭（与 `__SPLATROOM_SELECT_WORKER__` 同一约定）。

**为什么不用 `view.setBands` 做降级**：那条路会把值写进偏好（localStorage）、`.ssproj`、设置面板与导出弹窗
（`P0-3-交互期降级-前置侦察.md` §1/§5.1）。本实现的降级是**临时的渲染目标缩放**，**完全不碰 `view.bands`** ——
回归套件专门有一项断言这一点（实测 `view.bands 3 -> 3`）。

## 2. 先修掉的测量 bug ①：探针的旋转把相机搞成了 NaN

`docs/probes/sortrate.cjs`（上一轮遗留）与我的 `perf-probe.cjs` 用的是
`cam.setAzimElev(cam.azim + 1.2, cam.elev, 0)`。本 fork 的 Camera **只有 `elevation`，没有 `elev`**
（`src/camera/camera.ts:271` 是 `azim`、`:275` 是 `elevation`）⇒ 传进去 `undefined` ⇒
`elev = Math.max(minElev, Math.min(maxElev, undefined)) = NaN` ⇒ 相机矩阵整体 NaN。

实测对照（同一次运行，两个约定各转 1 秒）：

| | `cam.elev`（原探针写法） | `cam.elevation`（正确） |
| --- | --- | --- |
| 相机位姿是否有限 | **否（NaN）** | 是 |
| `elevation` 之后 | NaN | −15 |
| 运动检测看到几帧在动 | **0 / 60** | **60 / 60** |
| 控制台 NaN 报错 | **948 条/秒** | **0** |

⇒ 三件事因此被解释清楚：
1. 此前汇报的"20M 每次跑都刷 6 条 `translate(NaN, NaN)`"不是视图立方体的 bug，而是**探针的 NaN 相机**在驱动视图立方体（小夹具、正确旋转时 0 条）。
2. 用这两支探针量到的**旋转期数字全部作废**（模型当时并没有被正常绘制）——包括我上一轮报的"旋转 p95 21.3 ms"。
3. 排序**消息数**类结论（P0-2 的 45.1 → 4.2 次/秒）不受影响：引擎每帧无条件调 `sorter.setCamera`，闸门限的是它，与相机是否 NaN 无关。

已在 3 个文件里改为 `cam.elevation`（`sortrate.cjs`、`perf-probe.cjs`、`gpu-frame-probe.cjs`），
并在 `sortrate.cjs` 里留了注释说明这个坑。

## 3. 先修掉的测量 bug ②：合成夹具"20M 点"其实什么都没画

第一版合成夹具的核心高斯尺度 0.006–0.02 世界单位，在取景距离（`framingRadius` 1691）下**是亚像素**，
而着色器会把投影尺寸小于 `minPixelSize`（引擎默认 2 px）的高斯**直接剔除** ⇒ 20M 点里几乎全部被丢掉。

于是出现了一个"看起来很好"的假象：GPU 只有 **2.4 ms**、帧 p50 18 ms —— 因为屏幕上基本没东西。
给探针加 `litPercent`（沿用 `verify-large-model-ui.cjs` 的 `max(r,g,b) > 60` 口径）后一眼看穿：

| 夹具 | litPercent | GPU p50 | 帧 p50 |
| --- | --- | --- | --- |
| 旧（亚像素） | **2.1%** | 2.4 ms | 18 ms |
| 新（`--core-scale=1.6 --room-radius=360 --room-scale=2.4`） | **81%** | **70.0 ms** | 69.8 ms |

⇒ `docs/verify/gen-synth-large-splat.cjs` 增加了尺寸/房间半径旋钮（默认值保持原比例），
且**任何性能测量都必须带 `litPercent`**。

## 4. 旋钮量化（20M fill 夹具，静止强制帧，同一进程）

| 旋钮 | frame p50 | GPU p50 | Δ |
| --- | --- | --- | --- |
| 基线（bands 3 / minPixelSize 2 / 全分辨率） | 69.8 ms | 69.92 ms | — |
| **SH 波段 → 1** | 69.5 | 69.57 | **−0.5%** |
| **SH 波段 → 0** | 69.5 | 69.57 | **−0.5%** |
| minPixelSize → 4 | 69.9 | 70.01 | 0% |
| minPixelSize → 8 | 68.8 | 68.87 | −1.5% |
| minPixelSize → 16 | 58.6 | 58.75 | −16% |
| **渲染缩放 0.7**（`targetSizeOverride`） | **39.9** | 39.98 | **−43%** |
| **渲染缩放 0.5** | **25.4** | 25.43 | **−64%** |
| 渲染缩放 0.35 | 18.1 | 18.93 | −73% |
| 恢复全分辨率 | 69.9 | 69.92 | 0（画面 mean\|ΔRGB\| = **0**，逐像素精确恢复） |

**读法**：这个模型的 GPU 时间**与像素面积近似成正比**（填充/overdraw 主导），而不是被顶点/SH 主导
——所以"降波段"几乎没用，"降分辨率"才有效。顺带复核了两个文档结论：`alphaClipForward` 在本 fork 是 no-op（§2 已知），
"SH 波段是最便宜的降级"这条**在填充受限的场景下不成立**。

**另有一条走不通的路**：`config.camera.pixelScale` 不能当交互旋钮用。实测把它改成 0.5/0.35 时，
画布/设备分辨率跟着变（`targetSize 3658 → 1829/2560` 反复横跳），帧时间反而涨到 **242 / 472 ms**，
画面也整体变了（mean\|ΔRGB\| 148）。正确机制是 `camera.targetSizeOverride`（PiP 预览用的那个）。

## 6.5 "停手后补一帧干净排序"：为了验证它，又查出三个真问题（2026-09-21 第二轮）

目标里有一条硬要求：**停手后要强制补一帧干净排序**。原来的实现是"继承 P0-2 的 `_sortSettleAt` 启发式"，
**从未被验证过**。本轮给 `verify-motion-quality.cjs` 加了两项断言之后，它立刻失败了 —— 顺着查下去发现三件事：

**① 那个启发式确实会漏补帧。** `_sortSettleAt` 只在"被 800 ms 闸门挡下的帧"里才会武装
（`_sortSettleAt === 0` 时置位），而闸门放行时又会把它清零；于是"最后一次放行之后没有再被挡下"时，
停手就没有任何补帧。更隐蔽的一点：**闸门包的是 `sorter.setCamera`，它并不一定会真的给 worker 发消息**
（引擎 worker 自己还有 1e-3 门限）⇒ "闸门放行次数"也不能当作排序已刷新的证据。

**② 按需渲染 + 停手 = 那一帧永远不来。** 武装了 deadline 之后，真正执行补帧的那一帧需要有人请求渲染，
而"停手"那一刻正好是本应用想停止出帧的时刻 ⇒ 实测 deadline 一直挂着（`sortSettlePending` 永远为 true）。
**修法**：`Splat.forceSettleSort()`（显式武装，不依赖启发式）+ `Splat.sortSettlePending`（getter）+
`Scene` 在"运动 → 停手"跳变时武装它、**并在欠着补帧期间持续出帧**（带 1500 ms 上限，
避免 sorter 异常时无限出帧）。这是上游 SuperSplat `pendingResolve` 的对应物。

**③ 合成旋转不会请求渲染（这是一个测量陷阱）。** `cam.setAzimElev(...)` 是**程序化**改相机，
背后没有指针输入，因此**不会把场景标记为脏** ⇒ 应用几乎不出帧。实测：一次 1 秒的合成拖动之后
1.5 秒内 `Splat.onPreRender` 被调用 **0 次**（trace 长度 0），于是补帧分支根本没有帧可跑，
而探针却把"0 次派发"当成了失败原因。**所有合成旋转都必须自己 `scene.forceRender = true`**
（`gpu-frame-probe.cjs` / `perf-probe.cjs` / A/B 脚本一直是这么做的，`verify-motion-quality.cjs`
原来没有 ⇒ 已修，并在注释里写明了这个坑）。

**验证结果（小夹具，进批量）**：`verify-motion-quality.cjs` **9/9，`failed: 0`**，其中两项是本节新增：
- `the 800 ms sorter gate still limits dispatch opportunities during a 2.5 s drag` —— 2.5 秒拖动期间放行 **5** 次（界 1..6）
- `the settle sort is issued, not left pending` —— 停手后 `sortSettlePending` 归 **false**

（20M 上的 worker 消息级证据见 `_tmp/settle-20m.cjs`：该夹具上**停手 300 ms 后 `pending` 由 true 转 false**
（补帧被消费）✓。但同一支探针在这个夹具上数到的 `worker.postMessage` **始终是 0**，
即使补帧分支确实跑过 —— 说明该夹具上 `dispatchSort` 要么走了不走 worker 的分支，
要么 sorter 换过 worker 实例，**这一层没查清**；因此"补帧已派发"的证据以 `sortSettlePending` 由
true 转 false 为准，不以 worker 消息数为准。）

**本轮新增的一个已知边界（如实）**：`autoEngaged` 需要"一帧**真正在画模型**的静止帧"来测量
（`settledSpanPeak > 60 ms`）。按需渲染下，静止时应用几乎不出帧，所以：
**"载入后第一次拖动"通常不会被降级**，从第二次起才会（第一次拖动结束时的那一帧被补帧机制强制渲染
⇒ 它成为第一个静止样本）。`_tmp/ab-motion-quality.cjs` 里的 A/B 是显式先跑 2 秒"静止强制帧"
把策略武装起来再量的，所以那个 −58% 是"已武装"状态下的数字。要在真机上验证首拖体验，
需要用真实指针拖动（会正常请求渲染帧）。

## 6.6 用户报的"画面收缩到左下角、上部/右侧黑色"—— 是降级踩到了 1:1 的 final blit（2026-09-21 第三轮）

**用户原话**：「移动、缩放时画面会收缩到左下角，在上部、右部产生黑色空间，感官上很不好。」

**根因（我引入的）**：`src/shaders/blit-shader.ts` 的 final blit 是**逐 texel 1:1 拷贝** ——
`gl_FragColor = texelFetch(srcTexture, ivec2(gl_FragCoord.xy), 0)`。这条路径在"离屏主目标尺寸 == 画布尺寸"
时是正确的（在此之前永远成立：`pixelScale` 默认为 1、也没有 `targetSizeOverride`），
而**降级会把主目标缩小**（例如 896×537 vs 画布 1280×767）⇒ 画面按 1:1 落在**左下角**，
其余区域取到越界 texel（多数驱动 clamp 到边缘，看起来就是黑/拖边）—— 与用户描述的现象逐点吻合。

**改前/改后实测**（`_tmp/blit-diag.cjs`：全画布截图 → 统计亮像素的包围盒与占比；
同一进程、同一夹具，降级态 = `engaged=true`、主目标 896×537 / 画布 1280×767）：

| 量 | 旧 blit（1:1） | 新 blit（按比例） | 静止态（无降级，参照） |
| --- | --- | --- | --- |
| 亮像素占比 | **31.4%** | **64.5%** | 76.3% |
| 右侧黑边 | **25 px** | **0 px** | 0 px |
| 内容顶部到画布顶 | 0 px | 0 px | 0 px |
| **右上象限亮像素** | **40.2%** | **93.5%** | 92.7% |

**修法**：blit 增加 `uniform vec2 blitScale`（= 源尺寸 / 目标尺寸），
`ivec2(floor(gl_FragCoord.xy * blitScale))`；`Camera` 在 final pass 的 `vars` 里每帧下发它。
**`blitScale = (1,1)` 时与旧代码逐 texel 等价**（`gl_FragCoord.xy = (x+0.5, y+0.5)`，乘 1 再 floor 仍是 `x`），
所以正常渲染路径不受影响 —— 这一点由全量回归（双后端）与像素类套件共同保证。
顺带：`config.camera.pixelScale ≠ 1` 时原来也会踩同一个坑（现在一并修好）。

**新增的护栏**：`verify-motion-quality.cjs` 增加一项 —— 降级态下截全画布，
要求"内容右/上边距 ≤ 16 px 且亮像素 ≥ 静止态的 60%"。
实测：**边距 0/0 px、亮像素 57.7%（静止 67.4%）**；用旧 blit 时该项会因
"右 25 px" 与 "31.4% < 60%×76.3%" **两条同时失败** —— 也就是说这个回归以后不会再悄悄溜过去。

## 6.7 用户报的"快速旋转时背面内容跑到前面"—— 排序派发路径其实早就死了（2026-09-21 第四轮）

**用户原话**：「快速移动/旋转视角时，会出现排序错误——既背面的内容跑到前面遮挡住正常画面（这个比较严重，需要重点关注）。」

**根因（两层，都有实测）**

1. **自家派发路径彻底死掉。** `Splat.dispatchSort()` 用 `ws._sortInFlight` / `ws._pendingCamera` 做"同一时刻
   只有一次排序在飞"的合并，而这两个字段**在本机引擎（playcanvas 2.21.3）里根本不存在**
   （`grep -r _sortInFlight node_modules/playcanvas` 零命中）。第一次派发把 `ws._sortInFlight = true` 之后
   **再没有任何代码会清它** ⇒ 此后每次派发都走进"只记录、不发送"的分支。
   实测（`_tmp/admit-diag.cjs`，2000 点夹具、3 秒快转）：`dispatchSort` 被调用 **2** 次、
   `worker.postMessage` **0** 次、完成事件 **0** 次 ⇒ 顺序冻结在旧位姿上 ⇒ 背面盖住前面。
   （交接包 5.3 节记过"这个字段缺失、等于一直没有合并"，但没意识到它**会把整条路径锁死**。）
2. **闸门按固定 800 ms 放行**：即使路径没死，快转时 800 ms 内相机也能转过很大角度，顺序过期得离谱。

**修法**

- `dispatchSort` 不再碰引擎字段：用**自己的**在飞标记 `_sortPendingSince` + **自己的**待办位姿
  （`_sortPendingPos/_sortPendingDir`）。在飞时只记最新位姿；完成事件（`sorter.on('updated')`，引擎收到
  worker 回包时 fire）到达即补发；3 s 超时兜底；补发仍尊重最小间隔（避免"完成即发"自旋）。
- 闸门准入 `_sortAdmit()`：**不早于 200 ms + 没有排序在飞 + 自上次派发以来相机转过 >2.5°（或位移 > 模型半径 1%）**。
  顺序新鲜度绑在"动了多远"，worker 靠完成事件保证不被淹没。

**实测（同机同夹具同进程）**

| 量 | 改前 | 改后 |
| --- | --- | --- |
| 3 秒快转期间 worker 派发（2000 点夹具） | **0** | **30** |
| 同上排序完成事件 | 0 | **15** |
| 2.5 秒快转期间派发（套件内） | 0 | **16**（界 2..80） |
| 20M fill 上相邻两次派发间隔 | ——（无派发） | **54–172 ms** |

## 6.8 范围滑块"向外 = 扩边、向内 = 收芯"（用户批准后实现，2026-09-21 第五轮）

**根因回顾**（HANDOFF 第 26 条）：判定规则是"外窗之外丢掉；**core 与 outer 之间的带**不看形状直接选；

  core 一起收，视觉与以前一致。

## 6.9 排序残影的另一半：**顺序延迟补偿**（用户复报"快速旋转依然错位、短暂停留后消失"，第六轮）

**结论**：把派发给排序 worker 的相机位姿从"当下"改成"**落地时刻**"（按实测延迟 λ 沿当前速度外推），
20M fill 夹具上"顺序离正确深度顺序有多远"（`disp`，0 = 完全正确，0.333 = 与随机无异）：

| 场景 | 基线 disp（P50 / P95） | 补偿后（P50 / P95） | 变化 |
| --- | --- | --- | --- |
| 正常拖拽 125°/s（2°/帧） | 0.123 / 0.163 | **0.035 / 0.087** | **−71.5%** |
| 猛甩 375°/s（6°/帧） | 0.284 / 0.332 | **0.156 / 0.253** | **−45.1%** |
| 停手后（参考点） | 0.00046 | 0.00046 | 度量自检：确实能读出"正确" |
| 随机排序（上界） | 0.333 | 0.333 | — |

帧成本无变化（同一轮里 frame p50 31.6~32.3 ms、p95 71.5~73.1 ms），派发频率无变化（39 次/6 秒量级）。

### 怎么量出"顺序错位"

`docs/probes/sort-lag.cjs`：取 4000 个样本（固定种子），把它们**在生效排序表里的次序**与
**按当前相机算出的真实深度次序**各排一次，平均归一化秩差就是 `disp`。这比"数派发次数"直接得多 ——
派发次数只说明"顺序在刷新"，不说明"刷新出来的顺序对不对"。

**两个测量坑（都踩了，记在这里免得再踩）**：

1. **`sorter.centers` 读不到**：`GSplatSorter.init()` 把 centers 的 buffer **transfer** 给 worker 了，
   主线程那份已经 detached（`length === 0`）⇒ 拿它算深度全是 `NaN` ⇒ `disp` 恒在 0.19~0.33
   （看起来"顺序永远是错的"，包括停手之后）。正确做法：读 `splat.splatData` 的 x/y/z，
   用排序表里的**值**（就是 splatData 的原始下标，着色器本来就这么取值）定位中心。
2. **"派发方向 vs 落地时刻方向"的夹角不能当指标**：worker 会合并相机消息，配不上对
   （同一份代码配出来的 λ 在 150~380 ms 之间跳，差值全是被错误配对的样本污染的）。

### 实现（`src/splat/splat.ts`）

- **λ**：`postSort` 时刻 → `sorter.on('updated')` 的滑动平均（α = 0.4，夹在 [0, 600] ms）。
  实测 20M fill：**λ ≈ 155~163 ms**（未修闸门 bug 时曾测到 372 ms，见下）。
- **速度估计用 120 ms 时间窗**内的位姿差，而不是"上一帧 → 这一帧"。原因很实在：外推跨度 λ 有几百毫秒，
  单帧差分估出来的速度抖 ±30%，乘上 370 ms 就是 ±30° 的角度误差 —— 实测单帧差分版只能把 `disp`
  从 0.262 降到 **0.150**，换成窗口版降到 **0.087**。角速度存成**旋转矢量**（轴 × 角速度）：
  来回蹭（换向）时两个相反的矢量会互相抵消 ⇒ 速度估计趋 0 ⇒ 自动退回不补偿（而不是外推到错误的方向）。
- **派发时**：方向按 Rodrigues 外推 `|rotRate| · λ`，位置沿窗口线速度外推；外推角 < 0.5°（或位移
  小于模型半径的 0.2%）时**原样送当前位姿** ⇒ 静止/微动时行为逐字节不变（回归面最小）。
- **停手补帧不外推**（`predict = false`）：静止帧要的是精确顺序，而速度估计在停手 200 ms 后仍有残余。
- **逃生开关**：`window.__SPLATROOM_SORT_PREDICT__ = false`。
- 护栏：`docs/verify/verify-sort-predict.cjs`（7 项，小夹具即可）—— 断言"派发位姿 == 解析上的
  Rodrigues 外推"（误差 < 0.05°）、外推方向与转动方向同向（`cross(cur, posted)·rotRate > 0`）、
  仍是单位向量、λ 有界、速度无 NaN、停手帧不外推、逃生开关生效。

### 同一轮顺带查出并修掉三个"闸门把自己锁死 / 空转"的问题

1. **引擎那条派发路不带 `forceUpdate` ⇒ 闸门被锁 3 秒**。`sorter.setCamera` 在引擎 2.21.3 里只做一件事：
   把相机 `postMessage` 给 worker，**不带 `forceUpdate`**。worker 收到后按自己的 1e-3 门限判断，
   认为"没动够"就**直接 `return`**（`gsplat-sort-worker.js:44`）—— **不回包**。而我们据此把
   "有排序在飞"标上 ⇒ 完成事件永远不来 ⇒ 在 3 s 超时之前**一次都派发不出去**。
   实测（`verify-sort-predict.cjs` 抓到）：小夹具快转 1.5 s，`worker.postMessage` **0 次**。
   现在两条路都走自家 `postSort`（同一个消息 + `forceUpdate: true`），每次派发必有回包；
   这一修也把上面 20M 的 λ 从 **372 ms** 降回 **155 ms**（此前每次都白等一个超时窗口）。
2. **"相机停了"这一帧可能永远不来**。本应用按需渲染，而"停了"只能由**下一帧**观察到；用户松手后
   不再有指针事件 ⇒ 没有自然帧 ⇒ `_wasMoving && !moving` 那段永不执行 ⇒ 既不补"停手后的干净排序"，
   也没有帧去消费已完成排序的结果。大模型上这条被"降级期间一直出帧到恢复"掩盖了，**不降级时才暴露**
   （实测 2000 点夹具：快转结束后 1.2 s 内 `postMessage` **0** 次）。现在每次手势挂一个一次性定时器
   （静默点之后要一帧；若那一帧发现还在动就再挂一次），100 ms 级代价、只在手势期间存在。
3. **排序在飞也必须出帧**。排序结果是**异步**回来的：最后一次派发之后若不再出帧，那份结果永远不会被
   `applyPendingSorted()` 消费（画面停在旧顺序）。`scene.ts` 的"要不要继续出帧"加了 `sortInFlight`
   一条（`Splat.sortInFlight`，带 3 s 超时兜底，不会无限出帧）。

### 残留（诚实记录）

375°/s ≈ 1 秒转一整圈，比真实拖拽猛得多；这个速度下 `disp` 仍有 **0.156**、p95 **0.253**，
即最坏时刻仍然明显错序。剩下的是 λ 本身的抖动（同一段手势里 300~430 ms）与"派发 → 落地"之间
相机速度的变化 —— **靠外推无法再消掉**。再往下只有两条路：(A) 运动期改成与顺序无关的渲染
（不透明 + 深度测试 + 自己实现的 alpha 下限），(B) 把排序搬到 GPU 以缩短 λ。两者都在 §7 待办里。


## 6.10 用户报的"选区在移动/旋转视角时右上方出现虚影" —— 降级踩到体积形状的 `targetSize`（第六轮）

**结论**：这是**降级自己引入的**第二个"尺寸不一致"bug（第一个是 §6.6 的 1:1 final blit）。
修完之后，同一相机位姿下"全分辨率 vs 降级"的像素差（16×16 瓦片平均色差）里，
体积形状带来的额外差异从 **+135.0 降到 +10.8**（方块）/ **+53.1 降到 +10.0**（球体），
剩下的就是"分辨率下降本身"的正常差异（对照：没有选区形状时最差瓦片 5.8）。

**根因**：体积形状（`BoxShape` / `SphereShape`）的片元着色器用
`clip = gl_FragCoord / targetSize` 反推世界射线，再做体积内部的网格/棱线着色
（`src/shaders/box-shape-shader.ts:189-195`、`sphere-shape-shader.ts:135-141`）。
而那个 `targetSize` uniform 一直填的是**画布**尺寸（`device.width/height`）：
不缩放渲染目标时两者相等，所以从没暴露；交互期降级把主 render target 缩到 `camera.targetSizeOverride`
之后，射线就是按**错误的像素位置**还原的 —— 网格与棱线被画成一份错位的重影。
（y 方向还带着 WebGPU 的 `targetSize.y - gl_FragCoord.y` 翻转，所以偏移主要出现在画面上方，
与用户描述的"右上方虚影"一致。）

**修法**：两处都改成读**实际光栅化目标**的尺寸 —— `scene.camera.targetSize`（`camera.ts` 的 getter
已经包含 `targetSizeOverride`）。无 override 时它与 `device.width/height` 一致，所以是纯粹的
"修错"而不是"改行为"：

```ts
const size = this.scene.camera?.targetSize ?? { width: device.width, height: device.height };
device.scope.resolve('targetSize').setValue([size.width, size.height]);
```

**怎么量**（`docs/probes/shape-ghost.cjs`）：同一个相机位姿下抓两张画布像素 ——
静止（全分辨率）与"移动中"（走真实降级路径，`motionQuality.forceEngaged = true` + 一个
"出去再回来"的 0.05° 摆动：最后位姿完全相同，但最后一次位姿变化距抓图 < `settleMs` 所以 `moving` 为真），
按 16×16 瓦片比较平均色差；再和"没有选区形状"的对照相减。

| 场景 | 最差瓦片色差 | 平均 | >8 的瓦片数 |
| --- | --- | --- | --- |
| 对照（无形状） | 5.8 | — | — |
| 方块形状 · 修复前 | **140.8** | 15.63 | 58 |
| 方块形状 · 修复后 | **16.6** | 3.63 | 17 |
| 球体形状 · 修复前 | **58.9** | 9.99 | 79 |
| 球体形状 · 修复后 | **15.8** | 3.93 | 27 |

**教训（与 §6.6 同源）**：任何"把画布尺寸当渲染目标尺寸用"的地方，都会在降级时错位。
降级是一项**全局的尺寸改变**，所以每次给它加新通路都要搜一遍 `device.width/height` /
`scene.targetSize` / `canvas.clientWidth` 的用法。

## 6.11 "把排序搬到 GPU 能省多少"——上限实测（第七轮，只量不改）

用户问"把排序搬进 GPU 会产生什么后果"，先量收益上限再谈工程。探针 `docs/probes/sort-cost.cjs`
把现在的代价链**逐段拆开**（20M fill / WebGPU / 375°/s 拖拽 / 降级生效，同一次运行）：

| 环节 | 实测 |
| --- | --- |
| ① worker 全量排序（worker 自报 `sortTime`） | P50 **161.4 ms** |
| ② λ：派发 → 完成事件 | P50 **161.6 ms**，max 219.4 ms ⇒ **λ ≈ ①**（回包几乎没有额外延迟） |
| ③ 完成 → 被某一帧消费（`applyPendingSorted`） | P50 24.2 ms（≈ 等下一帧） |
| ④ upload 本身（主线程 memcpy + 提交） | P50 **4.1 ms**，max 10.7 ms |
| 排序频率 | 19 次 / 4 s ≈ **4.75 次/秒** |
| 4 秒内过主线程的索引数据 | **1.45 GB（362 MB/s）** |
| ≥1 MiB 的 GPU 缓冲分配 | **1 次 × 76.3 MiB / 19 次上传** ⇒ staging 池够用，**没有"每次排序新建 80 MB"** |
| 上传占主线程墙钟 | 84.3 / 4000 = **2.1%** |

**代价真正落在帧上的是 ④ 所在的那些帧**（124 帧里 18 帧含上传）：

| | 含上传的帧（18） | 不含上传的帧（106） | 全部 |
| --- | --- | --- | --- |
| 帧 P50 | **49.7 ms** | 28.7 ms | 30.5 ms |
| 帧 P95 | **82.6 ms** | 45.7 ms | 60.2 ms |

**反事实相位**（把 `uploadStream.upload` 变成 no-op：顺序会过期，但**画的还是同一批高斯** ——
`litPercent` 71.2% → 71.3%，所以帧时间是可比的口径）：

| | 含上传（基线） | 零上传（反事实） | 差 |
| --- | --- | --- | --- |
| 全部帧 P50 / P95 | 30.5 / 60.2 ms | 29.4 / **44.2 ms** | −1.1 / **−16.0 ms** |
| "本该上传"的那些帧 P50 / P95 | 49.7 / 82.6 ms | 29.5 / 42.4 ms | **−20.2 / −40.2 ms** |

**结论（上限口径）**：

1. **收益主要在尾部与顺序新鲜度，不在平均帧**：P50 只省 1.1 ms（只有 15% 的帧含上传），
   但 P95 省 **16 ms**、含上传的帧省 **20/40 ms**；同时主线程每秒 362 MB 的索引搬运归零。
2. **λ 才是顺序问题的根**：161 ms 的 worker 排序 ⇒ 125°/s 时顺序落后 ~20°、375°/s 时 ~60°。
   GPU 排序把这 161 ms 变成"几个 compute pass"（**预期**到单帧级 —— 未实测，20M 基数排序常见量级
   1–3 ms/趟），**顺带就不需要延迟补偿**了（那份代码可以留着，但 horizon→0）。
3. **净收益要打折**：GPU 排序自己也要吃 GPU 时间，而且它省掉的是"4.1 ms memcpy + 20 ms 帧惩罚"，
   不是"161 ms"（那 161 ms 本来就不在主线程上）。所以 **为了 P50 去搬 GPU 排序不值得**；
   值得的是"猛甩时顺序也不错"和"砍掉 p95 那 20~40 ms 的尾巴"。
4. **注意 ④ 的实测结构**：memcpy 只有 4.1 ms，但落在帧里就是 +20 ms ⇒ 大头不是 memcpy，
   而是 76 MiB `copyBufferToBuffer` + 提交串行化 + 缓存冲刷。这一点决定了"省内存带宽"类优化
   （例如换成 `orderBuffer.write` 直写）**不会**等于"省 20 ms"，要单独量。
5. 已有替代品的效果对照：延迟补偿让 disp 从 0.123 降到 **0.035**（125°/s）、从 0.284 降到 **0.156**
   （375°/s）；GPU 排序理论上能把两者都压到静止水平（**0.0005**），即"把猛甩那 0.156 也补上"。

⇒ 建议：把"GPU 排序"当成**体验打磨**（尾部 + 猛甩顺序）而不是性能优化；真要动，先做
**最小侵入版**（只把 worker 排序换成引擎已导出的 `ComputeRadixSort`，结果写进现有的 order storage
buffer，保留我们全部渲染/编辑/拾取代码，WebGL2 不动），而不要一上来就换 unified/hybrid
（数据模型要整体换、引擎 2.21.3 的 unified 还把 `SH_BANDS` 硬编码成 0）。

## 6.12 更长速度窗 + 双步外推：扫参结论（第八轮，2026-09-21）

用户要求"试更长的速度窗 + 双步外推"。做法：把外推拆成**两步**，窗口长度做成运行时可调
（`window.__SPLATROOM_SORT_TUNE__ = { windowMs, consumeWeight, extraMs }`，只给探针/套件用），
一次加载夹具扫多档（`docs/probes/sort-tune.cjs`，每档恒速段 9 s ⇒ n≈41~43）。

- **第一步** `_sortLatencyMs`：派发 → worker 回包（≈ worker 排序耗时）。
- **第二步** `_sortConsumeMs`：回包 → **某一帧真的把它上传并用于渲染**（按需渲染下总要等下一帧的
  `GSplatInstance.update()`）。只算第一步会系统性偏早一个帧长。

### 先纠正一个度量口径问题（很重要）

同一个配置、同一段旋转，`disp` 的数值取决于**在哪一刻采样**：

| 采样口径 | 含义 | 375°/s（旧版配置） | 125°/s |
| --- | --- | --- | --- |
| `timer`（每 200 ms 随机相位） | **典型帧**：含"一个周期末尾、新顺序还没到"的最差时刻 | **0.120 ~ 0.199** | 0.041 |
| `consume`（新顺序上线那一刻） | 每个周期里的**最优点** | 0.046 | 0.010 |
| `reply`（worker 回包那一刻） | 比 consume 略新 | 0.032 | 0.010 |

⇒ 同一配置在三个口径下能差 **4 倍**。历史头条数字（0.156 / 0.284）属于 `timer` 口径，
**跨文档比较必须同口径**。（第七轮我一度以为 consume 才是"屏幕真相"——不准确：consume 是每个
排序周期里最优点，`timer` 才是"用户大部分时间看到的那一帧"。）

### 扫参结果（20M fill / WebGPU / 降级生效 / predict 全开）

**375°/s（6°/帧）：**

| 配置 | horizon | timer P50 | timer P95 | consume P50 | 换向 timer P50 |
| --- | --- | --- | --- | --- | --- |
| predict OFF（参考） | — | 0.263 | 0.323 | 0.229 | 0.335 |
| 旧版：窗 120 / 不算第二步 | 157 ms | 0.120 | 0.265 | 0.046 | 0.296 |
| **双步：窗 120 / 权重 1** | 172 ms | 0.138 | **0.230** | 0.037 | **0.174** |
| 双步 + 固定 +15 ms | 206 ms | **0.099** | 0.223 | 0.038 | 0.191 |

**125°/s（2°/帧）：**

| 配置 | horizon | timer P50 | timer P95 | consume P50 | 换向 timer P50 |
| --- | --- | --- | --- | --- | --- |
| predict OFF | — | 0.126 | 0.151 | 0.078 | 0.092 |
| 旧版：窗 120 / 不算第二步 | 157 ms | 0.041 | 0.089 | 0.010 | 0.121 |
| **双步：窗 120 / 权重 1** | 180 ms | **0.030** | 0.076 | 0.009 | 0.073 |
| 双步 + 固定 +15 ms | 185 ms | **0.027** | **0.072** | 0.012 | **0.052** |

（长窗口 200/300 ms 也扫了：`consume` 口径 P50 0.047 / 0.073、换向 0.259 / 0.265（125°/s 侧 0.078），
即**恒速段不占优、换向明显更差**，见结论 1。）

### 结论

1. **更长的速度窗没有好处，换向时明确更差**：窗 200/300 ms 在恒速段与 120 ms 同量级，而换向 600 ms
   内 `timer` P50 从 0.174 涨到 **0.259 / 0.265**。原因：窗越长，速度估计在换向/变速时滞后越大；
   恒速段外推本来是线性的，长窗并不更准（只是更稳，而稳定性不是瓶颈）。⇒ **保持 120 ms**。
2. **双步外推是稳定的小胜**：换向段 **0.296 → 0.174（−41%）** @375°/s、**0.121 → 0.073（−40%）**
   @125°/s；P95 也降（0.265 → 0.230；0.089 → 0.076）；125°/s 的 P50 0.041 → 0.030。
   **375°/s 的 P50 在噪声内**（两次运行分别 0.199→0.138 与 0.120→0.138，符号不一致；
   单次 P50 的散布本身就有 ±0.08）。
3. **再加固定 +15 ms 不值得做默认**：它在 `timer` 口径上最好（375°/s 0.099、125°/s 0.027），
   但本质是"把 horizon 往一个排序周期中段推"，`reply/consume` 口径随之变差（刻意的过冲），
   375°/s 换向也不比双步更好（0.191 vs 0.174）。⇒ 留作可调项（`extraMs`），不设为默认。
4. **这一步买不到数量级**：双步把"每个周期起始的系统性偏差"补掉了，但典型帧的错位主要由
   **排序周期长度**决定（λ≈157 ms + 等待 ≈ 200 ms 一个周期）—— 想再降只有缩短 λ（GPU 排序，§6.11）。

**默认值**：窗 120 ms + 第二步权重 1 + 无额外常数（即上表加粗那一行）。护栏
`docs/verify/verify-sort-predict.cjs` 增到 **8 项**（新增"第二步延迟确实在采样并被折进 horizon"）。

## 6.13 运动期"不依赖顺序"的渲染（A 方案，第九轮，2026-09-21）—— **默认关闭**

> **状态：默认关闭**（`MotionOpaque.enabled = false`）。做出来并验证了机制与收益，但用户看过之后反馈
> **"这个看着太难受了"** ⇒ 不该由我替用户默认开启一个观感改变。现在只有显式打开才生效：
> `window.__SPLATROOM_MOTION_OPAQUE__ = true`（一行，不用重新打包），
> 默认行为回到 3.23.14 的"alpha 混合 + 双步外推补偿"。
> 想要这条收益仍在（猛甩时顺序也不错 + 砍掉运动期 80 MB 上传），但需要先解决观感：
> 见本节末尾"下一步可以怎么救"。

用户要求"试试运动期不依赖顺序的渲染"。做法：**运动帧干脆不要顺序** ——

- splat 材质切到 `BLEND_NONE` + `depthWrite = true`；
- 自写的片元着色器（`gsplatShaderPS`，GLSL + WGSL 两套）加 alpha 下限：低于它的片元 `discard`，
  其余按**不透明**写出（颜色不预乘、alpha 写 1；RT1 保持不变，所以选区/描边通路行为不变）；
- ⇒ 每个像素由**深度测试**决定谁可见 ⇒ 画面**与绘制顺序无关**；
- 运动期**不再派发排序**（可见性不靠顺序，排序纯浪费）；停手后补一帧精确排序，**并且不透明路径
  一直保持到那份排序真正上线**（否则切回半透明的一瞬间顺序还是旧的，会闪一下错序）。

开关（都不写偏好、不进 `.ssproj`、不影响导出）：
`window.__SPLATROOM_MOTION_OPAQUE__ = true`（打开，A/B 用）/ `= false`（强制关掉）、
`window.__SPLATROOM_MOTION_ALPHA_CLIP__`（alpha 下限，默认 0.5）。
为什么必须自己实现 alpha 下限：引擎的 `alphaClipForward` 在本 fork 是 **no-op**
（见 §2 —— 引擎拿它做 `clipCorner`，而我们替换了那个顶点入口）。

### 决定性判据：顺序无关性（同一位姿，把 order 换成乱序）

`docs/probes/motion-opaque.cjs`：同一相机位姿下比较"正确顺序"与"乱序（确定性 Fisher-Yates）"的画面
平均色差。另加 **all-zeros 顺序**对照（每个实例都读 0 号高斯）证明 order 确实被着色器读；
并做"连续两次抓图必须相同"的收敛检查（上传有一帧滞后，第一版就是被它坑出一堆假结论）。

| 夹具 | alpha 混合：乱序 vs 正确 | 不透明 + 深度：乱序 vs 正确 | all-zeros 对照 |
| --- | --- | --- | --- |
| **分层夹具 600k**（两面板，深度差大） | **36.37** | **0.00** | 113.73 |
| 分层夹具 200k（同上，套件用） | 48.76（套件内）/ 33.74（探针） | **0.00** | 114.62 |
| 20M fill | 4.68 | 0.07 ~ 1.88 | 53.94 |

⇒ 顺序无关性成立（分层夹具上从 36.37 掉到 0）。20M fill 夹具本身对顺序不敏感（overdraw 极大、
颜色相近 ⇒ alpha 混合下乱序也只差 4.68），**这类"顺序错位"要用有深度结构的夹具才测得出来** ——
为此新增 `docs/probes/gen-layered-splat.cjs`（两层平板，颜色区分，默认 600k）。

### 观感代价（20M fill，同一位姿：运动帧 vs 停手后的 alpha 混合帧）

| alpha 下限 | 平均色差（0..255） | 亮像素覆盖率 |
| --- | --- | --- |
| 0.37 | 12.75 | 64.4%（停手 71.2%） |
| **0.5（默认）** | 13.21 | 64.4% |
| 0.65 | 13.62 | 64.3% |

下限在 0.37~0.65 之间几乎无差别（因为足迹边缘 alpha ≈ 0.368 ⇒ 低于它等于"全留"），0.8 开始变差。

停手立刻恢复。这是**观感取舍**，需要用户拍板 —— 所以留了逃生开关。

### 护栏

`docs/verify/verify-motion-opaque.cjs`（进批量，两后端各 **9 项**）：
材质两向切换（不透明+深度写 ↔ alpha 混合）/ 运动期不派发排序（**开/关对照**，跳过起止过渡帧：
ON 0~1 次 vs OFF 7 次）/ 停手仍补一帧精确排序 / 顺序无关性 / 逃生开关 / alpha 下限覆盖 /
`view.bands` 全程不变。

**像素判据的边界（如实记）**：套件宿主里"alpha 基准是否对乱序敏感"本身不稳定 —— 同一份 200k 分层夹具，
独立探针稳定读到 33.74，套件里一次读到 48.76、另一次只有 0.05（上传/抓图的时序竞争，未定位）。
所以套件里这条断言是**有条件**的：先断言"度量有效"（基准确实在 alpha 混合路径上 + all-zeros 对照 > 5，
实测 94.8），基准敏感时才断言"不透明路径 ≤ 25%"，否则记为"本宿主不可测"并指向探针。
**权威口径是探针**（600k 分层 36.37 → 0；200k 分层 33.74 → 0；20M fill 4.68 → 0.07~1.88）。
WebGL2 上套件的像素判据完全不可用：order 是 R32U 纹理，`uploadStream.upload(array, texture)` 写不进去
（all-zeros 对照恒 0.00）。

### 下一步可以怎么救（如果还想拿这条收益）

用户反馈"看着太难受"的观感来源有三条，各自有对症的改法（都还没做）：

1. **硬边 + 时间走样**：每个存活片元都被写成全不透明 ⇒ 高斯变成硬边圆盘，运动时会"爬行/闪烁"。
   改法：把 alpha 测试做成**抖动式**（`alpha < clip * (0.75 + 0.5 * hash(screenPos))`），
   硬边变成随机噪点 —— 这是 1 spp 随机透明那套的常见做法，运动观感通常好很多。
2. **覆盖率掉了 6.8 个点**（71.2% → 64.4%）：相邻高斯的软边不再互相补，出现"孔洞"。
   改法：不透明路径下把足迹放大一点（顶点里把 corner offset ×1.2~1.4）让圆盘重叠起来。
3. **只在甩得很快时才切**（推荐）：观感代价只在"眼睛本来就抓不住细节"的时候付。用已经有的角速度
   估计做门限 —— 例如预测落后角 `|ω|·λ > 15°` 才进入不透明路径，慢速/中速拖动保持半透明
   （那里顺序误差本来就小，实测 125°/s 的 disp 只有 0.035）。这样"难受"的时刻大幅减少，
   而"背面跑到前面"这种最刺眼的时刻仍然被覆盖。

## 7. 已知风险 / 待办


1. **降级期间拾取坐标会不一致**：投影/拾取换算用 `scene.targetSize`（`src/app/editor.ts:1027` 等），
   降级时它变小了。实际影响面很小（相机拖动与选择手势不会同时发生），但"边转边框选"这种操作需要复核。
2. **PiP 预览也写 `targetSizeOverride`**（`camera.ts:1207/1214`）：本实现每帧幂等校验并重设，能抵抗互相覆盖，但两者叠加时的行为没有专项套件。
3. **`stepMs = 300`** 是因为我们的旋钮要重建渲染目标（不像上游改一个 uniform 可以 50 ms 一次）；档位切换那一帧会明显更慢。
4. **无 timestamp query 的适配器**上按模型规模回退（≥ 200 万点即降级），此时"降了但没测"——默认阶梯只降分辨率，代价可接受。
5. 上游那套更进一步的东西**没做**：紧凑化 + indirect draw（只画存活高斯）、贡献剔除、遮挡剔除、运动期完全不排序的 1 spp 随机透明。
   本轮的结论是：在填充受限的场景下，**先降分辨率**性价比最高；上面这些留给真正需要时再做（可行性见 `supersplat-3.3.0-代码可借鉴点.md`）。
6. **顺序补偿治不了"λ 太大"这件事本身**（§6.9 残留）：猛甩（375°/s）时 `disp` 仍有 0.156。
   要把这条彻底解决，只有 (A) 运动期改成与顺序无关的渲染（**第九轮已做并验证，见 §6.13**：
   实测乱序画面差 36.37 → 0、运动期帧 P50 −44%、order 数据 1526 → 76 MB；**但用户反馈观感
   "看着太难受"，现已默认关闭**，要拿这条收益得先按 §6.13 末尾那三条改观感）或 (B) 把排序搬到 GPU
   缩短 λ（引擎 2.21.3 自带 `ComputeRadixSort`，但 `unified` 通路打开即空屏，见 §6.5 的 spike；
   收益上限见 §6.11）。
7. **运动期不透明路径默认关闭**（§6.13）：代码/护栏/文档都在，靠 `window.__SPLATROOM_MOTION_OPAQUE__ = true`
   一行打开（不用重新打包）。用户说"太难受"的具体原因未确认（硬边+闪烁？孔洞？整体变"实"？），
   §6.13 末尾列了三条对症改法（抖动式 alpha 测试 / 足迹放大 / 按转速门限只在猛甩时切）。

# 8. v2（M2-1，2026-09-30，3.23.59）：贡献剔除 —— 第二杠杆与 unified 通路的真瓶颈

> 前提变了：3.23.58 起 unified（引擎 GPU 同帧排序）已是默认通路。v1 的全部测量都在主线上做的，
> 而 unified 下旋转帧的成本结构**完全不同** —— 本轮先踩了这个坑，再量出来，最后落地第二杠杆。

## 8.1 unified 下 v1 杠杆几乎失效（先量后改的第一课）

20M 填充夹具（`test-20m-fill.ply`，`--core-scale=1.6 --room-radius=360 --room-scale=2.4`），
WebGPU + unified，RTX 3070 Ti，同一进程：

| 状态 | rAF p50 | GPU p50 | lit |
| --- | --- | --- | --- |
| 静止、全分辨率 | 70.9 | 70.8 | 81.3% |
| 静止、**强制 0.5 分辨率** | 76.1 | 76.0 | 83.9% |
| 旋转、v1（阶梯到 0.5） | 78.3 | 78.3 | 80.0% |

**降分辨率几乎不再省时间**（静止 0.5 反而 +5ms）。解释：unified 每帧对全量 20M 点跑
projector compute + GPU 基数排序，这部分**与分辨率无关**，在旋转帧里占大头；
v1 在主线上"GPU 时间 ∝ 像素面积"的结论在 unified 上不成立。主线之所以成立，是因为
主线运动帧的成本几乎全是 per-instance 绘制的填充。

## 8.2 贡献剔除：杠杆是活的，但量纲差了三个数量级

引擎 projector compute 里本来就有这条剔除（`compute-gsplat-common.wgsl`）：

```wgsl
totalContribution = opacity * 2π * sqrt(det);   // det 是像素²单位 ⇒ ≈ α·π·radius²
if (totalContribution < minContribution) 剔除（不进排序键、不绘制）
```

排查记录（每一步都有探针证据，`_tmp/probe-mc-sanity.cjs` / `probe-mc-direct-dose.cjs`）：

1. 设 `scene.gsplat.minContribution = 1000`，画面不变 —— 一度以为杠杆死了；
2. patch `projector.dispatch` 追参数：**引擎确实每帧收到 1000**（72/72 次 dispatch）；
3. 小模型剂量响应：mc 3/100/1000 画面不变，**mc 10000 时 lit 75.6% → 5.6%** —— 杠杆是活的，
   只是本仓库模型/夹具里存活高斯的贡献普遍在 **10²–10⁴ 量级**（SuperSplat 的 0–1 加法步进
   是给它的航拍小高斯场景定的，搬过来 5 秒只能爬到 88，毫无效果）。

20M 夹具直接设引擎参数的剂量响应（旋转中，控制器关闭）：

| minContribution | rAF p50 | GPU p50 | lit |
| --- | --- | --- | --- |
| 3（基线） | 78.1 | 78.3 | 79.9% |
| 1000 | **18.9** | **18.9** | 48.5% |
| 3000 | 16.7 | 5.8 | 29.7% |
| 10000 | 16.7 | 4.0 | **0.2%（画面消失）** |

读法：剔除按"不透明度×投影面积"砍点 —— 远处/小/淡的高斯先死，近处主体保得住
（语义上接近运动期 LOD）；对 unified 的 per-splat 排序/投影成本按剔除比例线性回收。

## 8.3 v2 实现（`src/core/motion-quality.ts` + `scene.ts` + `splat-tier.ts`）

- **几何步进**：超预算每 50ms ×2，富余 ÷1.4（放松慢半档防震荡）。从基线 3 到 ~1000 只要
  ~9 步（450ms）。上游的加法 +0.05 在本仓库量纲下不可用（见 §8.2）。
- **静止值 = 引擎默认 3**：静止画面与今天的 unified 基线逐项一致；停手精确回落（幂等施加）。
- **上限 = 画质硬边界**（不是性能目标，预算控制器会在上限内自己停在预算上），
  按分级：A+高配 3（关闭，保持今天的行为）、A+低配 800、B 1500、C 4000。
- **暖启动**：记住上次手势收敛的工作点，再次拖拽直接从它开始（否则每次手势前 ~500ms 都付
  爬坡慢帧，实测 p95 被拖到 75ms）。暖启动帧重置步进时钟，不会立刻再 ×2。
- **组合次序**：贡献剔除便宜（一个 uniform、无 realloc）所以先行；分辨率阶梯只在贡献顶到
  上限还超预算时才往下走。
- **守卫**：`lockedRenderMode`（导出/360/快照）期间不施加（导出动画相机一直在动，不能让它
  丢淡 splat）；主线（`?unified=0`）不施加（引擎参数在主线没有消费者）；每帧幂等。
- **逃生门**：`window.__SPLATROOM_MOTION_CONTRIBUTION__ = false` 只关贡献剔除、保留分辨率阶梯。

## 8.5 已知边界 / 待办

1. **运动期的画质下限没有客观口径**：lit% 对剔除不敏感（大高斯仍在），剂量响应里的
   "lit 48.5%@mc1000" 是停手静止帧的等效读数。真实观感（细节变稀、远处先消失）需要
   用户在真模型上过目后再定 B/C 档上限。
2. **环/拾取语义**：CPU 拾取（selection worker）不经过 projector，不受影响；但被剔除的
   高斯如果带着选择环，运动期环会短暂消失（停手即恢复）—— SuperSplat 对环有显式豁免，
   引擎 projector 没有，接受为已知瞬态。
3. **mainline 上 v1 的结论依然成立**（主线仍是降分辨率有效）；贡献剔除是 unified 专属杠杆。
4. 分辨率阶梯在 unified 大模型上基本不再被用到（贡献剔除先到位）—— 阶梯保留作兜底。

# 9. M2-2（2026-09-30，3.23.60）：状态位脏区间上传 —— flush 从"每次 20MB"到"只传脏的"

> 对应路线图 M2-2 / 审计 P1-1（`docs/perf/supersplat-3.3.0-对比调研.md`）：
> 每次选择变更 = **20 MB 整块上传 + 全表 recount**。验收口径：**单次 flush ≤ 5 ms、上传 ≤ 4 MB**。

## 9.1 before 实测（20M 夹具，WebGPU，`_tmp/probe-state-flush.cjs`）

| 手势形态 | flush 耗时 | 上传字节 |
| --- | --- | --- |
| 50k 行小选区 | 19.4 ms | 20 MB |
| 500k 行大选区 | 19.6 ms | 20 MB |
| 8 段散点 ×1k | 19.8 ms | 20 MB |
| 全表 set/clear | 17.4–17.7 ms | 20 MB |

**任何手势都付全表代价**：`flush()` 是 `gpu.lock()` + `buffer.set(20MB)` + `unlock()`（整块上传），
且 bulk mutator（setBits/clearBits/toggleBits）把 `countsExact` 打假后 flush 再跑一次
**全表 recount**（20M 约 15ms）。两项都不达标。

## 9.2 实现（`src/splat/splat-state.ts`）

1. **脏 span 列表替换单区间**：mutator 现在按 run 逐条登记（最多 8 条，超出合并成一条包络，
   不劣于旧的单区间行为）。`dirtyLo`/`dirtyHi` 保留为兼容 getter（`verify-crop-export-state` 读它）。
2. **flush 只传脏 span**：
   - **WebGPU**：`wgpu.queue.writeTexture` 子矩形直传（先例：`writeCurveTable`）。引擎数据纹理宽度
     是 `ceil(sqrt(n))`（20M → **4473**，非 256 对齐），多行写的行距必须 padding 到 256 ——
     用一块复用 staging 逐行拷（行内 padding 不会被读）。同时镜像进引擎 `_levels[0]`
     （上下文恢复时引擎从这份 CPU 镜像重传，不镜像的话恢复后状态会回退）。
   - **WebGL2**：`gl.texSubImage2D` 直写（`UNPACK_ALIGNMENT=1`，任意行宽合法；末尾不完整的行
     单独写一行）。引擎自带的 `Texture.write()` 在 WebGL2 上每调用**泄漏一个 PBO** 且等 fence，不可用。
   - **≥50% 脏走引擎整块路径**（这不是兜底，是各后端最优解：整块 = 1 次 copy + 1 次上传；
     直传全量 = 3 次 20MB 拷贝，实测 7.3 vs 1.7ms）。种子 flush（导入后第一次，构造器登记全表）
     天然走整块路径，顺带把 `_levels[0]` 建好。
3. **recount 只剩种子一次**：setBits/clearBits/toggleBits 在内层循环里**增量维护三桶计数**
   （deleted > locked > selected 互斥桶，改动行 before/after 桶号不同才动计数），
   `countsExact` 从"每次 bulk 编辑打假"变成"永远为真"。

## 9.3 after 实测（20M 夹具，同一探针、同进程口径）

| 手势形态 | WebGPU flush | 上传 | WebGL2 flush | 上传 | 路径 |
| --- | --- | --- | --- | --- | --- |
| 50k 行小选区 | **0.2 ms** | **53.7 KB** | 0.1 ms | 53.7 KB | sub |
| 500k 行大选区 | **0.3 ms** | **505 KB** | 0.2 ms | 505 KB | sub |
| 8 段散点 ×1k | 0.1 ms | 49 KB | 0.1 ms | 49 KB | sub |
| 全表 set/clear | 1.7–2.0 ms | 20 MB | 4.4–4.7 ms（稳态） | 20 MB | full |

- **验收口径**：手势路径 flush ≤ 5ms（最大 0.4ms，**~50–100×**）、上传 ≤ 4MB（最大 505KB，
  **~40×**）双达标；全表脏（select-all/清除）时间也 ≤ 5ms（recount 消失的功劳）。
- **GPU 一致性**：探针末尾整纹理回读与 CPU 逐字节比对，两后端 mismatch=0、尾 padding=0。
- **回归**：`verify-crop-export-state` 6/6、`verify-model-renders` 7/7、`verify-selection-depth` 0 失败
  （WebGPU/unified）、`verify-edit-hide` 0 失败、`verify-selection-overlay` 0 失败；`npm run check` 全绿。

## 9.4 已知边界 / 决策记录

1. **全表脏的 20MB 上传保留**（时间达标、字节超标）：要让 select-all 也 ≤4MB 只能做
   **GPU 侧位压缩**（3 bit/点 → 理论 7.5MB，或学 SuperSplat 把状态拆到 instance 行），
   但那要改掉**全部 8+ 个着色器消费方**（splat-shader / splat-shader-wgsl / unified-shaders /
   overlay / bound / value / group-renderer / 数据处理 pass，GLSL+WGSL×双后端），
   风险收益比不划算 —— 记为待用户拍板的可选项，本轮只交"手势路径只传脏字节"。
2. **WebGL2 首次全量上传有 50–140ms 一次性尖峰**（引擎路径与直传路径都有，是驱动对首次
   大块传输的同步；旧代码在导入种子 flush 时同样付这笔，稳态 4.4–4.7ms）。种子发生在导入期，
   交互期的首个 select-all 可能再付一次 —— 接受为已知边界。
3. **`countsExact` 语义变化**：bulk mutator 现在增量维护计数，导入种子之后 recount 不再发生。
   外部唯一读数方（`splat.ts updateState` 的 numSelected/numLocked/numDeleted）行为不变
   （套件 `verify-selection-depth` 的选中数断言全过）。

# 10. M2-3（2026-09-30，3.23.61）：每帧 setParameter / 小分配清理 —— 稳态零写

> 对应路线图 M2-3 / 审计 P2-1/2/3：每帧 ~40 次 `material.setParameter`（含大量字面量数组
> 重新分配）+ `serialize()` 每帧 `Array.from` ×3 + unified 钩子每帧重建/散列着色器源码。
> 验收口径：**onPreRender 自耗时 ≤ 300 µs/元素**。

## 10.1 before 实测（test-model.ply，1 元素，`_tmp/probe-prerender-cost.cjs`）

| 通路 | Splat.onPreRender | scene.onPreRenderInner | unified 钩子 | setParameter/帧（moving / idle） |
| --- | --- | --- | --- | --- |
| unified（默认） | 117 µs | 276 µs | 98 µs | 37 / 37 |
| 主线 `?unified=0` | 39 µs | 147 µs | —（关） | 36.6 / 36 |

（此 Edge 环境 `performance.now()` 粗化到 100 µs 档，读数为均值；max 两通路均 ≤ 300 µs。）

结构性问题（与模型大小无关，纯每帧 churn）：
1. **unified 钩子**：`bakeUnifiedModifyVS/FragmentShader/VertexShader` 每帧对几 KB~几十 KB
   着色器源码做 `.replace()` 重建新串，再做 3 次 `hashSource`（O(全长) FNV）—— 只为确认
   "没变"。
2. **两条通路的参数块**：~35–40 次 setParameter/帧，引擎的 `Material.setParameter` 是纯赋值
   （`parameters[name].data = value`，无 dirty 标记），绘制前引擎每帧把 `parameters` 里
   **已有的**值重新推进 scope —— 稳态下这些写全部白费。
3. `serialize()`：每帧 `Array.from(Float32Array)` ×3 + 新 `curveFlat` 数组；scene `onUpdate`
   每帧 `new Set([...4 个临时数组])`。

## 10.2 实现

- **新增 `src/splat/material-param-cache.ts`**：`MaterialParamCache` —— setScalar/setArray/
  setValue 逐项比较，值没变就不调 setParameter；数组由缓存持有**持久副本**（调用方可传临时
  scratch，材质拿到的引用永远属于缓存）；材质对象换了（replaceData/引擎重建）自动清账重写；
  `ensureIntact` 哨兵校验防引擎原地重置 `parameters`（unified 的 copyMaterialSettings 风险）。
  语义等价依据：引擎 setParameter 纯赋值 + 绘制前每帧重推 parameters → scope。
- **`unified-shaders.ts`**：三个 bake 函数按烘焙键记忆化（键没变返回同一份字符串引用）。
- **`unified-material.ts`**：wantName 三段散列按**源码引用**记忆化（bake 记忆化后引用稳定）；
  ~35 次 setParameter 全部走 per-material 缓存（WeakMap）；缺省中性调色对象/字面量数组提为
  模块常量；安装状态对象每帧复用。
- **`color-params.ts`**：新增 `fillSplatColorParams`（原位填充）+ `splatColorParamsScratch`
  （**per-splat** 持久 scratch —— 不能全局共享：数组引用会进材质 parameters）+
  `applySplatColorParamsCached`；原 `splatColorParams`/`applySplatColorParams` 保留。
- **`splat.ts`**：onPreRender 参数块（~40 次）全部走 per-splat 缓存；serialize 直接传
  Float32Array（packa 原生支持）+ curveFlat 模块级复用。
- **`gpu-camera-uniforms.ts`**：可选缓存参数（主线传、PiP 的写入-恢复对不传，维持原行为）；
  两个 4 元素数组提为模块 scratch。
- **`scene.ts`**：unified 钩子用 fill+scratch、选中/锁定色 scratch、effectParams 不再 spread；
  onUpdate 的变化类型 Set 复用。

## 10.3 after 实测（同探针同口径）

| 通路 | Splat.onPreRender | unified 钩子 | serialize | setParameter/帧（moving / idle） |
| --- | --- | --- | --- | --- |
| unified before → after | 117 → 120 µs | 98 → **38 µs** | 15 → **3.7 µs** | 37 → **7.9 / 6** |
| 主线 before → after | 39 → 66 µs* | — | 21 → **12 µs** | 36.6 → **4.6 / 0** |

- **idle 残余 6 次/帧经逐名诊断为引擎内部**（hybrid renderer 每帧写 `sortedIndices` /
  `projCache` / `numSplatsStorage` / `clipToViewZ` / `alphaClip×2`）—— SplatRoom 侧稳态
  setParameter = **0**。
- **验收**：onPreRender 自耗时 ≤ 300 µs/元素（unified 120 / 主线 66，max 均 ≤ 200）✓。

## 10.4 已知边界

1. moving 时相机矩阵类参数（uSplatView×3 / srViewProj / srClipToWorld / 裁剪盒矩阵）确实
   每帧变化，缓存照样写 —— 消除的是分配与稳态白写，不是"变化时就不写"。
2. 引擎 hybrid renderer 自己的 6 次/帧 setParameter 不在本仓库可改范围（引擎侧）。
3. `scene.onPreRenderInner` 的 ~250 µs（unified）主体不在参数块（splats 遍历/放置收集等），
   本轮未动；如需再压，单列一轮。
