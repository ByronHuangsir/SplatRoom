# 交互期降级（P0-3 v1）—— 实现与实测

> 本轮把"运动期降质量、停手恢复"做出来了，并且是**先量后改**：先量化了每个候选旋钮，再挑真正有效的那个。
> 结论：**在 GPU 受限的 20M 上，旋转帧 p50 70.9 → 29.8 ms（−58%）**；而文档原来推荐的三个旋钮里，
> **SH 波段只值 −0.5%、`alphaClipForward` 是 no-op**，唯一有效的是**降渲染分辨率**。
> 同时查出并修掉了两个**测量层面的 bug**（见 §2、§3），它们此前让"旋转期"的结论建立在一个没有正常绘制的相机上。

## 1. 做了什么（代码）

| 文件 | 作用 |
| --- | --- |
| `src/core/camera-motion.ts`（新） | 相机运动检测：位姿对比 + 指针按下，`settleMs = 200`。位姿对比是主信号——`camera.userDragging` 漏掉自动旋转、时间轴 tween、`setPose` |
| `src/core/gpu-frame-timing.ts`（新） | GPU 每帧耗时：包装引擎 `gpuProfiler.report` 按 `renderVersion` 归属到帧，并按动/静分类统计；`settledSpanPeak` 是"最近若干静止帧的峰值" |
| `src/core/motion-quality.ts`（新） | 纯策略状态机（不引引擎、可纯 node 单测）：`autoEngageMs = 60`、预算 33 ms、步进限频 300 ms、阶梯 = 渲染缩放 0.7 / 0.5 |
| `src/scene/scene.ts` | 每帧接线：运动状态 → GPU 标签 → 策略 → 幂等施加 `camera.targetSizeOverride` + `rebuildRenderTargets()`；降级期间保持渲染直到恢复那一帧真正发生 |
| `docs/verify/verify-motion-quality.cjs`（新，进批量） | 浏览器回归 7 项：静止全分辨率 / 运动降分辨率且渲染目标真的变小 / **`view.bands` 全程不变** / 停手精确恢复 / 逃生开关 |
| `docs/verify/verify-motion-quality-policy.mts`（新，纯 node） | 策略单测 13 项：arming 阈值、预算方向、限频、恢复、无 timestamp 回退、master switch、forceEngaged、reset |
| `docs/probes/gpu-frame-probe.cjs`（新） | GPU 每帧耗时探针 + **`litPercent` 可见性检查**（没有它，"快"可能只是没画东西） |

**逃生开关**：`window.__SPLATROOM_MOTION_QUALITY__ = false` 整体关闭（与 `__SPLATROOM_SELECT_WORKER__` 同一约定）。

**为什么不用 `view.setBands` 做降级**：那条路会把值写进偏好（localStorage）、`.ssproj`、设置面板与导出弹窗
（`P0-3-交互期降级-前置侦察.md` §1/§5.1）。本实现的降级是**临时的渲染目标缩放**，**完全不碰 `view.bands`** ——
回归套件专门有一项断言这一点（实测 `view.bands 3 -> 3`）。

## 2. 先修掉的测量 bug ①：探针的旋转把相机搞成了 NaN

`docs/probes/sortrate.cjs`（上一轮遗留）与我的 `perf-probe.cjs` 用的是
`cam.setAzimElev(cam.azim + 1.2, cam.elev, 0)`。本 fork 的 Camera **只有 `elevation`，没有 `elev`**
（`src/camera/camera.ts:271` 是 `azim`、`:275` 是 `elevation`）⇒ 传进去 `undefined` ⇒
`elev = Math.max(minElev, Math.min(maxElev, undefined)) = NaN` ⇒ 相机矩阵整体 NaN。

实测对照（同一次运行，两个约定各转 1 秒）：

| | `cam.elev`（原探针写法） | `cam.elevation`（正确） |
| --- | --- | --- |
| 相机位姿是否有限 | **否（NaN）** | 是 |
| `elevation` 之后 | NaN | −15 |
| 运动检测看到几帧在动 | **0 / 60** | **60 / 60** |
| 控制台 NaN 报错 | **948 条/秒** | **0** |

⇒ 三件事因此被解释清楚：
1. 此前汇报的"20M 每次跑都刷 6 条 `translate(NaN, NaN)`"不是视图立方体的 bug，而是**探针的 NaN 相机**在驱动视图立方体（小夹具、正确旋转时 0 条）。
2. 用这两支探针量到的**旋转期数字全部作废**（模型当时并没有被正常绘制）——包括我上一轮报的"旋转 p95 21.3 ms"。
3. 排序**消息数**类结论（P0-2 的 45.1 → 4.2 次/秒）不受影响：引擎每帧无条件调 `sorter.setCamera`，闸门限的是它，与相机是否 NaN 无关。

已在 3 个文件里改为 `cam.elevation`（`sortrate.cjs`、`perf-probe.cjs`、`gpu-frame-probe.cjs`），
并在 `sortrate.cjs` 里留了注释说明这个坑。

## 3. 先修掉的测量 bug ②：合成夹具"20M 点"其实什么都没画

第一版合成夹具的核心高斯尺度 0.006–0.02 世界单位，在取景距离（`framingRadius` 1691）下**是亚像素**，
而着色器会把投影尺寸小于 `minPixelSize`（引擎默认 2 px）的高斯**直接剔除** ⇒ 20M 点里几乎全部被丢掉。

于是出现了一个"看起来很好"的假象：GPU 只有 **2.4 ms**、帧 p50 18 ms —— 因为屏幕上基本没东西。
给探针加 `litPercent`（沿用 `verify-large-model-ui.cjs` 的 `max(r,g,b) > 60` 口径）后一眼看穿：

| 夹具 | litPercent | GPU p50 | 帧 p50 |
| --- | --- | --- | --- |
| 旧（亚像素） | **2.1%** | 2.4 ms | 18 ms |
| 新（`--core-scale=1.6 --room-radius=360 --room-scale=2.4`） | **81%** | **70.0 ms** | 69.8 ms |

⇒ `docs/verify/gen-synth-large-splat.cjs` 增加了尺寸/房间半径旋钮（默认值保持原比例），
且**任何性能测量都必须带 `litPercent`**。

## 4. 旋钮量化（20M fill 夹具，静止强制帧，同一进程）

| 旋钮 | frame p50 | GPU p50 | Δ |
| --- | --- | --- | --- |
| 基线（bands 3 / minPixelSize 2 / 全分辨率） | 69.8 ms | 69.92 ms | — |
| **SH 波段 → 1** | 69.5 | 69.57 | **−0.5%** |
| **SH 波段 → 0** | 69.5 | 69.57 | **−0.5%** |
| minPixelSize → 4 | 69.9 | 70.01 | 0% |
| minPixelSize → 8 | 68.8 | 68.87 | −1.5% |
| minPixelSize → 16 | 58.6 | 58.75 | −16% |
| **渲染缩放 0.7**（`targetSizeOverride`） | **39.9** | 39.98 | **−43%** |
| **渲染缩放 0.5** | **25.4** | 25.43 | **−64%** |
| 渲染缩放 0.35 | 18.1 | 18.93 | −73% |
| 恢复全分辨率 | 69.9 | 69.92 | 0（画面 mean\|ΔRGB\| = **0**，逐像素精确恢复） |

**读法**：这个模型的 GPU 时间**与像素面积近似成正比**（填充/overdraw 主导），而不是被顶点/SH 主导
——所以"降波段"几乎没用，"降分辨率"才有效。顺带复核了两个文档结论：`alphaClipForward` 在本 fork 是 no-op（§2 已知），
"SH 波段是最便宜的降级"这条**在填充受限的场景下不成立**。

**另有一条走不通的路**：`config.camera.pixelScale` 不能当交互旋钮用。实测把它改成 0.5/0.35 时，
画布/设备分辨率跟着变（`targetSize 3658 → 1829/2560` 反复横跳），帧时间反而涨到 **242 / 472 ms**，
画面也整体变了（mean\|ΔRGB\| 148）。正确机制是 `camera.targetSizeOverride`（PiP 预览用的那个）。

## 5. 实现后的 A/B（20M fill，WebGPU，连续旋转 4 秒，同一进程）

| 量 | 关闭（`__SPLATROOM_MOTION_QUALITY__ = false`） | 打开 | 变化 |
| --- | --- | --- | --- |
| 4 秒内帧数 | 58 | **119** | **×2.05** |
| 帧 p50 | 70.9 ms | **29.8 ms** | **−58%** |
| 帧 max | 208.2 ms | 77.8 ms | −63% |
| >33 ms 的帧 | 52 | 48 | —（见下） |
| GPU p50（运动中） | 71.0 ms | **29.96 ms** | −58% |
| 降级生效比例 | 0 | **1.00** | — |
| 渲染目标宽度（运动中） | 1280 | **640**（= 阶梯第 2 档 0.5） | — |
| litPercent | 79.9% | 79.9% | —（该指标对清晰度不敏感） |
| 停手后 | — | `engaged=false`、override `null`、target 1280 | **精确恢复** |

**arming 过程（实测）**：静止期强制帧的峰值 `settledSpanPeak = 72.1 ms > 60 ms` ⇒ `autoEngaged = true`；
用户一停手就恢复（`afterSettle` 全绿）。**控制器自适应**：0.7 档实测 39.9 ms 仍超预算 33 ms ⇒ 自动进到 0.5 档（25–30 ms）。

**诚实边界**：
- **>33 ms 的帧数没降**（52 → 48）：p50 从 71 降到 30，但每帧仍有固定成本与抖动（阶梯切换会重建渲染目标，那一帧更慢）。**"p50 减半"不等于"全部 30 fps"**。
- p95（69.7 ms）仍高，原因同上：约 5% 的帧仍是全分辨率或正逢切换。
- `litPercent` 对清晰度不敏感，**不能用它衡量降级的画质代价**；画质代价见 §4 的 mean\|ΔRGB\|（0.5 档为 113）。
- 合成夹具依然是合成夹具：**真机上到底值不值，要用用户的真实扫描件复核**。

## 7. 已知风险 / 待办

1. **降级期间拾取坐标会不一致**：投影/拾取换算用 `scene.targetSize`（`src/app/editor.ts:1027` 等），
   降级时它变小了。实际影响面很小（相机拖动与选择手势不会同时发生），但"边转边框选"这种操作需要复核。
2. **PiP 预览也写 `targetSizeOverride`**（`camera.ts:1207/1214`）：本实现每帧幂等校验并重设，能抵抗互相覆盖，但两者叠加时的行为没有专项套件。
3. **`stepMs = 300`** 是因为我们的旋钮要重建渲染目标（不像上游改一个 uniform 可以 50 ms 一次）；档位切换那一帧会明显更慢。
4. **无 timestamp query 的适配器**上按模型规模回退（≥ 200 万点即降级），此时"降了但没测"——默认阶梯只降分辨率，代价可接受。
5. 上游那套更进一步的东西**没做**：紧凑化 + indirect draw（只画存活高斯）、贡献剔除、遮挡剔除、运动期完全不排序的 1 spp 随机透明。
   本轮的结论是：在填充受限的场景下，**先降分辨率**性价比最高；上面这些留给真正需要时再做（可行性见 `supersplat-3.3.0-代码可借鉴点.md`）。
