## 1. 目标与判据

* 目标：运动帧（相机在动）走"不依赖顺序"的随机透明，并且**观感接近正常 alpha 混合**——上一轮失败的
  原因就是缺这道 resolve：1 spp 逐片元取舍后高斯内部整片通过 ⇒ 实心圆盘。
* 成功判据（缺一不可）：
  1. `order independence`：打乱顺序表后运动帧逐像素**不变**（现在已有这条断言，`verify-motion-opaque.cjs`）；
  2. **观感**：运动帧与"停手后的精确排序帧"在同一机位下的差异，**逐像素均值明显低于旧硬边裁剪**，
     且**降采样（4×4 块平均）后更低**（噪声被平均掉，这才是肉眼看到的量）；这条要新增断言并把截图交给用户确认；
  3. 静止帧、导出、拾取、选区高亮/描边、裁剪盒、PiP 全部不回归（现有套件 + 批量）。

**默认值的硬规矩（上一轮教训）**：观感类改动，**我先截图/给数字，用户点头之后才改默认**。
未点头之前默认保持 `motionRender = 关闭`。

## 2. 上游怎么做的（已扒，出处可查）

* `src/projected-splat-renderer.ts`：splat pass 渲到 **RGBA16F** 目标，随机帧把 `alpha` 写成 **哨兵 2.0**
  （区分"这一像素来自随机采样"与"来自别的 pass"），并单独维护 depth 与上一帧的深度图（用于遮挡剔除）。
* `src/shaders/projected-splat-shader.ts:275-300`：阈值 = 屏幕 **2×2 quad 的四个分层** + 每 splat 哈希，
  再叠 1/4 抖动 ⇒ 一个 alpha=a 的高斯在 quad 内覆盖 4a±1 个像素。
* `src/shaders/blit-shader.ts:26-141` `resolveStochastic`：把每个 quad 的四个样本**求平均**，
  再在 quad 中心之间**双线性插值**；alpha≠哨兵的像素**原样穿过**（"nothing stochastic nearby: leave the
  pixel exactly as it was rendered"）。⇒ 采样噪声被换成量化误差 + 插值平滑，软边回来了。
* capture/导出时 `lockedRenderMode` 强制走排序路径（我们导出的通路本来就走排序，不必改）。

## 3. 落到我们这份 fork 上的 6 步

我们的约束与上游不同，必须按我们的结构走：

* 两个后端共用同一套几何/材质（WebGL2 = GLSL，WebGPU = WGSL，后者由"GLSL 风格源 + 转译器"生成，
  所以**新代码要写在转译器认的方言里**：`varying` 裸引用、不能用 `pcPosition`）；
* 我们的 splat pass 有 **MRT**：RT0 = 场景颜色、RT1 = 选区/描边叠加（`outline-shader` / `underlay` 消费），
  这套在 resolve 之后必须仍然成立；
* 引擎（PlayCanvas 2.21.3 fork）负责 pass 顺序，我们只能通过 `onPreRender` / `onPostRender` /
  自定义 `Camera` 层插入 pass。

| 步 | 做什么 | 完成判据 | 回滚点 |
| --- | --- | --- | --- |
| 1 | **加离屏目标**：运动期把 splat pass 渲到 `RGBA16F` 颜色 + 深度；静止期仍直渲 backbuffer（零风险路径不变）| 静止画面逐像素与改动前一致（截图 diff ≈ 0）| 本步只新增资源，不接线 |
| 2 | **写哨兵**：随机模式下把通过取舍的片元写成 `vec4(color, 2.0)`（RGBA16F 存得下，其它 pass 不会 > 1）| 用探针读回该目标，确认随机像素 alpha=2、非随机像素原样 | 改回 `alpha=1` 即回退 |
| 3 | **blit 通道**：`src/shaders/blit-shader.ts` 加 `resolveStochastic`（quad 平均 + 双线性 + 非哨兵直通），把它插到 splat pass 之后、overlay/描边之前 | 运动帧不再有实心圆盘；截图给用户看 | 不插这条 pass 即回退 |
| 4 | **保住 MRT**：RT1（选区/描边叠加）随颜色一起走同一目标，resolve 只作用于 RT0，RT1 原样拷贝 | `verify-selection` / 描边套件全绿；选中态截图像素级不变 | 单文件改动 |
| 5 | **两后端**：GLSL 与 WGSL 两份 resolve 实现（注意 WGSL 方言限制；`ComputeRadixSort` 与我们无关）| 双后端跑第 5 节的套件 + 观感断言 | 单文件改动 |
| 6 | **调参与定默认**：先做 4×4 降采样观感断言，拿两种阈值散列（quad 分层 vs 纯 IGN）与"是否插值"做 A/B | 观感断言达标 + **用户点头** 才把默认改成随机透明 | 默认值一行 |

## 4. 已知风险（按严重度）

1. **pass 顺序 / 目标生命周期**：我们依赖引擎的渲染管线，插错位置会黑屏或闪烁；`camera-preview.ts`
   （PiP）会**交换 sorter/orderTexture**，resolve 通道要保证 PiP 走它自己的路径。
2. **RGBA16F 与 MRT 的兼容性**：WebGL2 下 MRT + 半浮点目标需要检查 `EXT_color_buffer_float` 与
   `drawBuffers`；不满足就走"运动期降级为单目标 + 关闭描边叠加"的兜底（并明确告知用户）。
3. **性能**：多一个全屏 pass + 一个 16F 目标（4K 下 ~66 MB），运动期本就要省；需要实测帧时间不升反降
   （上游靠同时叠的贡献剔除/遮挡剔除抵消）。
4. **观感不达标**：即使有 resolve，1 spp 的噪点仍可能在细结构上可见；这时只能加大 quad 平均范围
   （4×4 = 16 spp）——代价是分辨率感下降。**任何一条都要先给用户看，再决定是否默认。**
