# 8K 导出 + 后台导出：能不能、代价多少、怎么落地（2026-09-22，第十八轮）

> 用户这一轮的要求：**① 渲染导出的分辨率上限提高到 8K；② 探索是否可以后台导出。**
> 结论先行：**8K 三条导出路径都通了**（图像 / 视频 / 旋转台；360 从 4096 抬到 8192×4096），
> 而且 8K 必须自动走 VP9/AV1（H.264 在 8K 被 WebCodecs 直接拒）；
> **后台导出原来不行**（最小化 40 秒写出 0 帧），加三行 Electron 配置后**最小化期间能跑完**（实测 12 帧全出）。

## 1. 为什么先量再改：8K 一次会碰到四个墙

`docs/probes/export-8k.cjs` 把四个墙一次量清楚（本机 RTX 5090 / Edge 141 / WebCodecs）：

| 墙 | 实测 |
| --- | --- |
| **设备** | `maxTextureSize` = **16384**（webgpu 的 `limits.maxTextureDimension2D` 同为 16384）⇒ 8K 放得下 |
| **编码器**（用**应用真实的 codec 字符串**问的） | H.264（`avc1.640033`）：4K ✓、**8K 被拒**；H.265（`hev1.1.6.L120.B0`）：**本机所有分辨率都被拒**（没有 HEVC 编码器）；VP9（`vp09.00.10.08`）与 AV1（`av01.0.05M.08`）：**8K / 360-8K 都能真编出帧**；**8192×8192 三者都不行** |
| **内存** | 8K RGBA 一帧回读 **126.6 MiB**（4K 31.6 MiB）；360-8K 128.0 MiB，另外还要 6 张 4096² 立方体面 |
| **出片** | 8K PNG 一帧 **18.62 MB / ~1.7 s**；360-8K PNG 一帧 4.68 MB / ~3.9 s（equirect 要先渲 6 面再投影） |

**真编一帧的对照**（`isConfigSupported` 说行不算行）：

| 试验 | 结果 |
| --- | --- |
| vp9 4K / 8K / 360-8K | 都能 `configure()` + `encode()` + `flush()`（8K 出 30,694 B 一帧） |
| av1 8K | 同样能编（1,026 B 一帧） |
| h264 8K | `isConfigSupported = false`（这就是"选了 8K 点导出就报错"的来源） |

## 2. 落地：共用一份分辨率表 + 两道筛子

新增 `src/core/export-resolution.ts`（纯函数，12 项 node 断言 `verify-export-resolution.mts` 全绿）：

- **预设表**：标准含 `8k` = 7680×4320；360 含 `360-8k` = **8192×4096**（2:1）；`MAX_EXPORT_DIMENSION = 8192`。
- **设备筛子**：`presetOptionsFor(projection, maxTextureSize)` 把放不下的档位**直接不出现在下拉里**
  （比"让用户选完再报错"友好），自定义输入的上限也按设备夹（原来是硬编码 16000）。
- **编码器筛子（静态）**：`CODEC_CEILING` —— H.264 4096×2304、VP9/AV1 8192×4320、H.265 8192×4320
  （H.265 那档仍会被运行时再筛一次）。
- **编码器筛子（运行时）**：`src/ui/export-codec-support.ts` 用**应用真实使用的 codec 字符串**问
  `VideoEncoder.isConfigSupported()`（按 `codec:WxH:fps` 缓存；异常一律当不支持）。
- **码率**：`bitrateFor()` —— 老实现的 `bbpfFactors` 表**没有 8K 这一档** ⇒ `factor = undefined`
  ⇒ `bitrate = NaN` ⇒ `configure()` 直接失败。现在表里补了 `8k: 1/8`、`360-8k: 1/8`，
  表里没有的按像素数折算并夹到 `[1/16, 1]`，**任何输入都返回有限正整数**（1080p/4K 数字与历史一致：
  20.7 / 49.8 Mbps；8K = **124.4 Mbps**）。

三个对话框（图像 / 视频 / 旋转台）都改成共用这份表：

| 对话框 | 改动 |
| --- | --- |
| `image-settings-dialog.ts` | 360 预设加 8K（8192×4096）；按 `maxTextureSize` 过滤；自定义上限按设备夹 |
| `video-settings-dialog.ts` | 360 加 8K；分辨率/帧率/码率任一变化都重跑编码器策略；码率走 `bitrateFor()` |
| `turntable-video-dialog.ts` | **4K → 8K**（这是用户说的"上限"）；同样的策略与码率修正 |

**选了 8K 会自动换容器+编码器并给一行说明**（新键 `popup.render-video.resolution-note`，9 语言各 697 键）：

```
7680x4320 只能用 VP9/AV1 编码器 —— 已自动切换为 WEBM / VP9。
```

（踩到的坑：策略自己 `formatSelect.value = ...` 会再触发一轮 change，把编码器重置、把说明行藏起来 ——
用一个 `applyingPolicy` 旗子挡住；文案插值必须用 `{{name}}`，本仓库是 i18next 双花括号。）

## 3. 实测：8K 三条路径都真的出片

`docs/verify/verify-export-8k.cjs`（**8 项**，webgpu 全绿；webgl2 见批量结果）：

| 检查 | 实测 |
| --- | --- |
| 设备放得下 8K | `maxTextureSize = 16384` |
| 标准 8K PNG | 7680×4320、colorType 6、**18.62 MiB**、1712 ms |
| 360-8K PNG | 8192×4096、4.68 MiB、3904 ms（6 面立方体 + 投影） |
| 旋转台 8K PNG 序列 | **12/12 帧**、每帧 7680×4320 RGBA、合计 **222.5 MiB**、22.3 s（≈1856 ms/帧） |
| 旋转台 8K 视频 | 真 WebM/VP9 文件 1.57 MiB（EBML 魔数校验）、11.5 s、bitrate 124,416,000 bps（改前是 NaN） |
| 图像对话框提供 8K | 标准 `4K / 8K`；切到 360 后 `4096x2048 / 8192x4096` |
| 旋转台对话框 8K 自动切换 | 选 8K 后容器变 WebM、编码器只剩 `VP9 / AV1`（H.264 消失）、说明行出现 |

## 4. 后台导出：原来不行，加三行配置后能跑完

机制（代码 + 实测）：导出循环靠"让一手宏任务"（`await new Promise(r => setTimeout(r, 1))`，
`src/app/render.ts`）驱动，真正的出帧依赖 PlayCanvas 自己的 rAF 渲染循环。
Electron 的 `webPreferences.backgroundThrottling` **默认 true** ⇒ 窗口最小化/被遮挡时
**rAF 暂停、`setTimeout` 降到 ~1 Hz**，两者叠加就是"导出卡住"。

口径：`docs/probes/background-export.cjs` —— 起打包版 → 8K 旋转台 PNG 序列（12 帧）→
用 PowerShell + user32 `ShowWindow(SW_MINIMIZE=6)` 最小化主窗口 → 每 4 s 采样页内
`document.hidden` / `rafHz` / 定时器间隔 / **已写出的帧数**（数 `URL.createObjectURL` 调用，每帧一次）。

| 量 | 最小化前 | 最小化中（默认 `backgroundThrottling: true`） |
| --- | --- | --- |
| `document.hidden` | false | **true** |
| rAF | 38–60 Hz | **停摆**（采样窗内不再前进） |
| 定时器间隔（200 ms 心跳） | ~200 ms | 最大 **1442 ms**（≈1 Hz） |
| 已写出帧数 | 2 | **40 秒里 0 帧**（一直停在 2/12） |
| 导出总耗时 | — | **60.4 s**（恢复窗口后才跑完；前台是 21 s） |

**修复**（`electron-main.js`，三行）：

```js
app.commandLine.appendSwitch('disable-renderer-backgrounding');
app.commandLine.appendSwitch('disable-background-timer-throttling');
// 主窗口（以及 window.open 出来的工具窗口）
webPreferences: { ..., backgroundThrottling: false }
```

**修复后同口径复测**（同一份 bundle，开发版 Electron = 仓库里的 `electron-main.js`）：

| 量 | 最小化中（修复后） |
| --- | --- |
| `document.hidden` | **false**（渲染进程不再被当成后台） |
| 已写出帧数 | **3 → 6 → 8 → 9 → 12 连续推进**，最小化期间跑完 |
| 导出总耗时 | **24.9 s**（前台 21 s；差异来自 8K 本身的负载，不是节流） |

⇒ **可以后台导出**，前提是关掉 Electron 的后台节流。注意两点：
① 这是"最小化/被遮挡后继续跑"，**不是**"关掉应用还能跑"（那需要真正的离屏渲染 + 常驻进程，本轮没做）；
② 长时间最小化时 8K 导出仍会占满 GPU/CPU，属于设计使然，UI 上没有"导出中"的指示器（下一轮可考虑）。

## 5. 新坑（HANDOFF 65/66）

1. **探针自己 spawn Electron 起不来**：`spawn(electronPath, [hostDir, ...])` 起一个"探针自己的
   Electron 主进程"在本机**静默退出**（无 stdout/stderr），而直接 `& electron.exe <dir>` 前台跑同一份
   代码却正常 —— 结论：**别自己起 Electron 宿主**，改用"打包版 + `ShowWindow` 最小化"这条路。
2. **最小化进程名**：打包版进程叫 `SplatRoom`，开发版叫 `electron`。第一版只按 `SplatRoom` 找窗口，
   attach 模式下拿到 `no-window` —— **窗口压根没最小化，于是"修复后也正常"是假绿**。
   探针现在两种进程名都试，并把 `ok:<进程名>:<pid>` 打出来作为"真的最小化了"的证据。
3. **`page.evaluate(async () => { await export })` 会等到导出结束**：第一版这样写，于是"最小化期间"的
   采样全部落在导出之后，得出"7 秒就完成"的假结论。正确做法是**不 await**，把 promise 挂在 window 上。

## 6. 还没做

1. **导入残留的逐行主线程工作**（60M 上 11.6 s、20M 上 9.8 s）—— 用户说"下一轮按我的顺序优化"，
   就是这一条（state/transform 通道懒分配、首次 GPU 上传分批让出宏任务）。
2. 导出中的进度指示 / 完成通知（后台导出已可用，但用户最小化后看不到任何反馈）。
3. 8K 的 H.265：本机没有 HEVC 编码器无法验证；若以后要为 8K 开 H.265，
   需要把 `render.ts` 的 `hev1.1.6.L120.B0`（Level 4.0）按分辨率抬到 Level 5.2/6.0 并在有编码器的机器上实测。
