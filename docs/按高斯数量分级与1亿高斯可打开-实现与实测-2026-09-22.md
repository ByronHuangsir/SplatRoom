# 按高斯数量分级 + 1.35 亿高斯模型可打开 —— 排查、实现与实测（2026-09-22）

用户休息前给的四件事里的第 1、2 件（外加第 3、4 件的探索结论见各自章节）：

1. **按模型规模分级**（< 500 万 / 500 万~5000 万 / > 5000 万）采取不同策略，兼顾性能、显示效果与
   **中低性能电脑的兼容性**；测试用 `C:\Users\admin\Desktop\szbwg-zzslbz-1\output` 里的真实扫描件；
2. **让桌面上的《1亿gs.ply》打开**（134,652,397 高斯 / 7.02 GB），同样要考虑低配机器。

结论先行：

- **1.35 亿高斯模型现在能打开了**：同一台机器、同一个文件，改前 **>900 秒仍未完成、0 个高斯**；
  改后 **87.2 秒**导入完成、**6000 万**高斯、`litPercent 91.6%`、帧 p50 **18 ms**。
  低配模拟（强制 600 万预算）**44.6 秒**导入、帧 p50 **18 ms**、p95 **18.1 ms**。
- **分级落地为一份纯决策模块**（`src/core/splat-tier.ts`）：模型三档 × 设备三档 ⇒ 导入预算 + 运行时策略。
  **A/B 档的真实扫描件一个点都不动**（实测 3.36M / 6.56M / 10.46M / 20M 四件全部 `reduction = null`）。

## 1. 为什么"打不开"：量出来的三层原因

### 1.1 第一条墙是我自己的探针先撞上的：单块 `ArrayBuffer` 上限（约 2 GB）

`docs/probes/huge-model-open.cjs` 的朴素路径（`fetch(url).arrayBuffer()`）对 7.02 GB 直接
`TypeError: Failed to fetch`（12.98 s），**连 4.72 GB 的 20M 夹具也失败**。
`docs/probes/huge-io-wall.cjs` + `docs/probes/alloc-wall.cjs` 把三层分开量：

| 层 | 结果 |
|---|---|
| 服务端流式读完 7.5 GB（`res.body.getReader()`，不进单块） | ✅ 7,540,534,597 字节 / 9.6 s / 88,483 块 |
| 页内单块分配（`new ArrayBuffer`，每 4 MB 真写一次） | 0.25/0.5/1/1.5 GB ✅；**2 GB ❌ `RangeError: Array buffer allocation failed`** |
| 渲染进程 JS 堆上限 | **4192 MB**（`performance.memory.jsHeapSizeLimit`） |

⇒ 任何"把整个文件读进一个 ArrayBuffer"的路径在 5 GB 以上都不可靠。
（`src/app/file-handler.ts:404` 的 **URL 分支**用的就是这条路径 —— 拖入文件走的是 `File`，不受影响。）

### 1.2 应用真正走的路径：流式读没问题，但**物化 7 GiB 列**

`src/io/read/file-systems.ts:14` `BLOB_CHUNK_SIZE = 4MB`，`BlobReadStream.pull()` 按 4 MB
`slice().arrayBuffer()` 流式读 ⇒ **7 GB 文件不会被整体读入**（这条没问题）。
问题出在 `src/io/read/loader.ts` 的 `materializeToDataTable()`：它把**每一列**都物化成
`Float32Array(134,652,397)`（14 列 × 538 MB = **7.02 GiB**），随后还有
`sortMortonOrder` + `permuteRowsInPlace`（索引 513 MB + 每列一次新缓冲），引擎侧再叠加
纹理 CPU 镜像（4.01 GiB）与 centers 三份（约 4.5 GiB）。

**实测（改前，`docs/probes/huge-model-open.cjs`，等 900 秒）**：
`fetch` 33.3 s → `import` 之后 **900 秒仍然没有完成**、`splatElements = 0`、无报错、无崩溃；
并行采样的 msedge 工作集爬到 **10.9 GB** 并停留约 40 s。这就是用户说的"打不开"：
窗口几分钟没有响应，也没有进度。

## 2. 修法

### 2.1 分级模块（`src/core/splat-tier.ts`，纯函数、可 node 单测 21 项）

```ts
splatTier(numSplats)   // A < 5,000,000 ≤ B ≤ 50,000,000 < C
deviceClass(facts)     // high / mid / low：集显字符串、绑定上限、内存、核数（外加 forcedClass 排障开关）
hardSplatLimit(facts)  // min(maxStorageBufferBindingSize/4, maxBufferSize/4, maxTextureDimension2D²)
importBudget(n, facts) // 导入该物化多少行 + 原因（within-budget / over-hard-limit / over-device-cap / forced-budget）
runtimePolicy(n, facts)// LOD 是否自动、LOD 比例、降级阶梯、启用门槛、目标预算、无计时兜底
```

**只做"不这样就打不开"的削减**，两条规则：

1. **适配器硬上限永远生效**（WebGPU 的排序结果是一个 u32/点的存储缓冲；纹理要 `ceil(sqrt(N))²`）。
   `maxStorageBufferBindingSize` 默认 128 MB ⇒ 约 3350 万点封顶 —— 这是硬墙。
2. **舒适上限只对 C 档（> 5000 万）生效**：`low 600 万 / mid 2000 万 / high 6000 万`。
   A/B 档的模型今天本来就能打开（用户自己的 2000 万点扫描件就是 B 档），
   为了"更快"把它们悄悄抽稀会直接改掉用户看到的画质 —— 那该由运行时策略（LOD / 交互期降级）去省。

### 2.2 在物化**之前**抽稀（`src/io/read/strided-source.ts`）

新增"抽稀视口"：把惰性 `ChunkSource` 包成行数更少的同类源，对外宣称
`numGaussians = target`，内部把每次读请求（chunk 或 gather）翻译成对底层源的 gather 读，
行号按等距抽样 `floor(i × total / target)` 映射。

- **峰值内存按比例下降**：1.35 亿 → 6000 万时 7.02 GiB → 3.1 GiB；→ 600 万时 → 320 MB；
- 只解码被保留的那些行；
- 为什么不用 splat-transform 的 `decimateSourceAdaptive`：本仓库已有结论
  （`src/lod/lod.ts:87-94`）——自适应抽稀需要一份完整工作副本，"for tens of millions of splats
  the copy alone would freeze the UI for minutes"。抽样只多一份目标大小的列，还能逐块报进度。
- 进度：`onBudget` / `onDecimateProgress` 回调 ⇒ 导入期把不定量 spinner 换成带文字的进度条
  （新 i18n 键 `popup.import-simplify-progress`，9 语言已补齐，各 690 键）。

### 2.3 运行时策略接线

- `MotionQuality.applyPolicy()`：阶梯/门槛/预算/无计时兜底按分级重设（`src/core/motion-quality.ts`）；
- `Scene.tierPolicy()` + `applyTierPolicy()`：档位键（`tier|device`）变化时才重设并
  `fire('tier.policyChanged')`；查询接口 `scene.events.invoke('tier.policy')`（给 UI 与套件）；
- `src/lod/editor-lod.ts`：**B/C 档自动开启运行时 LOD**（用户要的"不同等级不同策略"里性能那一半）。
  代理层只在相机远离到阈值外才接管，且 `lod.allowProxy` 仍要求"没选中、没在拖、没在撤销"；
  关掉：设置面板的 Runtime LOD 开关或 `window.__SPLATROOM_TIER_LOD__ = false`。
- 逃生开关：`window.__SPLATROOM_IMPORT_FULL__ = true`（强制全量导入，探针对照用）、
  `window.__SPLATROOM_IMPORT_BUDGET__ = <n>`（手动指定预算）、
  `window.__SPLATROOM_DEVICE_CLASS__ = 'low'|'mid'|'high'`（在一台机器上模拟三档设备）。

## 3. 实测

### 3.1 1.35 亿高斯模型（`1亿gs.ply`，134,652,397 点 / 7.02 GB，WebGPU / RTX 5090）

| | 改前（原样物化） | 改后（默认预算） | 改后（强制 600 万 = 低配模拟） |
|---|---|---|---|
| 导入是否完成 | ❌ **> 900 s 仍未完成** | ✅ **87.2 s**（fetch 30.2 s + 解析 57.0 s） | ✅ **44.6 s**（fetch 33.7 s + 解析 10.9 s） |
| 高斯数 | 0 | **60,000,000** | **6,000,000** |
| 抽稀信息 | — | from 134,652,397 → 60,000,000（over-device-cap） | → 6,000,000 |
| 亮像素占比 | — | **91.6%** | **86.2%** |
| 帧 p50 / p95 | — | 18 ms / 215 ms（导入后首帧含排序与上传） | **18 ms / 18.1 ms** |
| JS 堆 | 峰值未测到（渲染进程工作集 10.9 GB） | 6.9 GB | 727 MB |
| 运行时 LOD | — | 自动开启 | 自动开启，代理层 600k + 2.10M |

### 3.2 用户的真实扫描件（`szbwg-zzslbz-1\output`，WebGPU / RTX 5090）

| 文件 | 高斯数 | 档位 | 抽稀 | fetch | 解析 | 亮像素 | 帧 p50 | LOD 自动 | 代理层 |
|---|---|---|---|---|---|---|---|---|---|
| `point_cloud_30000.ply` | 3,355,656 | **A** | 无 | 3.1 s | 5.8 s | 97.0% | 18 ms | **否**（小模型不动） | — |
| `splat_70452.ply` | 6,559,584 | B | 无 | 6.1 s | 13.2 s | 99.3% | 18 ms | 是 | 656k + 2.30M |
| `splat_91648.ply` | 10,458,856 | B | 无 | 9.7 s | 23.3 s | 93.4% | 18 ms | 是 | 1.05M + 3.66M |
| `splat_138762.ply` | 20,000,000 | B | 无 | 19.3 s | 41.1 s | 86.2% | 18 ms（p95 230 ms） | 是 | 构建中 |

要点：
- **四件真实扫描件全部 `reduction = null`** —— 分级没有偷偷改用户的画质；
- 帧 p50 全是 **18 ms**：这是 60 Hz 垂直同步的地板（16.7 ms），说明这四件在本机都跑满帧；
- A 档不做 LOD、B 档自动做（代理层比例 + 距离阈值见 `lod.ts`）；
- 20M 的 p95 230 ms 出现在**导入刚结束的那几帧**（首次排序 + 80 MB 顺序上传 + LOD 构建并行），
  不是稳态帧时间。

### 3.3 设备分级（纯函数单测，21 项）

| 设备样本 | 判定 | 依据 |
|---|---|---|
| RTX 5090（binding 2 GiB） | high | 独显 + 绑定 ≥ 0.75 GiB + 内存 ≥ 8 |
| RTX 4060 Laptop（binding 1 GiB） | high | 同上（门槛取 0.75 GiB，避免刚好 1 GiB 掉进中档） |
| Intel Iris Xe（binding 128 MB） | **low** | 集显串命中 ⇒ 无论 limits 多大都算低档（共享显存才是本质） |
| 未知信息（`{}`） | mid | **绝不静默判成 high** |

## 5. 还没做的（诚实记录）

1. **导入期的"抽稀通知"只出现在进度条文字与 console**，没做完成后的 toast/popup
   （怕阻塞导入流程与探针；建议下一轮加一个非阻塞提示 + "下次按原样导入"入口）。
2. **抽稀是等距抽样**，不是质量感知抽稀：薄结构（栏杆、线缆）理论上会掉点。
   真要更好看，应该用 splat-transform 的 `decimateSourceAdaptive`（内存有界、可 spill），
   代价是慢（本仓库实测的"分钟级"）；可以在 C 档给一个"高质量导入（慢）"选项。
3. **导入仍在主线程**（load worker 默认关，且它把整个文件读成一个 ArrayBuffer，对本案无效）；
   1.35 亿 → 6000 万这档实测 57 s 主线程占用，窗口在这段时间没有响应（有进度条但不刷新画面）。
   下一步可以把"抽样 + 物化"搬进 worker（抽样本身是纯读+拷贝，很适合 worker）。
4. **A 档低配也给了一档退路**（[0.7, 0.5] / 门槛 45 ms），但没在中低配真机上验证过
   （本机只有 5090 + 集显；集显那台是核显输出，没跑过本应用）。
5. **超大模型（C 档）虽然能开，但这几条软门槛仍是降级的**（只读侦察报告核对出来的，
   建议下一轮一起处理）：
   - `src/splat/selection-core.ts:535-539` `CACHE_MAX_BYTES = 192 MB` ⇒ 6000 万点的**投影缓存直接置空**，
     每次推杆/框选都全量重投影（选择变慢）；
   - `src/splat/splat.ts:682` `mapping = new Uint32Array(this.numSplats)` ⇒ 6000 万点就是 **240 MB**
     常驻映射表；
   - `src/ui/floater-panel.ts:397` `AUTO_DETECT_MAX_SPLATS = 2_000_000` ⇒ 去浮云自动检测在 C 档**不跑**；
   - `src/io/load-worker-client.ts` 的 `readFileBytes()` 仍会**整块读进一个 ArrayBuffer**
     ⇒ 打开 load worker 开关对超大模型**不是解法**（会先撞 2 GB 的墙再回退主线程），
     真要搬 worker 必须先把它改成分块读（与本次的抽稀视口同一套思路）。
6. **失败呈现**：改前这类模型是"几分钟无响应、无弹窗"（渲染进程被 OOM 杀掉时连弹窗都没有，
   `file-handler.ts:368-372` 的 catch 只在解码抛错时触发）。现在有了进度条 + 导入预算，
   但"预算算错/磁盘满"这类异常路径仍会退回"沉默" —— 值得补一条看得见的失败提示。
