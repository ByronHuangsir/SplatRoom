## 三、建议（按可执行性分级）

### A. 需要你决策（我不会擅自动）

1. **是否删除 `archive/dead-src/`**：9 个模块已确认零引用，保留只是为了将来可能重接（平面修复、动画轨道等）。
   确认不要就直接删（顺带清理 `scss/planar-fix-panel.scss` 等死样式，注意它仍被 `style.scss` `@use`）。
2. **依赖精简**：524 个 devDependencies 建议单独做一轮——流程应为"删除 `node_modules` → 按实际引用（rollup/eslint/electron-builder/
   puppeteer 等约 30 个）重写 `devDependencies` → 重装 → `build` + 打包 + 真机启动验证"。风险中等（有些是构建期间接依赖），
   收益是可观的安装体积/时间。
3. **`src/` 根目录布局**：76 个松散文件可归并到 6–8 个领域目录（如 `camera/`、`splat/`、`gamepad/`、`pipeline/`、`io/`），
   但需要批量改写 import 且无自动化测试兜底，建议单独一轮做（我会用"移动一批 → tsc/eslint/build 全绿 → 提交"的节奏）。

### B. 低风险、可立即做（等你点头）

4. **收窄 61 个未引用导出的可见性**（`export const X` → `const X`，或从尾部 `export { … }` 列表移除）：编译器就是安全网
   （漏删会直接 tsc 报错），可一张提交完成。
5. **把审计脚本挂进日常流程**：`npm run audit`（待加脚本别名），或在提交前手动跑；它能持续发现新的死导出/孤儿/未用文案。
6. **逐条复核 19 处 `eslint-disable` 与 23 处 `@ts-ignore`**：能消掉的消掉，消不掉的补一句"为什么必须忽略"。
7. **拆分最大的两个文件**（`merge-scene.ts` 1,894 行、`editor.ts` 1,780 行）：按职责切分（如 editor 的选择/相机/文档段落），
   属结构性重构，建议在功能冻结期做。

### C. 不建议动

8. **批量替换 `as any`**：236 处大多是为了访问 PlayCanvas 引擎未公开字段，替换成接口声明收益低、回归风险高；
   建议只在新增代码里要求"新写的 any 必须带注释"。
9. **打开 `strictNullChecks`**：会波及全部 222 个文件、数千处空值判断，属破坏性改造；当前以 `noImplicitAny + 显式判空习惯` 维持。
