# 导入残留的 11.8 s 到底花在哪：CPU profile 归因 + LOD 代理层时机修正（第十九轮）

> 用户这一轮的 ②：**削掉导入残留的逐行主线程工作（建议：state/transform 通道懒分配、首次 GPU 上传分批让出宏任务）**。
> 结论先行：**那两条建议指向的不是瓶颈** —— 归因实测显示 11.8 s 里有约 11.3 s 是**引擎自己的
> 一次性 GPU 打包**（`updateTransformData` / `calcAabb` / `updateColorData`，本质是每高斯 ≈190 ns 的
> 逐行 CPU 循环），我们自己的通道分配与上传只占 0.4 s 量级。
> 真正能削的是**导入尾巴上的另一段 5.0 s**：LOD 代理层在 `import resolve` 之后 0.4 s 就开建
> （`editor-lod.ts` 里写死的 400 ms），正好砸在用户刚看到模型的那一刻。本轮把它挪到"线程真的空下来"
> 之后并逐层让出，**最长尾块 4,982 ms → 3,824 ms，且拆成 3,824 + 1,327 两段**。

## 1. 口径：CDP CPU profiler 归因（新增 `docs/probes/import-profile.cjs`）

前面几轮用的是"阶段打点 + 心跳 gap"，只能告诉你"哪一段占多久"，说不出"占在哪一行"。
这轮改成真正的采样 profiler：`Profiler.enable` → `setSamplingInterval(200µs)` → 导入 1.35 亿那只文件
（预算后 6000 万行）→ `Profiler.stop`，按**自时间**聚合，并把每个热点的**调用链**打出来
（CDP 的 profiler 节点给的是 `children`、没有 `parent`，要自己反向建表 —— 第一版链是空的）。

实测（webgpu，6000 万行，导入墙钟 57.9 s）：

| 自时间 | 函数 | 调用链 | 说明 |
| --- | --- | --- | --- |
| 3,368 ms + 1,749 ms | `H_.read` | `load ← createGSplatAsset ← Q_ ← updateTransformData ← H_.read` | 引擎 `SplatIterator.read` 的闭包：每个高斯读 10 个列 + 写 Vec3/Quat + 3 次 `Math.exp` |
| 1,542 ms + 679 ms | `calcAabb` | `… ← Q_ ← O_ ← calcAabb` | 引擎遍历全部高斯算包围盒 |
| 1,202 ms + 548 ms | `updateColorData` | `… ← Q_ ← updateColorData` | 引擎把 f_dc/opacity 打成半浮点写进显存纹理 |
| 1,176 ms + 640 ms | `updateTransformData` | `… ← Q_ ← updateTransformData` | 位置/旋转/缩放的打包（含 `r.normalize()`） |
| 642 + 591 ms | `float2Half` / `normalize` | 上面两个的子树 | 半浮点转换与四元数归一化 |
| 382 ms | `writeTexture` | `… ← unlock ← upload ← … ← writeTexture` | 真正上传显存 |

**`Q_` = 引擎的 `GSplatResource` 构造**（我们只做了一件事：`asset.resource = new GSplatResource(device, gsplatData)`），
所以这 ~11.3 s **全在引擎里**，是"把列式数据打成 GPU 纹理布局"的一次性成本。

> 顺手确认：导入后 `getElementsByType('splat').length === 1`，只有一份资源 —— 不存在"资源被建两遍"。
> 但 `lodAssets: 2` —— **有 2 层 LOD 代理**，那正是 profiler 里第二条 `Q_` 调用链（`d$ ← a$ ← Q_`）的来源。

## 2. 用户那两条建议为什么不解决问题

| 建议 | 实测代价 | 结论 |
| --- | --- | --- |
| `state`/`transform` 通道懒分配 | `state` 是 `Uint8Array(60M)` = 60 MB、`transform` 是 `Uint16Array(60M)` = 120 MB，都是**一次性 malloc + 清零**（profiler 里连前 22 都没进） | 不是瓶颈（≤0.2 s 量级） |
| 首次 GPU 上传分批让出宏任务 | `writeTexture` 自时间 **382 ms**（其余是打包，不是上传） | 分批只对 0.4 s 有意义 |
| — | 引擎逐行打包 ≈ **11.3 s**（≈190 ns/高斯） | **真正的瓶颈** |

引擎那段为什么慢：`SplatIterator.read` 每次调用要做 10 次类型化数组读取、4 次对象写、
以及（`activated === false` 时）3 次 `Math.exp`。60M × 这些 ≈ 5 s；再加上 `calcAabb`、`updateColorData`、
`updateTransformData` 的另外三趟逐行循环 —— 是**四趟 6000 万次的 CPU 循环**，不是某处写错了。
要真正消掉它只有三条路，都不在本轮范围：
① **少打行**（导入预算，已经在用：6000 万就是设备上限）；
② **绕开引擎自己预打包**（在 worker 里按引擎的纹理布局打包好再直接上传）—— 与引擎内部结构强耦合，
   且会打断编辑/导出依赖的列式访问（`getProp('x')`），风险极高；
③ 上游：让引擎把打包并行化/分块。

## 3. 本轮真正削掉的：LOD 代理层的时机

`src/lod/editor-lod.ts` 原来在 `scene.elementAdded` 之后**固定 400 ms** 就开建代理层：

```ts
setTimeout(() => { void generateForSplat(splat); }, 400);
```

而 `scene.elementAdded` 发生在导入过程中的"元素挂上场景"那一刻 ⇒ 那 400 ms 正好落在
**引擎打包的 11.8 s 冻结结束之后**。实测（`import-stall.cjs`，采样窗口延长到 resolve 之后 20 s）：

| 阶段 | 改前 | 改后 |
| --- | --- | --- |
| `import resolve` 之前的最长阻塞 | **11,716 ms** | 11,804 ms（引擎，未变） |
| resolve **之后**的最长阻塞 | **4,982 ms**（一段） | **3,824 ms + 1,327 ms**（两段） |
| 尾段起点 | 58.7 s（resolve 后 ~1.5 s） | 59.4 s |

改法两条：

1. **`editor-lod.ts`：等主线程真空下来再建** —— `requestIdleCallback(..., { timeout: 8000 })`
   （没有 rIC 时退回 4 s 定时器）。用户先拿到"能看能动"的模型，代理层随后补上。
2. **`lod.ts: buildLodAssets()`：逐层创建 + 每层之间让出一手宏任务** —— 代理层的打包同样是
   引擎在 `GSplatResource` 构造里同步做的，一次性建 2 层就是一段连续冻结；逐层让出后
   最长阻塞≈减半（实测 3,824 vs 4,982），进度条也真的能重绘。

**为什么要延长采样窗口**：`import-stall.cjs` 原来只采样到 `import resolve`，于是这 5.0 s 的尾巴
**一直被漏掉**（第十六轮报的"11.6 s"只是前半段）。这一轮把窗口延长到 resolve 后 20 s，
并把 >1 s 的阻塞按 `before-resolve` / `after-resolve` 归类 —— 这才是"导入到底卡多久"的完整口径。

## 4. 第二轮补记（同日）：让用户知道在等什么 —— 打包前先画一帧

上一节说"那 11.3 s 在引擎里、我们从外面动不了"。动不了耗时，但**动得了观感**：
原来那 11 s 里界面是一动不动的 spinner，用户既不知道在等什么，也不知道是不是卡死了。

改法（`src/app/asset-loader.ts`，`IMPORT_GPU_NOTICE_MIN = 5_000_000`，即 tier B/C 才提示）：

1. 进 `createGSplatAsset()`（= 引擎打包）**之前**，把进度条文案换成
   `popup.import-gpu-prepare`（新键，9 语言各 **698** 键）：
   `正在把 {{count}} 个高斯传给显卡（大模型这一步要几秒，期间窗口会无响应）…`
2. `paintBeforeBlocking()`：**等两帧**（第一帧只是入队、第二帧才保证上一次 DOM 改动真的 paint 过），
   并带 **250 ms 兜底** —— 浏览器里隐藏标签页的 rAF 可能永远不来，没有兜底会把导入挂死。

实测（`docs/probes/import-stall.cjs` 现在也记录 `progressStart/progressUpdate` 的时间戳）：

| 夹具 | 证据 |
| --- | --- |
| `test-20m-fill.ply`（2000 万行，tier B，不抽稀） | 提示在 **33,432 ms** 发出，主阻塞窗 **33,435 ms** 开始（10,192 ms）⇒ **提示早于阻塞**；随后 `Generating LOD…` 在 44,917 ms（LOD 已按上一节挪到冻结之后） |
| `1亿gs.ply`（6000 万行，抽稀路径） | 原来的**单块 11,716 ms 被拆成 1,212 ms（校验/净化）+ 10,557 ms（引擎打包）**，中间隔着一个心跳 tick —— 那一瞬就是画提示的那一帧；总耗时不变，没有回归 |

> 口径细节：`import-stall.cjs` 第一版把进度事件 `slice(0, 8)`，只截到抽稀阶段的 7 条，
> 把 30 多秒后的那条提示截掉了（假"没发出来"）。现在取**最后 10 条**。

## 5. 第三轮补记（同日）：把我们自己那一趟逐行扫描整个搬进 worker

§2 那张表里"用户建议不解决问题"说的是 `state`/`transform` 通道与上传；但**我们自己确实还有一趟
逐行主线程扫描**：`detectGiantGreySplats()`（巨型灰高斯检测，`asset-loader` 对用户导入的每个模型都会跑）
—— 它要全表扫两遍（一遍算场景对角线、一遍按三条规则计数），1.35 亿那档抽稀后 6000 万行实测
**约 1.2 s**，正好是阻塞窗口里紧挨着引擎打包前的那一段。

改法（三处）：

| 文件 | 改动 |
| --- | --- |
| `src/splat/splat-sanitize.ts` | 把判定抽成**纯函数** `detectGiantGreyFromColumns(columns, total)`（不依赖 `GSplatData`，所以 worker 也能用）；`detectGiantGreySplats()` 保留为同一实现的包装；顺手把 `Math.exp` 从判定链的**第一句挪到最后一句**（三个条件是与关系 ⇒ 语义不变，但巨型灰是极少数，绝大多数行在前两次绝对值比较就被否掉，省掉 ~99% 的 `exp`） |
| `src/workers/load-worker.ts` | 物化 + 重排之后，用同一批列顺手统计一遍，把 `giantSplat` 随结果回传（失败则给 `null`，不影响导入） |
| `src/app/asset-loader.ts` | 有 worker 报告就用它（`__GIANT_REPORT__.source === 'worker'`），否则回退自己扫（`source === 'main'`）；只有用户真选"移除/缩小"时才在主线程动数据 |

**实测**（`import-stall.cjs`，`1亿gs.ply`，预算后 6000 万行）：

| 量 | 改前 | 改后 |
| --- | --- | --- |
| 主线程最长阻塞 | 11,804 ms | **10,482 ms** |
| 阻塞窗口结构 | 1,212 ms（扫描）+ 10,557 ms（引擎打包） | **只剩一段 10,482 ms**（引擎打包） |
| 导入墙钟 | 57,416 ms | **55,373 ms** |
| 回退路径（worker 关） | — | 22,190 + 10,353 ms（自己扫，符合预期） |

⇒ 我们自己的逐行主线程工作到这一轮**清零**；剩下的 10.5 s 全是引擎的 GPU 打包（§2）。

**回归保护**：
- 新增纯函数套件 `docs/verify/verify-giant-detect.mts`（8 项）：与一份独立参考实现逐位对照
  （4 组数据）、`removable` 的 5% 阈值两侧、三个条件缺一不可、尺寸阈值 0.5% 对角线两侧、
  缺列时给安全空报告。
- `docs/verify/verify-import-worker.cjs` 增加一条：两条路径的 `{total, giantGrey, diag, removable}`
  必须一致，且 `source` 分别是 `worker` / `main`（实测 `{"total":2000,"giantGrey":0,"diag":2.3126…}`，
  两边逐位相同）。

## 6. 还没做 / 下一步

1. **引擎那 11.3 s 只能靠"少打行"或上游**：如果要继续压，建议的方向是
   把 tier C 的导入预算从"设备上限"改成"设备上限 × 可用内存余量"（需要与用户确认画质取舍）。
2. **草稿优先导入**（先 1500 万行立刻可用、空闲时再补全量）：能消掉"等 11 秒"的体感，
   但全量那 11.3 s 仍会发生（只是推迟到空闲时）—— 需要用户拍板。
3. `activated` 快路径：若把 `opacity`/`scale` 预先激活（在 worker 里算好）并置
   `gsplatData.activated = true`，引擎那 3 次 `Math.exp` 可以省掉（估计 0.5~1 s），
   但会改变全应用对这两列的语义（导出、数据面板、LOD 抽稀都按 log 空间处理），要先评估。
