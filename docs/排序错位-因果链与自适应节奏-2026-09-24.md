> 全网调研的结论在 `docs/排序错序-结构性解法-引擎GPU排序通路-2026-09-23.md` §7（含 30+ 条一手来源）。

## 1. 先量链条：一份顺序在屏幕上一共活了多久

新探针 `_tmp/probe-order-lifetime.cjs`（不入库，只读测量）包装四个东西，把"顺序新鲜度"拆开：

| 钩子 | 量的东西 |
| --- | --- |
| `sorter.worker.postMessage` | 派发时刻 + 派发时喂给 worker 的位姿 |
| `sorter.on('updated')` | worker 回包时刻 ⇒ **λ**（派发→回包，纯 worker 排序） |
| `sorter.applyPendingSorted` | **上线**时刻 ⇒ 回包→上线的等待（按需渲染下要等下一帧的 `update()`） |
| `requestAnimationFrame` | 每帧的真实转角 ⇒ 把这三种时间换算成"错位角" |

`D` = 派发间隔，`L` = 派发→上线，**一份顺序的寿命 D 整段都在用**，所以错位角 ≈ (D + L) × 角速度。

### 实测（30°/s 匀速旋转，4 秒，WebGPU）

| 模型 | 点数 | D p50 | λ p50 | 回包→上线 | 每份顺序活了 | 错位角 p50 / p95 |
| --- | --- | --- | --- | --- | --- | --- |
| `test-model.ply` | 2 000 | **100.1 ms** | **0.8 ms** | 16.7 ms | 6 帧 / 100 ms | **3.0° / 3.5°** |
| `test-layered.ply` | 600 000 | 116.5 ms | 3.8 ms | 55 ms | 2–3 帧 / 115 ms | 3.5° / 4.5° |
| `test-20m-fill.ply` | 20 000 000 | 188.8 ms | 149.2 ms | 50 ms | 3–4 帧 / 153 ms | 4.6° / 6.1° |

### 这张表说了一件很直接的事

* **小模型上排序只要 0.8 ms，而派发间隔是 100 ms。** 顺序新鲜度有 100 倍余量，
  却白送给了 `SORT_MIN_INTERVAL_MS = 100` 这条**为 2000 万点写的恒定地板**。
  那条地板当年的用途是"防止 worker 被请求淹没"，而现在这件事由**单飞**
  （`_sortInFlight` / 引擎 `jobsInFlight`）与引擎 worker 自己的 1e-3 门限兜着，
  恒定地板是多余的保险，代价却是 3° 的系统性错位 —— 正是用户说的"缓慢旋转也能看到翻转"。
* **600 万点以下 λ 都是毫秒级**（0.8 ms / 3.8 ms）。"排序太慢"这个直觉在小模型上是错的；
  慢的是**我们自己安排的节奏**。
* 只有 20M 那一档是真正的 worker 吞吐瓶颈（λ = 149 ms）—— 那一档本轮不动（见 §4）。

## 2. 这一轮改了什么：地板改成按实测代价自适应

```ts
// src/splat/splat.ts
const SORT_MIN_INTERVAL_FLOOR_MS = 16;   // 地板下限：一帧（60 Hz）
const SORT_MIN_INTERVAL_CEIL_MS = 100;   // 地板上限：原来那条恒定地板
const SORT_INTERVAL_COST_FACTOR = 1;     // 地板 = (λ + 消费) × 这个倍率

private _sortMinIntervalMs(tune = {}) {
    const cost = this._sortLatencyMs + this._sortConsumeMs;   // 都已经是实测滑动平均
    return clamp(SORT_MIN_INTERVAL_FLOOR_MS, SORT_MIN_INTERVAL_CEIL_MS, cost * factor);
}
```

三个调用点（`_sortAdmit`、`_sortPredictHorizon` 里的 D 估计、`_onSortUpdated` 里的补发）
**共用同一个函数** —— 这是本仓库记过的一条教训（"只修被点名的实例会漏掉整个家族"）。

* 小模型：λ+消费 ≈ 17 ms ⇒ 地板 = 16 ms（一帧）
* 中等模型：3.8 + 55 ⇒ 59 ms
* 20M：150 + 50 ⇒ 100 ms（被上限夹回原值，行为与从前一致）
* 换台更快的机器/更小的模型 ⇒ 自动更密，不需要任何按点数写死的阈值
* 调参口：`__SPLATROOM_SORT_TUNE__.minIntervalMs`（直接覆盖）/ `.intervalCostFactor`

### 实测效果（同一个探针、同一条转速）

| 模型 | D p50 | 每份顺序活了 | 错位角 p50 | 错位角 p95 |
| --- | --- | --- | --- | --- |
| `test-model`（2k） | 100.1 → **33.3 ms** | 6 帧 → **2 帧** | 3.0° → **1.0°** | 3.5° → **1.5°** |
| `test-layered`（600k） | 116.5 → **62.1 ms** | 2–3 帧 → **1 帧** | 3.5° → **1.9°** | 4.5° → **3.7°** |
| `test-20m-fill`（20M） | 188.8 → 192.6 ms | 3–4 帧 | 4.6° → 5.8° | 6.1° → 6.0° |

**2 帧就是这条通路的物理下限**：顺序必须"落地 → 下一帧 `GSplatInstance.update()` 上传 → 再渲染"，
所以 D ≥ 1 帧、L ≥ 1 帧。小模型已经打到底：**33.3 ms 恰好是 60 Hz 下的两帧**。

代价：派发次数 41 → 121 次/4 s（约 30 次/秒），每次多一帧的上传开销；
小模型上无感（帧时间 16.7 ms 不变），600k 上帧时间 54 ms 不变。

> 20M 那一档的 4.6° → 5.8° 不是回归：它的 λ 抖动大（145–168 ms），
> 而且地板被上限夹回 100 ms、行为与从前一致，两次测量差在噪声范围内（样本 24 次）。

## 3. 为什么"完美"还差一步

**这一轮压掉的是派发节奏，压不掉"帧序"本身。** CPU/worker 排序的物理链条是：

```
第 n 帧   : 相机 → 派发排序
第 n+1 帧 : worker 回包 → 引擎 update() 上传顺序（L 的下限 = 1 帧）
第 n+1/2 帧: 用这份顺序渲染
```

顺序对应的相机位姿**最早**也是 n 帧的，这就是 ≥2 帧的硬地板，任何门限/预测/调参都碰不到它。
**唯一能让顺序与绘制同帧的办法是让排序也发生在 GPU 上、和绘制同一帧内完成**
—— 引擎自己就有这条通路（unified 世界缓冲 + 自己的 GPU 基数排序 + indirect draw），
但我们的材质（曲线/裁剪/选区/状态贴图/特效全在 per-instance 材质里）接不上那条路。
这条路已单独立项：`docs/待办-引擎WebGPU-compute.md` 与
`docs/排序错序-结构性解法-引擎GPU排序通路-2026-09-23.md`（§2 架构、§7 调研结论）。

## 4. 现在的错位量级与它的观感

按 §2 之后的数字：小模型 **1°**、中模型 **2°**、20M **5–6°**（30°/s 匀速旋转时）。

作为对照：一条"平铺/分层"模型里，两个不同层的高斯要翻转前后顺序，
需要相机方向与它们连线的夹角变化到接近 90°；1° 的错位只可能让**本来就接近共面**的那些对翻过来，
所以小模型上剩下的应该是"擦边的地方偶尔闪一下"，而不是用户描述的"后面的内容翻到前面"。
**这条推断需要用用户的真实模型复验**（我们这边没有他的模型，也无法判断观感）。
