## 〇、按量级复查后的修订（**先读这一节**，两份详述见 `01-量级复查-bug.md` / `01-量级复查-perf.md`）

**量级口径**：T0a = 2000 点（`test-model.ply` 实测只有 2000，不是 10–20 万）；T0b = 12 万（`floater-scale-test.ply`）；
T1 = 93 万（`_tmp\scan.ply`）；T2 = 1300 万（用户 `选择工具\merged-scene.ply`）；T3 = 3000/5000 万（50M 在 WebGPU 上不可渲染）。
**每点成本不是常数**：T1 ≈ 8.6–11.8 ns/点，T2 ≈ 38.9–53.7 ns/点（退化 3.3–5.4×）——**不要用 T1×N 外推 T2**。

### 执行顺序（修订版）

1. **O1**（选区变更不要触发 GPU 包围盒 pass + `waitForGpuDrain` + 4 次同步回读）—— **全档必做，不加门槛**：
   T0a 推杆 22–32ms → **<1ms**、T0b −95%、T1 30–43ms → **8–11ms**；T2/T3 只 −2~9%，但它同时占着全局
   `commandQueue` 一整帧，所以大模型上也该做。（WebGPU 上这次 pass 的结果随后被 `splat.ts` 的 CPU AABB 覆盖 ⇒ 纯浪费。）
2. **O3**（去掉 `IndexRanges.fromPredicate` 的每索引闭包）—— **全档为正、无门槛**，T2 还省最坏 104MB 的 `number[]`。
3. **新发现的高危**：**全选 + 删除（`numSplats → 0`）⇒ 包围盒 ±1e6 ⇒ `near≈105` ⇒ 整个场景被近裁剪面切空**
   （WebGL2 无兜底，而默认后端就是 WebGL2 之外的场景也会中招）—— 见 `01-量级复查-bug.md` 第 13 条。
4. **环模式 UI 二选一（等用户拍板）**：①隐藏范围行（1 行、最稳）②让滑块作用在"表面层"上。
   现状 `26b99f7` 只是**止住了"静默翻转"**，滑块在环模式下变成了**完全失效的死 UI**，所以还没完。
5. **O2**（一趟按位更新，替掉 4 趟全扫 + 13MB 掩码）—— **门槛 ≥250 万点**：T2 506–699ms → **200–300ms**；小模型只白付回归成本。
6. **A1**（连通簇 `Map` → dense `Int32Array`、去浮云内存）—— 内存类改动无门槛；搬 worker + 簇按需算 **≥100 万点**。
7. **load worker 启用**（`__SPLATROOM_ENABLE_LOAD_WORKER__` 全仓无人设置 ⇒ 是死代码）—— T0 无感，**T2 就是那 15 秒**。
8. **A2**（导出/回退的 741MB 冗余拷贝）—— **≥500 万点**；T3 是 OOM 悬崖（叠加后 5–8GB）。
9. **O5 的正确用法**：交互路径节流在任何档都无意义（0.02ms/帧）；真收益在**导出** —— `render.ts` 的排序间隔常数 2
   → `max(2, ceil(n/1e6))`，13M 导出 150 → 23ms/帧（**≥300 万点**）。
10. **A3**（投影缓存 >2400 万点的悬崖）—— 量化到 6B/点 + 内存预算门槛（≤3200 万点）+ 超限给可见提示；
    13M 靠缓存省 ~900ms/次推杆，30M 被拒后**每次推杆多 1.95–2.34s**。
11. **着色器窗口判定**（最后手段）：T0/T1 净负、T2 边际（须先做 O2+O3 且回读异步）、T3 净正（省 1.9–2.3s）；
    它**替不掉**掩码→索引/状态回写/上传，仍要全量掩码回读；⚠️ **绝不能挂在 WebGPU 的 quad 路径上**（每顶点各算一次 ×6 = +240–360 ALU）。
    先做更便宜的替代：投影缓存量化到 6B/点。

### 只在小模型上暴露的问题（反向风险）

- 除 O1 外，全部优化在 T0a/T0b 合计省 **<0.05ms** —— 给小模型做这些只增加回归面；
- **环模式拾取 `readIds` 返回 `pw×ph` 的 JS 数组 + `Set`**：只与**屏幕分辨率**有关 —— 2000 点模型在 4K 上同样要分配
  **8.29M 元素**（0.5–1.0s），比 1080p 下的 1300 万点还慢；
- 手势 alpha 位图里的 `i % cw`（4K 每次 20–45ms）；2k 模型导 8K 视频**每帧同步回读 133MB**；
- `tailFractions` 的 `counted < 200` 退化 ⇒ **小框第一下推杆没反应**（四个档的小框都会中）；
- 后台/最小化时 `waitForGpuDrain` 走 500ms 兜底。

### 只有在 T3 才出现

投影缓存被拒（推杆 2–4s，"看起来没反应"）、floater 的 dense 阈值（8e6 格）在 ≈2100 万点越线退回 `Map`（8.1 亿次哈希）、
排序缓冲超 128MB（30M 仅剩 8MB 余量；50M 不可渲染 + 空视口 4s + **无降级路径**，且此时环模式每次框选都会清空选区、
快速填充退化成全选）、导入 35–60s 主线程冻结、每次手势 330MB 瞬时内存。

## 三、中低优先（排期用）

- 环模式仍白跑整条解析路径（`tailFractions` + 104MB 投影缓存 + 全量投影，结果随后被拾取覆盖后才丢弃）。
- 环模式拾取：`readIds` 返回 `pw×ph` 的 **JS number[]**（满屏可达 800 万元素），再建 `Set` + 13M 次 `Set.has` → 秒级卡顿 + 数百 MB 瞬时分配（这就是 V2 逻辑在大屏上的代价，**要按 V2 行为保留、但可以换成位图**）。
- 套索"点一下没画"的空手势以 `set` 提交 → 清空整个选区 + 一条无效撤销。
- `flush` 全量上传 13MB + recount 全表（见 O4）。
- 面板每次事件重写三行 + 每次 render 约 9–12 次强制布局；链式约束有两套实现（`range-slider.commit` vs `selection-flags.normalize`）。
- **轨道端点之后"值继续变、滑块不动"**（值域 -50..150 vs 窗口随芯厚变化）→ 面板与实际选区脱钩且无反馈。
- 对比工具 `estimateCellSize` 尺度错到让隔离判据恒不成立；对比工具每帧 52MB 掩码 + `getCenters()` 4×156MB。
- 破洞模式逐格插入排序最坏 O(k²)；导出/导入零并发守卫；`planar-fix` 字符串 key + 全主线程；`SplatsTransformOp.undo` 未命中静默写 0；地面/水域面板容差被算成整条对角线。
- **死代码**（已核实不可达）：`keepSurface` / `selectDepthBand` / `SURFACE_SHELL` / `RINGS_SURFACE_PCT` / `splat/selection-band.ts`；以及 `workers/load-worker.ts`（见高危 7）。

## 四、建议的动手顺序（如果只做三步）

1. **高危 2**（等你拍板：环模式滑块）—— 用户每天都在碰的地方。
2. **O1 + O3**（"最便宜的大头"）—— 不改语义、双后端套件就能回归，93 万点推杆预计 30–43ms → 15–22ms。
3. **高危 3 + 5**（`MultiOp.undo` 逆序、`water-detect` 列名）—— 各几行，但都属于"静默给错结果"。

之后再做 **O2 → A1 → 高危 7（load worker）→ A2**。
