## 二、性能：值得做的优化（含预期量级）

| # | 优化 | 预期收益 | 风险 |
| --- | --- | --- | --- |
| **O1** | **选区变更不要触发 GPU 包围盒 pass**：`SelectRangeOp.do()` → `updateState(selected)` → `updateLocalBounds()`，含 `waitForGpuDrain()`（= 一整帧）+ 4 次 `immediate` 回读 + JS 归约，**还占着全局 `commandQueue` 等**。而 `localBound` 只依赖 `deleted`（与 selected 无关），`selectionBound` 的唯一消费者是变换手柄枢轴 | 93 万点每次推杆省 ≥1 帧：**30–43ms → 15–22ms**；13M 每次省 100–300ms | 拖动期间 bound 短暂过期，必须在手势结束补算一次 |
| **O2** | **掩码→状态位压成一趟**：一条推杆现在 = 掩码(13MB 新分配) → `fromPredicate` 闭包全扫 → `clearBits×2 + setBits` 三次区间遍历 → flush 的 recount 全表；改成 op 直接持 `Uint8Array` + 同趟记 `[lo,hi]`，`SplatState.applyMask` 一次按位更新 + 增量维护 `numSelected`，掩码每 entry 复用 | 13M 每次 ~600ms → **150–250ms**（估算） | 必须保持 pre/post/applied 三快照语义（A1-7 修过的坑），用 `verify-selection-range`(24) + `verify-selection-depth-bar`(19) 双后端回归 |
| **O3** | **去掉"每索引一次闭包"**：`IndexRanges.fromPredicate` 先 push 进 JS `number[]` 再转 `Uint32Array` | 改动最小、风险最低、立竿见影 | 低 |
| **O4** | `recount()` 与全量状态上传按拖拽节奏降频（`dirtyLo/Hi` 已有却没用） | 拖动时省重复全表扫描 + 13MB 上传 | 低 |
| **O5** | 每帧强制 worker 排序 → 按排序耗时自适应节流 | 大场景帧率 | 中 |
| **A1** | **去浮云/连通簇算法**：`cluster-filter.ts:117` 的 `Map` 体素化 + 洪泛里每体素 26 次 `Map.get`（估算 7800 万次查询、4–10s）→ 照抄 `floater-removal.ts:345-347` 已有的 dense `Int32Array` 分支；`detectFloaters` 用单个线性格号 `Int32Array` 替掉 `cellX/cellY/cellZ`（**省 104MB**）+ `counts` 改 Uint16（省 26MB）+ 复用调用方已算的包围盒 | 簇过滤 **→ 亚秒~2s**；去浮云 **−30~50% 时间、峰值内存 −50%**；判据/阈值完全不变 | 中（算法等价性要回归） |

## 三、中低优先（排期用）

- 环模式仍白跑整条解析路径（`tailFractions` + 104MB 投影缓存 + 全量投影，结果随后被拾取覆盖后才丢弃）。
- 环模式拾取：`readIds` 返回 `pw×ph` 的 **JS number[]**（满屏可达 800 万元素），再建 `Set` + 13M 次 `Set.has` → 秒级卡顿 + 数百 MB 瞬时分配（这就是 V2 逻辑在大屏上的代价，**要按 V2 行为保留、但可以换成位图**）。
- 套索"点一下没画"的空手势以 `set` 提交 → 清空整个选区 + 一条无效撤销。
- `flush` 全量上传 13MB + recount 全表（见 O4）。
- 面板每次事件重写三行 + 每次 render 约 9–12 次强制布局；链式约束有两套实现（`range-slider.commit` vs `selection-flags.normalize`）。
- **轨道端点之后"值继续变、滑块不动"**（值域 -50..150 vs 窗口随芯厚变化）→ 面板与实际选区脱钩且无反馈。
- 对比工具 `estimateCellSize` 尺度错到让隔离判据恒不成立；对比工具每帧 52MB 掩码 + `getCenters()` 4×156MB。
- 破洞模式逐格插入排序最坏 O(k²)；导出/导入零并发守卫；`planar-fix` 字符串 key + 全主线程；`SplatsTransformOp.undo` 未命中静默写 0；地面/水域面板容差被算成整条对角线。
- **死代码**（已核实不可达）：`keepSurface` / `selectDepthBand` / `SURFACE_SHELL` / `RINGS_SURFACE_PCT` / `splat/selection-band.ts`；以及 `workers/load-worker.ts`（见高危 7）。

## 四、建议的动手顺序（如果只做三步）

1. **高危 2**（等你拍板：环模式滑块）—— 用户每天都在碰的地方。
2. **O1 + O3**（"最便宜的大头"）—— 不改语义、双后端套件就能回归，93 万点推杆预计 30–43ms → 15–22ms。
3. **高危 3 + 5**（`MultiOp.undo` 逆序、`water-detect` 列名）—— 各几行，但都属于"静默给错结果"。

之后再做 **O2 → A1 → 高危 7（load worker）→ A2**。
