## 0'''''''''. 本轮（3.16.0）：merged-scene（1300 万点）上的三条

用户用自己的 `选择工具\merged-scene.ply`（**13,007,105 点 / 695MB / binary PLY**，是之前 93 万点的
14 倍）报：1、从顶部框选中间的塔只选到塔身一半；2、上下左右推滑块有时候有反应有时候没有；
开头还有一句"还是有一些不顺滑"。

**量出来的**：

- 手势 **2003ms**、一次推杆 **840–1016ms**（尾巴分析在中途加了两趟全扫，13M 上等于 4 倍代价）；
- 相机定住后，默认范围下框内投影到的 12,147,085 点选中 **12,139,322（99.9%）** —— 范围逻辑没裁塔；
  "只选到一半"来自**上一次调过的滑块值还留着**（3.9.x 起的"范围跨手势保留"），把新框选裁掉一半；
- "有时有反应有时没有"来自 `tailBins` 里"尾巴已贴两端就退回线性"的守卫 —— 框画得紧时没压紧。

**改了三处**：

1. `runRangeSelection` 开头先清 `rangeGesture` 再 `events.fire('selection.resetRange')` —— **新的一次
   框选永远从整段穿透开始**（范围只属于"你正在微调的那一次"）；
2. `RangeProjectionCache`（sx/sy Int16 + dist Float32，8 字节/点）+ `selectRangeFromCache`：投影在手势
   那一次的全扫里顺手存好，之后推杆只比较窗口/深度/形状（>2400 万点自动退回逐点投影）；
3. 去掉 `tailBins` 的退化守卫 → 尾巴**无条件**压紧，第一下推杆响应恒定。

**实测**：手势 2003 → **774ms**；推杆 840–1016 → **556–721ms**；新框选不再被旧范围裁（99.9% 照选）；
93 万点上推杆仍是 **30–43ms**。**剩下的瓶颈**从投影转成了 `IndexRanges` + 状态回写 + 上传（都是 O(n)
的 JS），想再快要把窗口判定搬进着色器 —— 留作下一轮。
验证：`verify-selection-range.cjs` 24 项 0 失败（"预置范围作用于下一次手势"改成"新框选从整段穿透
开始"）；全量 32 套 + diag 7/7；`npm run check` 干净。

## 0'''''''. 上一轮（3.14.0）：深度轴压掉两端空尾巴 —— 第一次推杆就删掉 2% 的选区

用户：*"现在这个效果很好了……尤其是最近和最远两个滑块需要做特别的调整，逻辑就一个，我需要在首次
滑动滑块就能看到选区范围的变化，因此，尤其是最远的那个要快速进入视野内变化。"*

量出来的病根：深度轴 0..100 是按**包围盒**算的，而真实扫描的深度分布是"两端稀、中间挤"：

- 0–7.5% 只有 2,045 点、85–90% 挤了 63% 的点（85,934 + 149,895）、90–100% 又稀到 21,523 点；
- 于是 最远 100/99.5/99/98 分别删掉 **0/0/0/0** 个高斯，97 才删 3 个，90 删 1,471 个，
  然后 **90→85 一下删 198,773（53%）**；
- 最近同理：0/0.1/0.5/1/2/3 → 0/0/0/0/0/0，5 才开始动。

- **`depthTailFractions`**：按**本次手势框内**高斯的深度分布（512 桶直方图，一次 O(n)）找出两端各占
  `TAIL_SHARE = 2%` 的那一段，压进滑块行程的 `TAIL_PERCENT = 0.5%` 里（分段线性）；
  0/100 仍对应包围盒两端 → **没有东西够不着**，"默认整段穿透"语义不变；只有深度轴有
  （左右/上下是用户自己画的框，框边本来就在内容上）；
- 直方图每个手势算一次、存进 `RangeEntry.tails`，拖动时的实时重切照样便宜；
- 实测（打包版 + 真实鼠标 + 93 万点）：推 **最远 20px → 删 2,932（2.34%）**、40px → 4,379（3.49%）、
  80px → 26,193（20.87%）；推 **最近 20px → 删 2,793（2.23%）**；改前这两处都是 **0**；
  "90→85 一下 53%" 的断崖也没了；
- 坑：`depthTailFractions` 一开始忘了套模型变换（`selectRange` 是先 local→world 再算深度），每个
  高斯都落到直方图外、`counted = 0`，函数静默退回线性映射 —— 现在签名直接收 `view`；
- 验证：`verify-selection-range.cjs` 20 → **23 项 0 失败**（新增"第一小步必须真的删掉高斯"、
  "0/100 仍等于整段穿透"）；`depth-bar` 19 项 0 失败；全量 32 套 + diag 7/7；双后端 0 失败；
  `npm run check` 干净；打包版重置回 0/100 与 125,498、无控制台错误。

## 0''''''. 上一轮（3.13.0）：面板只剩两个钉死的推杆

用户三条：*"1、`----■------------■----`，只有这两个带字的滑块，不需要任何数值；2、两个滑块在固定
位置，在调整完成后释放鼠标，自动归到固定位置；3、越靠近视角，越精确；越远离视角，速度越快。"*

这是**推杆（jog）**，不是滑块：滑块不沿轨道走，是被"推"的。

- **一行只剩两个方块**（外柄细柄 + 两条扩边带从面板去掉），块里写字；
  **没有任何数字** —— 没有数字框、没有拖动读数，整行 `textContent` 的 digits 实测 **0**（扩边的
  **语义**还在 API / 选择逻辑里，`verify-selection-range` 20 项照旧通过）；
- **两块永远停在轨道 20% / 80%**：`span = (high-low)/0.6` → 任何厚度下选区带恒 **264px**、
  块宽恒 25px（实测厚度 100/40/0.2/0.1 四种状态完全一致）；
- **推杆手感**：`offset(dx) = sign(dx)·0.02·(|dx| + dx²/80)`。同一次按住：
  `0→20px 走 0.5`、`200→220px 走 2.5`（**快 5.0 倍**）；块 1:1 跟手（40px → 0.20→0.291），
  推过头停在轨道端点、值继续涨（440px→57.2、700px→136.5），不用松手重抓；
- **松手归位**：拖动期间比例尺冻结，松手按新选区重排 → 两块回到 20%/80%、值不丢；
- 修 bug：值域边界上（low 夹到 150）"至少一个步长"的兜底会把两端一起夹成 150、厚度变 0 →
  现在顶不动高端就收回低端（149.9/150），`selection-flags.normalize` 同样收口，滑块 commit 末尾
  再兜一次链式约束；
- 验证：`verify-selection-depth-bar.cjs` 重写 **19 项 0 失败**；双后端 0 失败；全量 32 套 + diag 7/7；
  `npm run check` 干净；`rangeHandleHint` 9 语言改文案，语言键 685 不变；
- 打包版端到端（3.13.0 exe / WebGPU / 93 万点）：面板 460×147、轨道 440、2 块 / 0 外柄 / 带 264px /
  行内 digits 0；厚度四档停靠一致；推到底 `0.5 / 2.5` 与公式一致；松手归位且值保留；
  重置回 0/100 与 56,828；无控制台错误。

## 0'''''. 上一轮（3.12.0）：拖动全程 1:1，尺度不再在手里变

用户：*"这个操作很麻烦，而且不直观，我其实不需要让人看到那个非线性变化的尺度，只需要简单的移动

  一个方向一直拖能走完全值域；平移不成回路（值只由指针位移决定）；
- **松手才重新贴合**：丢掉 `dragView`，两块回到 ≥126px；
- **芯不许塌成 0**：`MIN_THICKNESS = 0.1`（`range-slider` 链式约束 + `selection-flags.normalize`）——
  以前拖到 0 厚两块完全重叠、只有上面那个点得到、拖 80px 只挪 0.1，打不开；
- 实测（`verify-selection-depth-bar.cjs` 21 项 0 失败）：连续 8 步 ×22px 的增量

  0.2 厚的芯 600px 拖动值持续走 `49.9→50.9`（柄钉在 0.94、轨道在底下滑），
  拖 480px 压向另一块 → 厚度停在 **0.1**、间距 **126px**；
- 代价：拖动中厚度缩太多时两块会临时靠近，松手立刻重新贴合分开；极薄的芯每 0.1 要走 ~60px。
- 打包版端到端（3.12.0 exe / WebGPU / 93 万点）：`rect 40-60%` 31ms → 56,828；连续 8 步 ×22px

## 0. 上一轮（3.9.0）交付了什么：D 项（扩边/收边）长进三轴 —— 两柄变四柄

用户原话：*"接着做 D，但是不要单独做，在现有基础上优化，做成'----o近o-------o远o----'（o 代表滑块）。"*

- **每个轴四柄**：每端一对 = **外柄（扩边到哪）+ 内柄（现在选到哪）**，两柄之间那段（半透明橙）就是
  扩边多吃进来的部分；默认同心 = 与上一版逐位相同。
- **拖动规则**：拖内柄（收边）外柄跟着走；拖外柄往外 = 扩边；拖外柄越过内柄 = 扩边收到 0 再顶着内柄走。
  同心时外柄是画在内柄下面的**空心圆环（20px vs 12px）**，形成"靶心"，圆环边缘 4px 抓取带保证能抓到
  （坑：最初外柄 10px 被内柄完全盖住，鼠标永远拖不到它）。
- **语义修正（重要）**：旧版 2D 窗口只能裁不能扩（判定是 `区域 ∩ 窗口`，窗口 ⊆ 区域框）。现在
  **外柄窗口 = 选中范围**、**内柄窗口 = 形状（矩形/套索）仍生效的范围**，中间那圈扩边带按矩形加：
  `选中 = 在外柄窗口内 &&（在核心窗口内 → 还要满足绘制形状；在核心外 → 直接选中）`。
- **实测**（93 万点 / WebGPU / 同一手势实时重切）：拉框 40–60% 全轴默认 60 ms 选中 104,080；
  左右核心→45-55（收边）7,663（49 ms）；左右外柄→±50（扩边）156,996（52 ms）；
  上下外柄→±50 374,626（52 ms）；深度最远→50（收边）40,312（48 ms）；深度外柄→100（扩边）374,626；
  重置回 104,080。
- **验证**：`verify-selection-depth-bar.cjs` 16 项（四柄/三段填充、真实鼠标拖内柄与外柄、靶心圆环外缘抓取）、
  `verify-selection-range.cjs` 20 项（扩边是**真超集** 101→813、收边是**真子集** 101→1、深度扩边把后墙
  234 点带回来）；全量 32 套 + diag 0 失败；语言键 685（9 语言同步）。
- **打包版端到端**（3.9.0 exe / WebGPU / 93 万点 / 真实鼠标拖四类柄）：面板 352×147、三行各 4 柄、
  拉框 40–60% 34 ms 选中 56,828；左右内柄→45（收边）52,931；左右外柄→-50（扩边）59,920；
  上下外柄→150 69,749；深度内柄→50 7,319；重置回 56,828 且十二个数回默认；无控制台错误。

## 1. 上一轮（3.8.0）交付了什么：三轴双柄 range

用户原话：*"不用最近、最远单独设滑块，直接按照'最近-滑块1----滑块2-最远'这样来布局……可以做 3 个
'最近---最远'、'左---右'、'上---下'三个，分别对应深度、左右范围、上下范围。"*（3.9.0 已把每轴再扩成四柄，见第 0 节。）

- **新控件** `src/ui/range-slider.ts`：自建双柄 range（PCUI 只有单柄）。两柄之间用高亮色填充 = 选中的部分；
  拖柄 / 点轨道 / 方向键都能改；写入时 `updating` 守卫，`Number.isFinite` 兜底 NaN。
- **浮条** 改成竖排三行 + 重置：`#selection-range-bar`（标题「选区范围」），三行 = 最近|最远、左|右、上|下。
- **语义**：深度 = 占**模型**沿手势视轴深度范围的百分比；左右/上下 = 占**手势自己的选区框**的百分比；
