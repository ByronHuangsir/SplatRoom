**为什么能不改引擎就做到**（这一轮最关键的发现）：引擎的 `projCache` 本来就是按
「**splat 行号** × CACHE_STRIDE」寻址的，而顶点里的 `cacheIdx = sortedIndices[order]`
**就是该 splat 在数据里的行号**；状态贴图（`Splat.stateTexture`，R8 行主序）本来就在
两条通路之间共用。所以只要：① 顶点把 `cacheIdx` 用 flat varying 带给片元、
② 片元用 `textureLoad(srStateTex, texel)` 取样，就能在这条路上复刻主线的
"删除隐藏 / 选中染色 / 锁定相乘 / 删除但显示染淡红"。**不需要新资源、不需要改 bind group、
不需要 user varyings 通路**（那条路原本是计划中的做法，现在证明是多余的）。

**中性不变**：没有任何选中/删除时状态字节全 0，整段不生效 —— 同一张图与改动前**逐位相同**
（探针 52 里 unified 的 `0-导入后` 仍是 `[112.9,56.5,65.6]`）。全部代码都在
`?unified=1` 之内，主线零改动。

**两个自己踩的坑（都记下来）**：
1. **WGSL 不能写 `half4(mix(...), srClr.w)`**（`half4(vec3<f32>, f32)` 没有构造函数）⇒
   管线无效 ⇒ **整帧零图元、画面全黑且不抛异常**。是 `docs/probes/probe-wgsl-error.cjs`
   一眼指出来的（这条探针值回票价）。
2. **`@rollup/plugin-typescript` 默认把诊断当警告**：着色器注释里出现反引号 ⇒ 模板串被截断 ⇒
   构建"看起来绿"、`dist/` 留的是**上一次的旧 bundle** ⇒ 我改了代码却一直看到同一个错误，
   白查两轮。已给 `rollup.config.mjs` 的 typescript 插件加 `noEmitOnError: true`，这类失败
   现在直接以非零退出码失败。

**已知残余差异**（同向但不等值，记录在案）：框选一半时主线黄像素 16.46%、unified 10.14% ——
主线那部分高亮里还叠了**轮廓/选区覆盖层**（RT1 → outline 通道），这条路目前只做 per-splat 染色；
多模型场景下这条材质是按 layer 的，现在只反映"最后一个" splat 的状态（与调色参数同一处已知边界）。

### 再追加（同夜）：**根因找到并修好了 —— unified 通路的 splat 第一次真的画出来了**

用户选择"留在仓库里继续钻引擎 compute 内部"。于是从链尾往链头逐级读中间量，结论是：

1. **中间那一整条 compute 链全是好的**：用"裸 compute 把引擎自己的 buffer 抄进可读 buffer"读到

2. 真正的第一个 0 在**最前面**：引擎只在 `GSplatWorld.markSorted()` 里、且条件是

   `comp.unified` 翻成 true**，那一刻它早已 `sortedBefore = true` ⇒ **首传被永久跳过**，
   之后每帧只走增量路径（上传 0 块）⇒ 数据贴图全空 ⇒ 投影器把每个 splat 都判无效
   （实测 `renderCounter = 0`）⇒ `ProjectorWriteIndirectArgs` 把 `numSplatsBuf[0]` 与间接绘制参数
   写成 0 ⇒ **零图元**。整条链**不报任何错**，这就是它藏这么久的原因。
3. **修复（已入库）**：`src/splat/unified-material.ts` 新增 `ensureUnifiedWorkBuffer()`，
   在渲染前钩子里对每个 GPU-排序 world 做一次 `world.invalidate({ workBuffer: true })`

### 本轮（2026-09-24）做了什么：把"顺序错位"的因果链量出来并压掉派发那一段

| # | 事项 | 结果 |
| --- | --- | --- |
| ① | **量出完整链条**（新探针 `_tmp/probe-order-lifetime.cjs`：包装派发/回包/上线/帧，把三种时间换算成错位角）| 小模型（2 000 点）：派发间隔 **D=100 ms**，而 worker 排序只要 **λ=0.8 ms** ⇒ 顺序新鲜度白送 100 倍；600k：D=116 ms / λ=3.8 ms；20M：D=189 ms / λ=149 ms（只有这一档是真正的吞吐瓶颈）。**一份顺序活 6 帧 / 100 ms = 3.0° 系统错位**，正是用户看到的"翻转" |

**两条重要教训（写进文档）**：
1. **`disp` 是拿错尺子量补偿**：它衡量"当前顺序表 vs **当前**相机位姿"，而补偿的目的正是让顺序对齐到
   **这份顺序真正上场的那一帧**。补偿越准，`disp` 反而越"差"（实测 6°/帧 下 不补 0.003 / 补偿 0.15，
   画面观感正好相反）。评判补偿只能用"顺序对齐到显示位姿后的残差"或画面指标。
2. **恒定地板是给小模型白送的税**：为 2000 万点写的防淹没保险，在 2 000 点上变成了唯一的约束。
   凡是"按最大场景定一个常数"的地方，都值得回头问一句"小场景能不能自适应"。

**还没做的（已立项）**：**引擎 unified GPU 排序通路**（顺序与绘制同帧 ⇒ 连那 2 帧地板都没有），
但需要把我们的材质（状态贴图/变换调色板/曲线/裁剪/选区/特效）整体迁到 `workBufferModifier` +
`GSplatVaryings` 那套挂钩上 —— 见 `docs/待办-引擎WebGPU-compute.md` 与
`docs/排序错序-结构性解法-引擎GPU排序通路-2026-09-23.md` §2/§7。

**第三轮补记（2026-09-21）**：用户报「**移动、缩放时画面会收缩到左下角，在上部、右部产生黑色空间**」——
**是我引入的回归**。根因：`src/shaders/blit-shader.ts` 的 final blit 是**逐 texel 1:1 拷贝**

**改法**（**不碰 splat-transform 本身，只在它之上包一层**；全部在 `src/splat/splat-serialize.ts`）：

1. **`buildViewerTemplate()` / `getViewerTemplate()`** —— 用一个"1 个高斯点"的假 `DataTable`
   （`Column` / `DataTable` / `Transform`，14 列）调一次 `writeHtml(bundle: false)`，取回 viewer 的
   html / css / js（模板与数据无关，取一次缓存住；失败则整体退回官方 writer）。
   取模板时把进度 renderer 临时换成 **`silentRenderer`**（新增的 `setProgressRenderer` /
   `activeProgressRenderer` 就是为它加的）。
2. **`renderViewerDocument()`** —— 按 `renderViewerHtml` 的**同一批接缝**
   （`SEAM_STYLESHEET` / `SEAM_MODULE_IMPORT` / `SEAM_BOOTSTRAP`，以及上游那两条安全检查
   `</style`、`</script|<!--|<script`）内联 css / js；`contentUrl` 先写占位符 `VIEWER_PLACEHOLDER`，
   再用 `indexOfBytes` **按字节定位、原地替换** ⇒ HTML 其余字节与旧路径**逐字节相同**。
3. **`Base64RelayWriter` + `Base64RelayFileSystem`** —— `.sog` 仍由 `writeSource` 的 `sog-bundle`
   分支（`writeExportSog`，流式、不 materialize）产出，**边产出边 base64 直接写进同一个 HTML 输出流**。
   块大小 **`BASE64_INPUT_CHUNK = 3 * 4 * 1024 * 1024`（12 MiB）**，编码走原生 `btoa` +

4. **`writePackagedViewer()`** —— 打包（zip）同样处理：`.sog` 直接流式写进 zip 条目，不再先过一遍
   `MemoryFileSystem`；viewer 的 css / js / settings / html 用模板里取回的**原条目名**
   （`tpl.sogName` / `cssName` / `jsName` / `settingsName` / `htmlName`）写进去。
5. **出口**：`useViewerStream()` 读 `window.__SPLATROOM_VIEWER_STREAM__`（**`= false` 退回官方
   bundle writer**，现场排查不用重新打包）；模板接缝对不上时返回 false 自动退回并 `console.warn`。
6. **顺带修掉一个真 bug**：没给 `experienceSettings` 时官方 writer 会兜底用库里的
   `defaultSettings('object')`，我们原来会**漏掉 settings**（导出的 HTML 会去找同目录的 `settings.json`，
   单文件场景必然拿不到）—— 现在两处都改成 `?? defaultSettings('object')`
