## 0. 第十四轮：分通道 + 两条"值通路"的镜像

### 0.1 分通道（纹理从 33×1 变 33×4）

- 纹理：`Splat.curveTexture` 改成 **33×4 的 R32F**，行 0 = RGB 主曲线，行 1/2/3 = R/G/B
  （`CURVE_CHANNELS` 的顺序就是行号，着色器里的 `ch` 直接用它）；
- **施加顺序 = 先主曲线、再各自通道**（Lightroom 语义）：`out.r = f_red(f_master(in.r))`。
  GLSL 与 WGSL 各 6 次查表（3 次主 + 3 次通道），CPU 镜像 `applyCurveSetToRGB()` 同序；
- 状态：`Splat.setCurves({ master, red, green, blue })` + `Splat.curves`（控制点）+ `Splat.curveTables`
  （33×4 采样表，**全恒等时为 `null`** ⇒ `uCurveEnabled = 0` 整段跳过，画面零改动）；
  `setCurvePoints()` 保留为"只设主曲线"的快捷入口（探针/脚本用）；
- 面板：曲线分类加了 **RGB / 红 / 绿 / 蓝** 四个通道页签（复用 `.hsl-tab`），
  切换页签时编辑器装载对应通道的控制点；分类复位按钮清空**全部**通道；
- 撤销：`ColorAdjustment.curves`（`undefined` = 不碰、`null` = 清空）；
- 持久化：`.ssproj` 存 `curves: { master: [[x,y],…], red: …, green: …, blue: … }`（各通道可为 `null`），
  旧文档没有该字段 ⇒ 保持恒等；变更 hash 用 NaN 分隔各通道，避免跨通道撞 hash；
- 9 语言新增 4 个通道页签文案（各 **695** 键）。

### 0.2 直方图 / 范围选择的曲线镜像（这是本轮真正的"缺口修补"）

用户看到的画面已经变了，但筛选还按曲线前的颜色算。修法：

  `cgCurve`（33×4 纹理）+ `cgCurveEnabled`，并在 `applyColorGrade()` 里按
  **scale/offset → 主曲线 → 各通道曲线 → 饱和度** 的顺序施加（与顶点着色器、CPU 镜像同序）；
- `calc-histogram.ts` / `select-by-range.ts` 各把 `cgCurve: splat.curveTexture` 与
  `cgCurveEnabled: splat.curveTables ? 1 : 0` 喂进 `values`（这两条通路本来就是靠

## 1. 已经做完的（可以立刻验证）

### 1.1 模型与采样（`src/core/color-curves.ts`，纯函数）

- `CURVE_SAMPLES = 33`（0 与 1 都是采样点，32 段，每段 1/32）；
- `sampleCurve(points)`：控制点 → 33 点采样表，**单调保形三次插值（Fritsch–Carlson）**。
  为什么不用 Catmull-Rom：普通三次样条会过冲（暗部出现负值、亮部冲出去），
  摄影曲线的手感是"拉中间点不把两端甩出去"，单调插值保证不产生新的极值。
- `isIdentityCurve` / `identityCurveSamples` / `evaluateCurveAt`（CPU 求值，与着色器同一套线性插值）/
  `applyCurveToRGB`。
- 边界行为：控制点夹到 `[0,1]`、重复 x 取最后一个、NaN 原样透传、±∞ 夹到两端。

### 1.2 着色器（GLSL 与 WGSL 各一份，插在顶点分级之后）

```
color = color * clrScale + vec4(clrOffset, 0.0);      // 原有：白场/黑场/亮度/色温
if (uCurveEnabled > 0.5) { color = applyCurve(color); } // 新增：33 点 LUT 线性插值
```

- 曲线表是一张 **33×1 R32F 纹理**（`Splat.curveTexture`），
  GLSL 用 `texelFetch(uCurve, ivec2(i,0), 0).r`、WGSL 用 `textureLoad(uCurve, vec2i(i,0), 0).r`；
- 插在**顶点阶段**（`splat-shader.ts:305` 之后 / `splat-shader-wgsl.ts:333` 之后）：
  这个 fork 的顶点 chunk 本来就有纹理先例（`splatState` / `splatTransform` / `transformPalette`），
  片元 chunk 目前**一个 sampler 都没有**，第一次往片元里塞纹理的风险更大；
- **默认零改动**：`uCurveEnabled = 0` 时整段跳过，且 `setCurve(null)` 与"设了一条恒等曲线"
  等价（`isIdentityCurve` 短路）⇒ 不设曲线时画面与"没有这个功能"**逐像素一致**（实测最大差 0）。

### 1.3 材质接线（`src/splat/splat.ts`）

- `Splat.setCurve(samples: Float32Array | null)`：写纹理（`lock/unlock`）+ 发 `splat.curve` 事件；
- `Splat.curve` getter：给导出镜像读；
- `onPreRender` 里按 `_colorGradeEnabled` 推 `uCurveEnabled`（调色整体关掉时曲线也一起关）；
- 曲线纹理在 `rebuildMaterial` 里绑定一次。

### 1.4 CPU 导出镜像（`src/core/color-grade.ts`）

`ColorGrade` 的 `apply()` 在 scale/offset 之后、饱和度之前施加同一条曲线（`evaluateCurveAt`），
并且**把曲线算进 `hasTint`** —— 这一条很关键：不算进去的话
`splat-serialize.ts` 的 `if (!keepColorTint && (grade.hasTint || grade.hasHsl))` 会跳过烘焙，
导出图与视口不一致。

### 1.5 验证

- `docs/verify/verify-color-curves.mts`（**11 项**，纯 node）：恒等、端点固定、单调不过冲、
  抬亮/压暗中点方向、恒定曲线（抬黑）、越界与重复 x、**`evaluateCurveAt` 与独立重写的着色器查找
  逐位一致（最大差 0.00e+0）**、NaN/∞ 行为、恒等表是 no-op、逐通道施加。
- `docs/verify/verify-color-curve.cjs`（**8 项**，真浏览器，双后端 0 失败）：

  抬亮曲线 meanLum 0.4197 → 0.6234（+0.2037）且开关变 1 / 压暗曲线 → 0.2801（−0.1396）/
  S 曲线改变分布形状（展布 0.0333 → 0.0350，低端相对中位数被压 0.0294 → 0.0328）/

### 每题一个坑（探查得到，别踩）

1. **`hasTint` 是 `readonly` 且构造时冻结** —— 曲线必须并进去，否则 `.ply/.sog` 导出会跳过烘焙。
   （第十二轮已改好。）
2. **着色器里只能插一次**：片元的调用序列是 `highlights → shadows → contrast → HSL`，
   顶点是 `clrScale/offset → 主曲线 → 各通道曲线`。四份数学（GLSL/WGSL 顶点、CPU 镜像、
   值通路）的**顺序必须完全一致** —— 现在都是"先主后通道"。
3. **`propMode` 必须用颜色模式**（5..7 / 18..20）才经过 `applyColorGrade`；`1` 是位置。
4. **直方图柱是 [min,max] 归一化的** ⇒ 不要用柱形/重心判定"曲线有没有生效"，要看 min/max 或扫档位。
5. **分组渲染恒为中性**（`src/splat/group-renderer.ts:611-624`）。
6. **`.ssproj` 没有 schema 校验**（只有 `version: 1`），新字段必须按"可选 + 默认"读
   （`curves` 就是这么读的：`Array.isArray(raw) && raw.length >= 2` 才生效）。
7. **`new Container({ class: 'a b' })` 会抛**（整串被当成一个 token）⇒ 多类名要 `class.add()`；
   这个坑会让**整个应用起不来**，表现是探针 `window.scene` 超时。
8. **新分类加在面板底部要先滚进可视区**：面板在第十二轮改成可滚动，
   套件里驱动这类控件必须先 `scrollIntoView({block:'center'})`，否则真实鼠标事件打不到它。

### 为什么先做引擎再做 UI（而不是反过来）

四份数学（GLSL/WGSL 顶点 + CPU、值通路）里最容易出错的是**采样与插值、以及组合顺序**，
而它只有一份实现且被 33 项断言钉住（15 项纯函数 + 18 项像素/UI），
UI 只是"控制点 → 33 点表"的编辑器 —— 先钉住数学，接 UI 与分通道的回归面就很小。

## 3. 第十七轮：把剩下的两处补完（`.sscg` 侧车 + 分组渲染中性）

### 3.1 `.sscg` 侧车原来把曲线整个丢掉

`serializeGrade()` 逐个字段抄了调色参数（色调/色温/饱和度/亮度/黑场/白场/对比度/HSL…），
**唯独没有曲线** —— 于是"存了调色 → 读回来"曲线消失，而 `.ssproj` 早就存了。
这类"新字段忘了加进序列化"的坑和 HSL（v3 → v4）一次一模一样。

### 3.2 分组渲染的中性分支要**显式**关掉曲线

`src/splat/group-renderer.ts` 的合并材质把调色项逐个写成中性（`clrScale/clrOffset/饱和/HSL…`），
但**没有写 `uCurveEnabled`**。合并实体是一次 draw、来源多份、每份曲线各不同 ⇒ 只能不施加；
问题是"没写"和"写了 0"在着色器里不是一回事：`uCurveEnabled` 一旦非 0，片元就会去采样
`uCurve` 纹理，而**合并材质根本没有绑定那张纹理**（未绑定采样在 WGSL/GLSL 上都是未定义行为）。
本轮显式写 `uCurveEnabled = 0` 并写清理由，避免以后有人把 splat 的 uniform 抄过来时踩雷。

### 3.3 顺手修掉一条"空过"的检查

`docs/verify/verify-tone-range.cjs` 里那两条"直方图/范围选择不炸"的检查用的是
`calcHistogram(splat, 1)` / `selectByRange(splat, 1, …)`，而 **`propMode = 1` 是 `worldPos.y`（坐标），
根本不经过 `applyColorGrade`**（HANDOFF 53）—— 它只证明了"不崩"，没证明调色走到了这条通路。
改成颜色模式 **5（最终颜色 R）** 并新增一条判据：

```
最终颜色 R 范围：退化档(黑场=白场=1) -14.000..-2.002  vs  正常档(黑场 0.5) -0.400..0.800
```

⇒ 黑场/白场确实作用在这条通路上（退化档被 `MIN_TONE_RANGE` 兜到 0.05 后整段压黑，值域为负是"全黑"的表现）。
