# 调色"黑场拉到底变过曝"排查与修复（2026-09-21）

用户报：**调色模块里把"黑场"拉到底，画面不但没变黑，反而整体过曝（冲成一片白）**，
怀疑这些数值范围的参数有问题。结论：**三处数值范围缺陷叠加**，另外顺手查出并修掉了一个
**颜色面板行重叠导致"黑场"这一行根本拖不动**的布局缺陷。

复现/验证用探针：`docs/probes/grade-blackpoint.cjs`（含黑场 / 白场两端的滑块扫描）；
回归套件：`docs/verify/verify-tone-range.cjs`（10 项，双后端 0 失败）。

---

## 1. 用户看到的现象，量出来的数字

`grade-blackpoint.cjs` 直接把黑场滑块扫一遍（滑块反向映射 `blackPoint = -blackSlider`），
读**真实视口材质**的 `clrScale` / `clrOffset`，再抓画布统计平均亮度 / 冲白像素比例：

| 黑场滑块 | 有效黑场 | 有效白场 | 范围 | `clrScale` | `clrOffset` | 平均亮度 | 冲白像素 |
|---|---|---|---|---|---|---|---|
| 0 | 0 | 1 | 1.00 | 1 | 0 | 0.420 | 0.00% |
| −0.5 | 0.5 | 1 | 0.50 | 2 | −1 | 0.164 | 0.00% |
| −0.9 | 0.9 | 1 | 0.10 | 10 | −0.9 | 0.994 | **98.8%** |
| −0.99 | 0.99 | 1 | 0.01 | 100 | −0.99 | 0.994 | **98.9%** |
| **−1** | **1** | **1** | **0.00** | **1000** | **−1** | **0.994** | **98.9%** |

注意滑块 −0.5 那一行**已经**能看出问题了：范围 0.5 时正常做法应该压黑
（`meanLum` 应 ≤ 0.42），实测反而是亮的；到 −0.9 直接冲到 0.994。
这正是"越压越亮、拉到底就过曝"的来历，而且是**三个缺陷叠加**：

### 缺陷 ① UI 护栏允许"范围 = 0"这个退化值

参数语义是**层级（levels）区间** `blackPoint` .. `whitePoint`，映射必须按"区间"算。
UI 两个滑块是反向的：

```ts
splat.blackPoint = -blackSlider;    // 滑块 −1..1
splat.whitePoint = 2 - whiteSlider; // 滑块  0..2
```

旧护栏（`src/ui/color-panel.ts`）只保证 `whitePoint - blackPoint >= 0`，**等号可达**：
默认白场滑块 = 1（白场 1.0）时，把黑场滑块拉到 −1 ⇒ 黑场 1.0 = 白场 1.0 ⇒ **范围 0**。
而视口那条公式是

```ts
const denom = Math.max(0.001, whitePoint - blackPoint); // 范围 0 时缩到 0.001
```

⇒ `scale = 1000`，`(color - lo) * 1000` 把整幅画面推到饱和 ⇒ 冲白 98.9%。

### 缺陷 ② `offset` 没乘 `scale`（这才是"中间调整体变亮"的主因）

正确的层级映射是 `out = (in - lo) / (hi - lo) = in * scale + (-lo * scale)`，
即 `offset = -lo * scale`。旧代码写的是 `offset = -lo`：

| 范围 | 正确 offset | 旧代码 offset | 结果 |
|---|---|---|---|
| 1.0 | 0 | 0 | 正常 |
| 0.5 | −1 | −0.5 | 中间调被**抬亮**一倍 |
| 0.1 | −9 | −0.9 | 几乎全白 |

所以用户看到的不是"范围退化造成的偶发 bug"，而是**只要范围 ≠ 1 就一路变亮**。
导出通路（`src/core/color-grade.ts`）里还有第三种写法
（有序化区间 + `max(0.001, hi-lo)` + `-lo`），于是**视口与导出在同一组参数下结果不一致**：
交叉参数（黑场 1.2 / 白场 0.8）时视口读 `scale=1000`、导出读 `2.5`。

### 缺陷 ③ 直方图 / 范围选择里是裸的除法

`src/data-processor/calc-histogram.ts`、`src/data-processor/select-by-range.ts` 直接写
`1 / (whitePoint - blackPoint)`：范围 0 ⇒ `Infinity`，交叉 ⇒ 负数。
这两条是 GPU shader 常量，拿到 Inf/NaN 后直方图与"按范围选择"都会失效（表现是选择结果乱掉，
不一定是崩溃，所以一直没被发现）。

## 2. 修法：把"区间"这件事收进一个模块

新增 `src/core/tone-range.ts`（唯一真源，四处调用点全部换成它）：

```ts
export const MIN_TONE_RANGE = 0.05;

export const toneRange = (blackPoint: number, whitePoint: number) => {
    const bp = Number.isFinite(blackPoint) ? blackPoint : 0;
    const wp = Number.isFinite(whitePoint) ? whitePoint : 1;
    const lo = Math.min(bp, wp);          // 有序：交叉参数也按区间处理
    const hi = Math.max(bp, wp);
    const range = Math.max(MIN_TONE_RANGE, hi - lo);
    const scale = 1 / range;
    return { lo, hi, range, scale, offsetBase: -lo * scale };
};
```

- `src/splat/splat.ts`（视口材质）：`scale = tone.scale`、`offset = tone.offsetBase + brightness`；
- `src/core/color-grade.ts`（导出/离屏）：同上（视口与导出从此同一套公式）；
- `src/data-processor/select-by-range.ts`、`src/data-processor/calc-histogram.ts`：`cgInvRange = tone.scale`、`cgOffset = tone.offsetBase + brightness`；
- `src/ui/color-panel.ts` 护栏改成 `whiteSlider - blackSlider <= 2 - MIN_TONE_RANGE`
  （在"差 2"的边界上留出 `MIN_TONE_RANGE`），两个滑块互相联动。

**为什么是 0.05**：`scale` 上界 `1 / 0.05 = 20`，即最狠也只能把 5% 的亮度区间拉满，
画面会**压成纯黑**而不是过曝；同时比 0.05 更小的区间在 8bit 输出上已经没有可用信息。
另外这个"不对称"是故意的：黑场拉到底是压黑（用户要的），白场拉到底是冲白（同样合理）。

## 3. 修完的实测

`grade-blackpoint.cjs`（webgpu，20 万点测试模型）：

| 黑场滑块 | 范围 | `scale` | `offset` | 平均亮度 | 冲白 | 纯黑 |
|---|---|---|---|---|---|---|
| 0 | 1.00 | 1.00 | 0.00 | 0.420 | 0.00% | 0.00% |
| −0.25 | 0.75 | 1.33 | −0.33 | 0.229 | 0.00% | 0.00% |
| −0.5 | 0.50 | 2.00 | −1.00 | 0.164 | 0.00% | 0.00% |
| −0.75 | 0.25 | 4.00 | −3.00 | 0.125 | 0.00% | 0.00% |
| −0.9 | 0.10 | 10.0 | −9.00 | 0.008 | 0.00% | 96.2% |
| **−1（UI 极限）** | **0.05** | **20.0** | **−20.0** | **0.008** | **0.00%** | **96.2%** |

- 平均亮度**单调下降**，全程 0% 冲白；
- 交叉参数（黑场 1.2 / 白场 0.8）：视口与导出都是 `scale=2.5 / offset=−2`，不再打架；
- UI 滑块"到底"的位置现在停在 `range = 0.05`（白场滑块被护栏自动抬到 0.95 ⇒ 白场 1.05），
  `scale = 20`，实测**真实鼠标拖拽**得到同一组数字。

### 3b. 另一端（白场滑块拉到底）也量了一遍

用户报的是黑场，但同一套公式的另一端必须一起确认，否则下次就会收到"白场拉到底全白"的报告。
白场滑块往上推（白场值往下走）的实测（webgpu / 20 万点）：

| 白场滑块 | 黑场滑块（护栏联动） | 有效黑场 | 有效白场 | 范围 | `scale` | `offset` | 平均亮度 | 冲白 | 纯黑 |
|---|---|---|---|---|---|---|---|---|---|
| 1（默认） | 0 | 0 | 1.00 | 1.00 | 1.00 | 0 | 0.420 | 0.00% | 0.01% |
| 1.25 | 0 | 0 | 0.75 | 0.75 | 1.33 | 0 | 0.526 | 0.00% | 0.01% |
| 1.5 | 0 | 0 | 0.50 | 0.50 | 2.00 | 0 | 0.687 | 0.00% | 0.01% |
| 1.75 | 0 | 0 | 0.25 | 0.25 | 4.00 | 0 | 0.993 | 98.46% | 0.01% |
| 1.95 | 0 | 0 | 0.05 | 0.05 | 20.0 | 0 | 0.994 | 98.92% | 0.01% |
| **2（到底）** | **0.05** | **−0.05** | **0** | **0.05** | **20.0** | **+1.0** | 0.994 | 98.92% | 0.01% |

结论：**这一端冲白是设计语义**（白场 = 0.25 就是"亮度 ≥ 0.25 全部算纯白"，与任何层级工具一致），
要点在于它同样**有界**（`scale` 封顶 20、`offset` 仍 = `-lo*scale`，没有 Inf/NaN）且**单调**
（0.420 → 0.994，不会中途反向）。套件里这条也成了断言（第 4 项）。

**为什么两端不对称是故意的**：黑场到底 ⇒ 压黑（用户要的）；白场到底 ⇒ 冲白（同样合理）。
真正要防的是"越压越亮/范围 0 ⇒ scale 1000"那种**非单调、无界**的行为。

## 4. 顺手查出的缺陷：颜色面板行重叠，"黑场"这一行拖不动

写回归套件时发现"在标签上横向拖拽微调"这条交互在无头浏览器里**怎么拖都不动数值**，
一路查下去是面板布局的问题（`docs/probes/grade-blackpoint.cjs` 之外的 DOM 体检）：

- `#color-panel { max-height: 90vh; overflow: hidden }`，而 `.color-panel-category` /
  `.color-panel-category-content` 都是 flex 子项、**默认可收缩**；
- 1280×800 窗口下（90vh = 720px，内容需要 935px）分区被压扁：
  tone 分区的 `category-content` 是 `clientH=164 / scrollH=220`，
  **"黑场"行底部溢出自己分区 56px**（"洋红"行溢出 84px），行与行之间还相互重叠 16px；
- 溢出部分落在**下一个分区容器**的范围内，而下一个分区在 DOM 里更靠后 ⇒ 它盖在上面：
  `document.elementFromPoint(标签中心)` 返回的是 `color-panel-category-content`（别的分区），
  不是标签本身 ⇒ 指针事件根本到不了标签 ⇒ **这一行既拖不动、也点不到**（滑块同理）。
  实测 `document.body.style.cursor` 在 `pointerdown` 后仍然是空字符串（正常应是 `ew-resize`）。

修法（`src/ui/scss/color-panel.scss`，只动三处）：

```scss
#color-panel {
    overflow-x: hidden;
    overflow-y: auto;   // 原来是 overflow: hidden —— 装不下就滚动，而不是把分区压扁

    .color-panel-category { flex: 0 0 auto; }          // 新增：分区不收缩
    .color-panel-category-content { flex: 0 0 auto; }  // 新增：内容不收缩
}
```

修完：1280×800 下**没有任何行溢出分区**（`overflowing rows: none`），
面板 `clientH/scrollH = 720/935`（超出部分改为内部滚动），
`elementFromPoint` 命中 `label "黑场"`，真实鼠标拖拽把黑场拉到极限并拿到 `range=0.05 / scale=20`。
回归套件里这两条都成了硬断言（`color panel layout: …`）。

## 5. 回归

`docs/verify/verify-tone-range.cjs`（**10 项**，webgpu / webgl2 均 0 失败）：

1. 沿黑场扫一遍：平均亮度单调下降、全程不冲白（改前尾部 0.994 / 98.9% 冲白）；
2. 黑场到极限是**压黑**：`black=96.17% blown=0%`；
3. `scale` 有界（≤ 20）且 `offset == -lo*scale`；
4. 另一端（白场到底）：平均亮度单调上升、`scale` 有界、`offset` 仍 = `-lo*scale`（冲白是设计语义）；
5. 退化区间（`blackPoint == whitePoint`，UI 够不到）仍有限、压黑不炸；
6. 交叉区间（`.ssproj` 可直接给出）视口 == 导出，不过曝；
7. 面板布局：行不溢出分区 + 黑场标签可命中；
8. 真实鼠标把标签拖到底：`range >= MIN_TONE_RANGE`、`scale ≤ 20`、像素压黑不冲白；
9. 键盘通道（滑块自身 `change` 事件路径）得到同一组数字；
10. 直方图 / 范围选择在退化与交叉参数下不产生 Inf/NaN（真实调用 dataProcessor）。

全套件（42 个 verify 套件 × 2 后端）见 `docs/HANDOFF.md` 的批量脚本说明。

## 6. 经验

1. **"区间"参数必须在一个地方算**。同一个 `(blackPoint, whitePoint)` 曾被三处各写一遍，
   于是"范围 0"在视口是 1000、在导出是 2.5 —— 这类不一致查起来比崩溃更费时间。
2. **数值护栏要留死区**。`>= 0` 这种"刚好允许相等"的边界，一旦等号可达，
   下游就必然拿到 `0 / 0`；`MIN_TONE_RANGE = 0.05` 这种死区是廉价的保险。
3. **UI 交互类断言不能只断言"数值变了"**。这次"拖不动"不是逻辑错，是**命中区域被覆盖**；
   必须在套件里断言"标签真的能被 `elementFromPoint` 命中"，否则这条断言会长期空过/误报。
4. **布局用 `overflow: hidden` + 可收缩 flex 子项 = 内容重叠**。装不下时应该滚动，
   不该把分区压扁到互相覆盖 —— 覆盖的后果是"看得见但点不到"，最难被自动测试发现的一类缺陷。
