# 时间轴关键帧"位置不在当前帧、跳出去很远" —— 排查与修复（2026-09-21）

## 结论（先看这个）

用户报「webgpu 模式下，时间线大关键帧有时候会出现关键帧位置不在当前帧位置，跳出去很远」。
实测查出**两条与渲染后端无关的真 bug**（同一次探测在 WebGPU 与 WebGL2 上给出**逐位相同**的偏差，
所以"WebGPU 特有"是错觉 —— 打包版默认走 WebGPU，用户只在那儿看到）：

| # | 位置 | 现象 | 影响 |
| --- | --- | --- | --- |
| ① | `src/anim/spline.ts` 弧长分段记账 | 关键帧帧号处的求值**差"上一段弧长的 1%"** | 相机与关键帧标记**永远落不到关键帧上**；段越长偏得越远 ⇒ "跳出去很远" |
| ② | `src/camera/camera-path-3d.ts` `rebuildMesh()` 早退分支 | 删掉最后一个关键帧后，标记数组没被清空 | 画面里残留一个**幽灵关键帧方块**（停在已经没有关键帧的位置上）⇒ "位置不在当前帧" |

修复后：关键帧处的位置与 target 偏差 **≤1e-9（逐位精确）**，相机视图模式下擦洗到关键帧时
视口相机偏差 **0**；删光关键帧后标记数据与标记网格**都归零**。

## 现象为什么"有时候"、"很远"

偏差大小 = **上一段弧长 × 1%**，所以它只跟"那一段有多长"有关：

- 关键帧密（段短，例如中间插了很多隐藏控制点）：偏差小到看不见（均匀布局实测 0.012~0.048）。
- 关键帧稀（段长，例如 0→4→118→122→176 这种不均匀间距）：偏差明显（实测关键帧 118 前一段 114 帧
  → **0.0904**，176 前一段 54 帧 → **0.0656**，正好各段弧长的 1%）。
- 用户场景里关键帧之间常常跨几十上百帧、相机走了几十米 ⇒ **1% 段长就是"跳出去很远"**。

## 根因①：弧长重参数化"分段起点"记错了一个采样

时间轴的相机姿态走这条链：`timeline.frame → AnimationTrackBase.evaluate → onEvaluate →
spline.evaluateBySegmentArcLength(seg, localF)`（按段内**弧长**均匀推进），关键帧标记
（`CameraPath3D.rebuildMesh` → `track.getValueAt`）用的是**同一条**求值，所以两者一致 ——
**一起偏**。

`buildArcLengthTable()` 原来这样记账：

```ts
this._segmentStartArcs[seg] = this._totalArcLength;   // ← 在本段第一个采样**之前**记录
for (i = 0; i < count; i++) {
    ... this._totalArcLength += 弦长; segArcLength += 弦长;
    this._arcTable.push(time, this._totalArcLength);
}
```

而 `evaluateBySegmentArcLength` 用 `targetS = _segmentStartArcs[seg] + localF * _segmentArcLengths[seg]`
反查时间。问题在于：段首那条弦（上一段 localT=0.99 → 本段段首）是在 `_segmentStartArcs[seg]`
**之后**才累加的 —— 于是

- `localF = 0` 反查到的弧长对应**上一段 99% 处**（离关键帧差 1% 段长）；
- `localF = 1` 反查到的是**本段 99% 处**（永远到不了下一个关键帧）。

**修法**：按"段首采样在弧长表里的下标 → 下一段段首采样下标"重算每段的 `startArc / arcLength`
（`buildArcLengthTable` 里记录 `firstSampleIndex[]` 然后统一重算），并在
`evaluateBySegmentArcLength` 里对 `localF ≤ 0 / ≥ 1` **直接按时间求值**（段两端逐位落在关键帧上，
不依赖弧长表与二分插值的精度）。

## 根因②：删光关键帧后残留幽灵标记

`CameraPath3D.rebuildMesh()` 有三条早退分支（没有轨道 / 轨道没有关键帧 / 位置采样为空），
它们只做了 `this.mesh.primitive[0].count = 0`，**没清** `kfMarkers / kfMarkerFrames /
kfConePositions / kfSpherePositions / controlPoints ...`。而标记网格 `_cpMesh` 是"有标记就重建"，
于是删掉最后一个关键帧后，它继续按**上一次**的数组画 —— 实测：轨道 `keyframes.length = 0`，
元素仍留 **1 个标记（frame 73）/ 108 个顶点**，画面里就多出一个停在旧位置的关键帧方块。

**修法**：新增 `clearMarkerData()`（清全部标记类数组 + 归零标记网格 + 关掉实体），三条早退分支与
`scene.clear` 都走它；并且不破坏"删光后再加关键帧要能重建"。

## 排查过程（可复跑）

- `docs/probes/keyframe-marker.cjs`：造关键帧 → 逐帧擦洗 → 同时量**三条链路**：
  ① 元素持有世界坐标 vs 轨道求值；② 求值 vs 关键帧自身值（位置与 target）；③ **相机视图模式下
  视口相机**的实际位置。还带"均匀布局 / 不均匀大跨距压力布局 / 插入关键帧后 / 含隐藏控制点 /
  删光后"几个相位，以及 `_fixCameraPosition` 距离钳制的诊断（`rawArc` 与 `getValueAt` 对比）。
- 排除项：标记坐标与轨道值**逐帧一致**（偏差 0）；钳制**没有**在关键帧处触发（`clampDelta = 0`）⇒
  既不是"标记画错地方"，也不是"距离钳制把相机推走"。
- `docs/probes/keyframe-marker-pixels.cjs`：像素级归属探针（结论未依赖它，但记两个坑：
  `onPreRender` 每帧重设实体 `enabled` ⇒ 手动启停无效，要改 `isVisible()`；224 档灰是无限网格线，
  白色判据要 ≥248）。

## 护栏

`docs/verify/verify-keyframe-accuracy.cjs`（**7 项**，两后端 0 失败）：

1. 探针挂钩可用；
2. 均匀间距：关键帧处求值**逐位等于**关键帧值（位置 + target）；
3. 不均匀间距 + 长段：仍然逐位精确（修复前最大 ~0.09 世界单位 = 8% 场景半径）；
4. 插入隐藏控制点（真实编辑会产生）后仍精确；
5. **相机视图模式**下擦洗到关键帧：视口相机偏差 0；
6. 删光关键帧：标记数据与标记网格**都归零**（修复前 markers=1 / verts=108）；
7. 删光后重新加关键帧：标记与路径能重建且仍精确。

## 影响面 / 注意

- 根因①的修复会**改变回放轨迹**（这次是真修对：现在会精确穿过关键帧，之前每段都少走 1%）。
  隐藏控制点越多、段越短，改动越小。全量回归（两后端）已跑通。
- 两条都**不是**后端相关；不要再按"WebGPU 专属"方向排查。
