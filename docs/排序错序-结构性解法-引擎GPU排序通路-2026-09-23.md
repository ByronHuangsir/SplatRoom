# 排序错序的**结构性解法**：引擎自带的 GPU 排序通路（2026-09-23 实测发现）

> ## ✅ 2026-09-24 更新：这条路**在本机已实测可用**（不再是"待验证"）
>
> 起因：`docs/待办-引擎WebGPU-compute.md` 当时写着"引擎侧 WebGPU compute 不落地"，
> 那会让这条路的可行性悬着。2026-09-24 补了决定性测量，结论是**那条待办下得太宽**：
>
> * `_tmp/probe-compute-dispatch-count.cjs`（数 `device.computeDispatch`，60 帧旋转，test-layered）：
>   per-instance 通路 **0 次/帧**；unified 通路 **11 次/帧**。
> * `_tmp/probe-unified-toggle2.cjs`（同一次会话里就地翻转 `comp.unified`）：
>   `_placement` 建起来、`instance` 让位、`currentRenderer` 仍是 2、**零 pageerror**、
>   **画出了正确几何**（meanLuma 25.95 / lit 51.24%），切回来逐字节可逆。
> * 而 unified 的绘制**没有 CPU 兜底**（`GSplatHybridRenderer.setCpuSortedRendering()`
>   会把 `meshInstance` 关掉），所以"画面正确 + 每帧 11 次派发"就是引擎 compute 真的在跑、
>   结果真的被用上的直接证据 —— 不需要依赖已经证明不可信的 `StorageBuffer.read()`。
>
> ⇒ 可行性问题从"要先修引擎缺陷"降级成"**纯材质迁移工作量**"：引擎的投影器与 GPU 基数排序
> 都已经在跑，我们要做的是把材质挂上去。下面是当时的分析，仍然有效。

> 用户问题原话："即使在小模型上，也能在缓慢旋转的情况下出现排序错误，后面的内容翻转到前面。"
> 本文只写**已实测**的事实与它意味着什么；建议方案与取舍在文末。

## 1. 根因性质：这是**滞后**问题，不是排序质量问题

我们现在的顺序是"为某个位姿算出来的快照"，算完再回传主线程、上传成 orderTexture，
被消费时相机已经又转过一个角度。小模型上排序只要几毫秒，但**回传 + 上传 + 等一帧消费**
这条链的延迟与模型大小无关 ⇒ 慢速旋转也能看出错序。

## 2. 引擎里已经有一条"顺序与绘制同帧"的通路

`node_modules/playcanvas/build/playcanvas.mjs`（2.21.3，我们当前锁的版本）里有两套 splat 渲染器：

| 值 | 名称 | 排序在哪 | 顺序的位姿 vs 绘制的位姿 |
| --- | --- | --- | --- |
| 1 | `GSPLAT_RENDERER_RASTER_CPU_SORT` | worker 里排完 → 回传主线程 → 上传 orderTexture | **相差一段延迟**（就是用户看到的错序）|
| 2 | `GSPLAT_RENDERER_RASTER_GPU_SORT`（`GSplatHybridRenderer`）| 引擎自带 `ComputeRadixSort` + `GSplatProjector` + 间接绘制，**全在 GPU 上、同一帧内** | **同一帧**（无滞后）|

关键代码位置：

* `_createRenderer(mode)`（`playcanvas.mjs:88321`）：`mode === 2` 时建 `GSplatHybridRenderer`，否则建
  `GSplatQuadRenderer` + `initCpuSorting()`。
* `usesGpuSort`：基类返回 false（`:85368`），`GSplatHybridRenderer` 覆写为 true（`:87233`）。
* `update()`（`:88400`）里 `if (this.renderer.usesGpuSort) { … prepareRenderView(…) }`：
  **每帧**都跑投影 + GPU 基数排序 + 间接绘制（`:87331` `sortAndProjectForCamera`）。
* 相机移动判定 `testCameraMovedForSort()`（`:88363`）：每帧转角 > `1e-3` rad 即视为需要重排 ——
  比我们自己那道闸门的 `1e-6` 更宽松（更省），而**顺序永远是这一帧的**。
* 渲染后端解析 `_resolveRenderer`（`:35222`）：`AUTO(0)` 在 WebGPU 上就是 `GPU_SORT(2)`，
  在 WebGL2 上**自动退回** `CPU_SORT(1)`。

## 3. 实测：我们现在的状态（不是推测）

用一次性探针 `_tmp/probe-engine-renderer.cjs` 读运行时事实（WebGPU 后端、`test-layered.ply`）：

| 事实 | 值 |
| --- | --- |
| `scene.app.scene.gsplat.currentRenderer` | **2（GPU 排序）** —— 引擎设置层面早就是 GPU 排序 |
| 组件的 `entity.gsplat.unified` | **false**（我们每个 gsplat 组件都显式传了 `unified: false`）|
| `entity.gsplat.instance` | 有（per-instance 通路）|
| `entity.gsplat.instance.sorter` | 有（**worker 排序器**）|

⇒ **引擎的 GPU 排序通路只服务 unified 世界缓冲；我们把组件设成 `unified: false`，实际渲染因此
绕开了它，落到 per-instance + worker 排序上。** 这就是延迟的来源。

## 4. 实测：把组件切成 unified 会怎样

探针 `_tmp/probe-unified-toggle.cjs`（同一个模型、同一机位，切换前后各截一张）：

| 观测 | 切换前（per-instance）| 切换后（unified）|
| --- | --- | --- |
| 报错 | 无 | **无** |
| `comp.unified` | false | true |
| `_placement` | 无 | **有**（世界缓冲已接管）|
| `instance` | 有 | 无 |
| `currentRenderer` | 2 | 2 |
| 画面覆盖率网格（4×4）| 58/54/56/16 … 76/72/58/64 | **58/54/49/14 … 76/72/58/64（逐格一致）** |
| 平均亮度 | 92.6 | **23.0** |
| 像素差 | —— | MAD 69.7 / 55.2% 像素变化 |

**结论：unified 通路能画出结构完全相同的模型、零报错，但整体亮度约 1/3。**
这是**色彩空间 / 激活函数**差异的典型特征（unified 用的是引擎自己的 `gsplatPS`，而我们
per-instance 那边用的是我们定制的着色器，含我们自己的色调映射/伽马处理），不是几何或排序坏了。

（补一条历史：`src/core/gpu-frame-timing.ts:192` 记着"曾经误开 unified ⇒ frameTime 变成
1.79e12 ms、视口空"。本轮实测**没有**复现那个症状 —— 现在能出图、GPU 计时也没炸。
当时的失败很可能同时缺了别的接线，值得在真要做的时候再核一遍。）

## 5. 实测：错序本身降了多少（不依赖 GPU 回读的口径）

`docs/probes/sort-lag.cjs` 那套 `disp` 读的是 per-instance 的 `sorter.orderData`（CPU 表），
unified 通路的顺序在 GPU 缓冲里**读不回来**，所以这里换一个不需要回读的口径
（探针 `_tmp/probe-order-lag-visual.cjs`）：

> 同机位、**同样的慢速旋转步长**（0.5°/帧）、逐帧截图，看**帧间变化量**。
> 顺序滞后的表现是"这一帧还在用上一帧的顺序" ⇒ 同一小段旋转会产生更大的帧间跳变。
> 三组对照：现状 / unified / 停手（噪声下界）。相机步长完全相同 ⇒ 几何变化相同，
> 差异只可能来自顺序。

| 通路 | 帧间 MAD 平均 | 最大 | 变化像素 | 相对停手下界 |
| --- | --- | --- | --- | --- |
| **现状**（per-instance + worker 排序）| **0.11** | 0.32 | 0.46% | **3.7×** |
| **unified**（引擎 GPU 排序）| **0.04** | 0.11 | 0.10% | **1.3×** |
| 停手（不动，纯噪声下界）| 0.03 | — | — | 1× |

夹具 `test-layered.ply`（两层平板，故意做的"前后景深度差很大"，正是错序最容易看出来的场景）。
**结论：切到 unified 之后，慢速旋转下的帧间跳变从"近 4 倍噪声下界"回落到"基本贴着噪声下界"** ——
这正是用户报的"背面内容翻到前面"在量化口径下的对应物。

## 6. 这意味着什么

* **排序错序有一条"结构性"解法，不需要我们自研**：让 splat 走 unified 通路，
  引擎每帧在 GPU 上投影 + 基数排序 + 间接绘制，**顺序与绘制同一帧** ⇒ 滞后消失，
  慢速旋转下的"背面翻到前面"从根上不再存在。
* 代价是**材质要接**：unified 通路的材质由引擎提供（`UnifiedSplatHybridMaterial`），
  我们现在挂在 per-instance 材质上的东西（自定义 GLSL/WGSL 着色器块、逐通道曲线、
  裁剪盒、选区/描边 MRT、状态/变换贴图……）都得改从**世界缓冲**或引擎的材质扩展点接进去。
  这不是小工程，但它比"自研一套 OIT / 每像素合成"现实得多。
* **WebGL2 上没有这条路**（`_resolveRenderer` 自动退回 CPU 排序）⇒ 长期仍是双轨：
  WebGPU 用 GPU 排序（顺序同帧），WebGL2 继续 worker 排序（有滞后）。这与
  `docs/并行双轨-上游compute通路-计划-2026-09-22.md` 的双轨结论一致，但**这次的 GPU 通路是
  引擎自带的，不用搬上游代码**。

## 7. 全网调研的结果：哪些路能走、哪些是坑

一轮系统性检索（各家源码/文档/论文）的结论，按**对我们的适用性**排序。

### 7.1 先说一条行业事实：这个问题在别家也没有被"解决"

* **PlayCanvas 官方文档自己承认**（CPU 排序那条路）："Because sorting is asynchronous,
  **very fast camera motion can briefly reveal slightly out-of-date ordering** until the next
  sort completes." —— 我们踩的就是这句。注意它只承认"很快的运动"；用户**在小模型慢速旋转下**
  也能看到，说明我们的滞后比引擎设计的基线更长（这条怀疑很值得单独量，见 §7.4）。
* **Spark（World Labs）**文档：顺序"lags the render by at least one frame"，并称"通常察觉不到"。
* **mkkellogg/GaussianSplats3D** 把"移动/旋转太快时出现伪影（因为 CPU 排序）"写进 **Known issues**，
  把"某种增量排序"列为 future work；该项目已停止维护。
* 学术界的几乎全部工作攻的是**排序键的正确性**（StopThePop / VRSplat / TileGS / SAP），
  而不是**顺序的新鲜度**。也就是说：**文献能给你更好的顺序，生态能给你更新的顺序，这是两件事。**

### 7.2 六个候选，按优先级

| # | 方案 | 是什么 | 剩下什么伪影 | 我们的可行性 |
| --- | --- | --- | --- | --- |
| 1 | **顺序与绘制同帧**（引擎 GPU 排序 / 分块 compute）| 每帧在 GPU 上投影 + 排序 + 间接绘制 | 无（对当前位姿而言顺序精确）| **WebGPU 可行**：本轮已实测（§4/§5）。WebGL2 没有 compute ⇒ 不可能 |
| 2 | **少排一点**（压缩 + LOD 预算 + 变量宽度计数排序）| 只排可见集；用引擎那种"距离分箱"计数排序代替全 32 位基数排序 | 不修伪影本身，但把排序成本压到能"排得更勤" | 两端都可做，成本中低 |
| 3 | **径向排序 + 键复用** | 用 ‖p−c‖ 而非视深做键；纯旋转时键不变 ⇒ **可以整帧跳过排序** | 把 popping 从旋转搬到平移；**小模型+轨道相机收益很小**（见下面的警告）| 两端都可做，成本低 |
| 4 | **按 staleness 触发的无顺序路径 + 正确的随机透明** | 只在"手上这份顺序已明显过期"时切成无顺序 | 蒙特卡洛噪声（靠时域累积消）| 两端都可做；**但我们试过的那版是"欠做的"**（见 §7.3）|
| 5 | 分块（per-tile）排序 | 每个屏幕 tile 内排序、逐像素前向合成 | 无 | WebGPU only；实现量大（引擎 PR #8531 就是这个，尚未默认开）|
| 6 | 加权求和 OIT / 矩 OIT / 深度剥离 / 混合透明 | 用可交换算子替代 `over` | **比现状更糟**：不透明表面会变半透明/发浑；多数还要重训或要 compute | 不适合 |

**两处必须自己纠正的直觉**（调研里明确点出来的）：

* **"径向排序能解决旋转错序"—— 对小模型基本无效。** 对直径 D、距离 R≫D 的紧凑模型，
  ‖p−c‖ ≈ R − z，径向序与视深序**几乎是同一个序**。径向排序真正救的是"相机在场景内部原地转"
  （XR / 第一人称）。我们是轨道相机看外部模型 ⇒ **不要把它当解法。**
* **"premultiplied alpha 就不需要排序了"是错的**：premultiplied 只让 `over` 满足**结合律**
  （所以能分组合成），不满足**交换律**。顺序仍然要紧。

### 7.3 我们试过的那两条为什么失败（"正确版本"差在哪）

调研把 PlayCanvas/SuperSplat 的随机透明读到了源码级，与我们删掉的那版逐点对比：

| 点 | 他们 | 我们（已删）|
| --- | --- | --- |
| 噪声 | **蓝噪声纹理**（32×32）+ 每帧 `blueNoiseJitter` + **按 splat id 偏移** | 自写 hash（屏幕 quad + 视深），**不含时间项** |
| 采样数 | 1 spp + 时域累积（靠应用的 TAA）| 1 spp，**没有时域累积** |
| resolve | **不做空间 resolve**（顺序由深度测试 + 累积决定）| 自己加了 2×2 quad 平均 + 双线性（**对已着色的颜色做空间模糊**，不是样本解算）|
| 深度 | 接受后写深度、深度测试定可见性 | 同 |
| 触发条件 | SuperSplat 默认 `Auto` = **"排序帧在你这台机器上慢了才切"** | 我们是"相机一动就切" |

→ **我们那版"看起来像实心圆盘 + 噪声"不是这条路不行，是欠了三样**：蓝噪声去相关、
时域累积、以及"不要对已着色颜色做空间 resolve"。论文侧也有量化对照
（StochasticSplats, ICCV 2025：1 spp MSE 0.0211 → 4 spp 0.0072 → 16 spp 0.0020），
并明确指出低 spp 就是 noisy、要靠 TAA 累积。

**还有一条关键策略差异**：SuperSplat 的 `Auto` 是"按**成本**切"，而我们这种**小模型慢速旋转**
的场景里排序帧永远不慢 ⇒ `Auto` **永远不会触发**，问题照旧。所以若重做这条路，
**触发条件必须改成"按 staleness 切"**（当前顺序与当前位姿的角度差超过阈值）——
这是调研里没有先例、需要我们自己的判断。

### 7.4 现在最该先做的一件事（比换通路便宜得多）

调研指向一个可验证的怀疑：**150 ms 这个量级更像"排队"而不是"排序耗时"**（60 Hz 下 150 ms ≈ 9 帧）。
我们已经有合并器（在飞时只记最新位姿、完成后补发一次），但它究竟把端到端延迟压到了多少、
其中"结果落地 → 真正画到屏幕上"占几帧，**从没量过**。而小模型上排序本身只要几毫秒 ——
如果结论是"排队/消费时机占了大头"，修这一条就能把现状的错序压掉很大一块，
**代价远小于换通路**。

（`docs/probes/sort-lag.cjs` 那套 `disp` 口径读的是 per-instance 的 CPU 排序表；
unified 通路的顺序在 GPU 缓冲里、读不回来 —— 见 §7.5 第 4 条。）

### 7.5 下一步

1. **先量滞后链**：在"派发 → worker 回包 → 落地 → 真正画出"四点上打时间戳，得到端到端延迟
   与"排序位姿 vs 显示位姿"的角度差；再看合并器/消费时机能不能直接压掉大头。
2. **把材质接通**（真正的工作量所在）：引擎给了官方扩展点 ——
   `scene.gsplat.varyings.add([{name, type, components}])`（`GSplatVaryings`，`playcanvas.mjs:34838`）
   会自动生成"compute 写入 + 顶点读回 + 片元 varying"三处代码（WebGPU 侧走
   `gsplatUserCacheWriteCS` / `gsplatUserCacheReadVS`）。逐项迁移并跑对应护栏：
   * 逐通道曲线调色 / 色调 / 饱和（曲线护栏）
   * 有向裁剪盒（`verify-*crop*`）
   * 选区 / 描边 / underlay（MRT RT1；`verify-selection-*`）
   * 状态与变换贴图（现在是我们的 `splatState` / `splatTransform` 材质参数）
   最大的一处是**色彩空间**：本轮实测 unified 画面亮度只有现状的 1/3（结构一致、零报错），
   说明 unified 走引擎 `gsplatPS` 那套输出，伽马/色调映射要对齐。
3. **WebGL2 的取舍**：`_resolveRenderer` 在 WebGL2 上自动退回 CPU 排序 ⇒ 滞后依旧。
   要么接受双轨（WebGPU 好、WebGL2 旧），要么做 §7.2 里的方案 2/3/4（都不需要 compute）。
4. **回读那条坑不要重踩**：unified 的顺序在 GPU 缓冲里，`StorageBuffer.read()` 在 WebGPU 下不可信
   （见 `docs/待办-引擎WebGPU-compute.md`）。要验证 unified 的排序**内容**，
   得走渲染回读（把 order 写到一张可读纹理）或统计口径，别指望直接读 buffer。
